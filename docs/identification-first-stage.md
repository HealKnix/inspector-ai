# Документы и редакции: первый этап

Внутри объекта раздел «Документы и редакции» показывает логические документы, редакции и файловые представления выбранного расчёта. PDF/XML одного акта учитываются один раз, если собственные реквизиты полностью установлены и согласованы. Неполные или конфликтующие реквизиты уточняет назначенный инспектор с обязательным основанием.

## Работа инспектора

Начало пути — страница «Загрузка комплекта» внутри объекта. После приёма файлов
система обрабатывает их и обновляет список. «Сведения подтверждены» означает,
что учтено сохранённое решение инспектора. Отдельное «Проверьте файл» относится
к чтению или составу оригинала и не снимается исправлением номера или даты.

В блоке «Комплектность» можно раскрыть предложенный перечень и подтвердить его.
Только после подтверждения и расчёта по текущим документам показываются
выполненные требования, недостающие документы и оставшиеся вопросы. Неизвестный
состав не означает, что загруженных документов достаточно.

1. Дождаться завершения обработки и открыть документ. Источник показан рядом с короткой карточкой: для АОСР это вид, номер и дата, место и период работ. Ссылка на РД показана отдельно от собственного номера.
2. Сверить сведения с документом и при необходимости исправить. Система сама подбирает источник сравнения по существующей политике. Когда требуется решение, карточка задаёт конкретный вопрос о применимости или неоднозначной редакции. Подтверждение реквизитов не означает утверждение редакции.
3. Нажать «Подтвердить и проверить» либо «Сохранить и проверить». Отдельного шага добавления в пакет нет. Действие сохраняет основание сверки и только явно подтверждённые показанные значения; заметку можно дополнить. Пока форма не отправлена, расчёт её не использует.
4. Создаётся новый Run того же процесса с прежними оригиналами. Совместимые результаты PAR переиспользуются по hash и версии pipeline с отдельными записями артефактов нового Run; предметные результаты вычисляются заново. История решений и прежние расчёты доступны отдельно от основной формы.
5. Вернуться к загрузке и нажать «Проверить документы». После завершения обработки действие формирует протокол по текущим источникам и открывает существующий экран проверки. В списке показаны только вопросы по найденным сведениям с цитатой и местом в документе, а также сохранённые решения. Пустые результаты и автоматические совпадения не добавляют карточек. Покрытие всей матрицы учитывается отдельно: отсутствие находок не означает, что все параметры проверены.
6. Выбрать находку справа. При наличии доказательств открываются зафиксированные документы и страницы, выделяются относящиеся к этой находке фрагменты. Разные области и периоды одного параметра остаются отдельными находками. Прежний протокол и его доказательства доступны в истории. Финализация оставляет протокол доступным для чтения после обновления страницы.

Уточнение разрешено в PENDING, READY, VERIFYING, COMPLETED при отсутствии обработки. PARSING и FINALIZED закрыты для изменений сервером. Конкурентное изменение карточки или расчёта возвращает 409; необходимо перечитать результат и сверить правки.

Пустое поле означает отсутствие установленного значения, а не доказанное отсутствие
реквизита в оригинале. Подтверждение уже верных значений использует тот же API
уточнений и создаёт новый расчёт; отдельной отметки проверки без пересчёта нет.
Автоматический выбор сравнения не снимает требования подтверждённой применимости.

## Запуск и обновление

Аддитивная миграция: `backend/prisma/migrations/20260925120000_document_identification/migration.sql`. Применить обычным `bun run --cwd backend prisma:deploy`, затем пересобрать backend/frontend. Миграция сохраняет прежние документы и протоколы без пересчёта. Новая идентификация выполняется существующим `classification-worker`; отдельный сервис не добавлен. Для полного цикла также нужен `extraction-worker`. Локальный `bun run dev:all` запускает оба worker; перед запуском нужна backend-сборка, как описано в README.

## Контракт API

- `GET /api/v1/processes/:processId/documents?run_id=…` — реестр выбранного Run.
- `GET /api/v1/processes/:processId/documents/:documentId?run_id=…` — карточка, доказательства и история.
- Оба GET дополнительно принимают `resolved_input_hash` для точного исторического снимка внутри Run; ответ содержит `snapshot_versions`, актуальность и `allowed_actions`.
- `POST /api/v1/processes/:processId/document-resolutions` — `request_id`, `expected_run_id`, `basis`, массив `documents` с `document_id`, `expected_version` и изменениями `revisions`. Идентичный повтор возвращает тот же Run; изменённое содержимое с прежним ключом даёт 409.
- Ручной `classification/resolve` требует те же версии, ключ и основание и использует общий сервис уточнений. Старый запрос только с `kind_code` отклоняется явно.
- Чтение классификации дополнено `review` из актуального снимка и `review_active` для ожидания идентификации. Исходный машинный `result` сохранён; подтверждение реквизитов и ограничения исходного файла передаются отдельно.
- Исторические PAR-доказательства читаются с `run_id` и `artifact_id` вместе. Параметр `artifact_id` без `run_id` сохраняет проверку текущего результата.
- Протокол и находки принимают `protocol_id` для истории. Старые доказательства без достоверного снимка возвращаются с `historical_evidence_not_recoverable`; текущая группа вместо них не подставляется.
- Находки содержат `has_evidence` и `evidence_preview`, вычисленные только по сохранённому снимку. Предпросмотр содержит значение и цитату первого достоверного фрагмента; число записей самого протокола не изменяется при фильтрации интерфейса.

Схемы запросов и ответов публикуются в OpenAPI. Deep link реестра: `/objects/:objectId/documents?processId=…&runId=…&documentId=…&revisionId=…&resolvedInputHash=…`.

## Границы

Автоматически поддержаны целые документы. Сборные PDF, частичная замена листов, неизвестная область, период или утверждение блокируют соответствующее сравнение. `edition`, `Signed`, поздняя загрузка и максимальный номер не означают применимость. Предложения LLM требуют проверки.

Автоматическое разделение сборных PDF, анализ подписей/печатей, качество всех 132 правил, производительность и полный граф INC остаются последующими этапами. Интеграционные тесты с PostgreSQL/RabbitMQ используют синтетические результаты парсера для проверки транзакций, выбора и сохранности истории; они не измеряют качество OCR.

На локальном стенде 26.09.2026 каталог содержит 132 параметра, но валидные
исполняемые правила извлечения есть для 12, а сравнение настроено у 11 из них.
Это техническая исполнимость, а не подтверждённая точность правил. Отсутствие
правила уменьшает покрытие проверки и не создаёт карточку находки; оно не является нарушением или
доказательством отсутствия сведений в документах.

Результаты проверки: [OpenSpec evidence](../openspec/changes/add-document-identification/evidence.md).
