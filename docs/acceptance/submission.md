# Передача контракта EXPORT

Источник — участнический `data/submission_schema.json`, прямо указанный в QA H5. Оба выданных участнических комплекта содержат одни и те же байты. У схемы нет `$id`, поля версии или номера редакции; `2020-12` обозначает диалект JSON Schema, не версию контракта. Точная закреплённая версия — SHA-256 `75c58bef6b580528e7e4af8e4fdcdf5a5d40599b8966dae90df38b3a5f04a8d7`. Нельзя назвать её «1.0», изменить enum или добавить обязательный bbox от имени организатора.

Оригинальная [схема](contracts/submission_schema.json) сохранена побайтно. Обязательны `object_id`, `checks`; у точки — `parameter_code`, `location`, `violation_label`, `evidence`; у ссылки — `stage`, `file_id`, `pdf_page_number ≥1`. Внешние enum сохраняются только в адаптере, не заменяют внутренние статусы/решения инспектора.

Внутренние коды `P001…P132` отличаются от кодов внешнего каталога (`PZ-001`, `IOS4-079` и т. д.). [Таблица соответствия](contracts/parameter-code-map.json) проверена для всех132 строк по parameter_id, matrix_row, имени и единице; исходные хеши сохранены. EXPORT переводит код явно по этой таблице, не отправляет внутренний `P001` как будто это код оценщика и не переименовывает существующие MatrixRow. При изменении исходного каталога соответствие перепроверяется; это идентичность строки, не допуск её правила.

QA H17 задаёт атомарный ключ `object_id + parameter_code + location` (`check_id` как идентификатор), а finding group объединяет связанные точки. Внешняя схема не требует `check_id`; внутренний адаптер сохраняет его связь в trace/sidecar. Групповой ответ допустим только с покрытием всех atomic locations и полным evidence. Не сериализовать список комнат в одну строку вместо нескольких точек и не создавать фиктивный 133-й код для гипотез вне Матрицы: их самостоятельный rule_id остаётся во внутреннем доказательном протоколе до согласования внешнего расширения.

`submission.mjs` использует Ajv draft2020-12 и выдаёт два результата:

- `schema_valid` — точная внешняя схема. Она допускает неизвестные дополнительные поля, пустые массивы, произвольные value и не задаёт bbox. Это свойство исходного контракта, а не разрешение считать пустую сдачу качественной.
- `semantic_valid` — локальный предварительный контроль: известные object/parameter/file, принадлежность файла объекту и стадии, подтверждённый диапазон PDF-страниц, непустая атомарная location без дублей; definite `VIOLATION_PRESENT/NO_VIOLATION` требуют evidence. `MISSING_DOCUMENT/COMPARISON_IMPOSSIBLE` могут не иметь источника. Этот слой явно не выдается за дополнительную схему организатора.

Семантический контроль не доказывает актуальность редакции, правильность значения/нарушения, покрытие всех expected locations, полноту стадий или IoU. Эти проверки выполняет независимый оценщик по GOLD и полной внутренней EvidenceGroup (§14, QA H33). `full_evidence_group_quality_verified` всегда false для проверки одного submission. Публичный page-level gold не превращается в координатный gold автоматически.

EXPORT должен использовать закреплённую схему как целевой формат, реализовать адаптер и передать реальный output в этот валидатор (ACC2.2). Текущие fixtures — синтетические проверки структуры с публичными file IDs, не результаты продукта и не новые экспертные выводы. Новая схема организатора требует сохранения новой версии/digest и обновления fixtures/адаптера после сравнения.

Старый [scoring_summary](contracts/scoring_summary_without_answers.json) описывает 100-балльный рейтинг и cap59. Позднее QA H16 задаёт 40 баллов (30 экспертная часть, 10 питч). Для текущего H применяем поздний источник; старую формулу не запускаем и не выдаём локальный score за официальный. Точные веса/алгоритм внешнего оценщика сверх выданной схемы не опубликованы. Это не меняет самостоятельные пороги качества §14.
