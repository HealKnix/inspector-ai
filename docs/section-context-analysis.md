# Секционный анализ контекстов

После идентификации и публикации снимка источников инспектор может запустить секционный анализ: сначала находятся границы нужных разделов в выбранных источниках, затем их содержимое сопоставляется сразу по нескольким реальным пунктам Матрицы, и инспектору показываются проверяемые факты. Это отдельный технический конвейер: он не заменяет регулярное извлечение и не выносит вердиктов.

Задания, результаты и идемпотентные квитанции хранятся в PostgreSQL (`section_analysis_tasks`, `section_analysis_receipts`, `section_index_cache`); доставка идёт через существующий transactional outbox и очередь `inspector.extraction.artifacts` того же `extraction-worker`. Отдельный worker процесс не создаётся.

Функция выключена по умолчанию. `SECTION_LLM_ENABLED=false` — и приём запроса, и исполнение отклоняются конфигурацией; настроенная классификационная LLM сама по себе отправку секционного текста не разрешает.

## Конфигурация

В корневом `.env` для Docker Compose, либо в `backend/.env` для локальных процессов. Значения передаются только сервисам `backend` и `extraction-worker`:

```dotenv
SECTION_LLM_ENABLED=true
SECTION_LLM_BASE_URL=
SECTION_LLM_MODEL=
SECTION_LLM_API_KEY=
SECTION_LLM_TIMEOUT_MS=
SECTION_LLM_MAX_REQUEST_BYTES=262144
SECTION_LLM_MAX_RESPONSE_BYTES=
SECTION_LLM_MAX_CANDIDATE_BYTES=49152
SECTION_LLM_MAX_CHUNK_BYTES=98304
SECTION_LLM_MAX_BLOCK_CHARACTERS=4000
SECTION_LLM_MAX_PARAMETERS_PER_REQUEST=8
SECTION_LLM_MAX_CALLS=32
SECTION_LLM_MAX_EXPANSION_CANDIDATES=8
```

Пустые значения `BASE_URL`, `MODEL`, `API_KEY`, `TIMEOUT_MS` и `MAX_RESPONSE_BYTES` наследуют настройки `CLASSIFICATION_LLM_*`; задавать их нужно только для секционного переопределения. Ключ хранится только на сервере, без префикса `VITE_`, и не входит в отпечаток конфигурации задачи. Ограничения запросов, чанков, кандидатов, параметров на вызов и общего числа вызовов фиксируют потребление на один анализ; исчерпание бюджета вызовов — допустимый ограниченный результат с честной отметкой покрытия, а не техническая ошибка.

Настройки API и worker должны совпадать: отпечаток конфигурации входит в семантический базис задачи, поэтому смена провайдера, модели, версий промптов/движка или бюджетов делает прежний результат устаревшим и не публикуемым как текущий.

После обновления кода и `.env` обычный запуск применяет миграции и поднимает worker:

```sh
docker compose --env-file .env up -d --build --wait --wait-timeout 900
```

Локально: `bun run --cwd backend prisma:deploy`, затем обычный `bun run dev:all`. Аддитивная миграция `20260928020000_section_analysis` применяется тем же `migrate deploy`, что и остальные.

## API

- `POST /api/v1/objects/:objectId/section-analysis` с `{ "request_id": "UUID", "expected_run_id": "UUID", "parameter_codes"?: ["P001", …] }` — идемпотентный приём, HTTP 202. Без `parameter_codes` анализируются все строки закреплённого импорта Матрицы. Повтор того же `request_id` возвращает записанную квитанцию и не пересоздаёт задачу; каждый новый `request_id` выбирает текущий базис анализа Run, включая повторный выбор уже завершённой задачи с той же семантикой без обращения к провайдеру.
- `GET /api/v1/objects/:objectId/section-analysis?run_id=…` — прогресс и текущий результат выбранной задачи (`no-store`): техническое состояние, отпечатки базиса, признак устаревания и сами результаты только пока базис полностью актуален.

Доступ проверяется по назначению инспектора на объект, с теми же блокировками объект→процесс, что у соседних сервисов. Провайдер не вызывается ни внутри HTTP-запроса, ни внутри транзакции: допуск только создаёт долговечную задачу и событие outbox.

## Результаты

`results` содержит проверенные сервером факты из движка: оценки по выбранным параметрам с цитатами-доказательствами в обеих ролях сравнения, покрытие контекстов и список пропущенных контекстов. Наряду с суммарным покрытием контекста движок возвращает покрытие по отдельным строкам Матрицы; для чтения старых результатов это поле остаётся опциональным. Не найденный раздел одного параметра не отменяет обоснованный факт по другому. Общая неопределённость источника или границ влияет на все связанные параметры. Неподтверждённые или неполные места помечаются недостатком покрытия.

Границы разделов кэшируются в `section_index_cache` по семантическому ключу (содержание источника и выборки, конвейер парсинга, модель, версии промптов/движка, идентичность Матрицы); идентификаторы Run в ключ не входят, поэтому выборки переиспользуются между запусками без повторных вызовов.

Первый LLM-запрос получает компактные кандидаты из заголовков и оглавления с соседними блоками. Дополнительный контекст запрашивается в пределах бюджета. После проверки границ код собирает полный текст выбранных разделов, включая доступные таблицы и примечания. Большие разделы разбиваются на части; итог по частям требует отдельного согласования моделью либо отмечается как неполный. Лимит размера учитывает весь JSON-запрос провайдеру, включая схему ответа и инструкции. Нераспознанные таблицы или области на страницах раздела также мешают объявить покрытие полным.

## Работа инспектора

На экране верификации доступны запуск анализа, его состояние и ошибки. После завершения генерация протокола включает факты по пунктам Матрицы, даже если для них нет регулярного извлекателя. Точный численный или составной результат существующего движка сохраняет приоритет.

Карточка показывает предварительную оценку, описание факта, вопрос инспектору, недостающий контекст и цитаты с переходом к нужному PDF. Название файла и страницы начала/конца раздела выводятся из проверенных сервером источников. Факт, границы, цитаты, версия Матрицы и основание анализа сохраняются в неизменяемом снимке находки.

Оценка LLM не подтверждает нарушение автоматически. Инспектор подтверждает нарушение, отклоняет его как отсутствие расхождения или запрашивает уточнение в рамках существующих правил доступности доказательств. Изменение факта, вопроса или покрытия не переносит прежнее решение на новые данные. Незавершённый повторный анализ и устаревшие источники блокируют решение или финализацию по прежнему основанию. При выключении функции ранее сохранённые доказательства остаются читаемыми.

## Долговечность и повторы

Задача арендуется с возобновляемым lease и heartbeat; истёкшая аренда и потерянная доставка восстанавливаются recovery-циклом worker. Таймауты, обрывы, HTTP 429 и 5xx дают до трёх попыток с задержкой; терминальные ошибки провайдера и невалидный ответ завершают задачу технической ошибкой, при этом частичный проверенный результат сохраняется в записи. Отмена по сигналу остановки worker не может завершиться публикацией успеха. Смена Run, финализация процесса, новый снимок источников, другая Матрица или другой отпечаток конфигурации переводят задачу в `section_superseded` либо помечают её результат устаревшим — он не выдаётся за текущий.

## Тесты и качество

Интеграционные тесты (`backend/test/section-analysis.test.ts`) поднимают реальный Nest-модуль на изолированной базе с применёнными миграциями и детерминированным исполнителем: провайдер не вызывается. Они проверяют допуск, идемпотентность, порядок выбора базиса, повторы, fencing и публикацию — но не качество извлечения на реальном корпусе документов. Оценка качества секционного поиска и фактов требует прогона на реальных разобранных документах с включённым провайдером.

`backend/test/section-verification.test.ts` проверяет полный путь через настоящий движок анализа, задание, HTTP-генерацию протокола, замороженные доказательства и решение инспектора; подменены только ответы LLM. Итоговые команды, результаты независимых прогонов и ограничения проверки записаны в `openspec/changes/add-section-context-analysis/evidence.md`.
