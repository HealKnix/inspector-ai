# Начальный офлайн-комплект

## Профиль первого этапа и подключение новых модулей

Проверяемый профиль — Linux/amd64, Node.js 24.16.0, Docker Engine 29.1.2 и Compose v2. Bun 1.4.2 остаётся менеджером пакетов при сборке. Текущий локальный стенд предоставляет Docker 12 CPU и 7.36 GiB RAM; это характеристика стенда, а не доказанный минимум для любой нагрузки. Для отдельной установки выделяют не менее 8 GiB RAM и 25 GiB свободного места под образы/архив/модели/пустые volumes; объём документов и резервных копий рассчитывают дополнительно. Одновременную работу нескольких тяжёлых OCR-заданий этот ранний профиль не обещает.

Для Docker Desktop проверяют свободное место и на диске хранения его виртуального диска: расположение исходников/архива на D не означает, что образы и volumes тоже хранятся там. Независимый Docker-in-Docker стенд создаёт ещё одну распакованную копию образов; несколько кандидатов увеличивают этот объём. После освобождения места и перезапуска Docker 27.09 кандидат r8 прошёл установку на новых томах, smoke 91/91 и повтор bootstrap; отдельно подтверждено восстановление 9/9 образов в пустой daemon без сети. Результаты и границы раннего допуска указаны в [evidence OFF](../openspec/changes/add-offline-release-bundle/evidence.md).

| Компонент                              | Ограничение раннего профиля                                       | Дальнейшая приёмка                                                                                          |
| -------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Parser                                 | 2 CPU, 4 GiB RAM, `/tmp` 512 MiB; локальные 9 моделей             | PAR измеряет GPU-путь, OCR-качество и совместимость CUDA/драйвера                                           |
| Validator                              | Ограничения существующего Compose, изолированный локальный сервис | Большие/повреждённые файлы остаются в регрессиях ING                                                        |
| ClamAV                                 | Включённые main/daily/bytecode; автоматический FreshClam выключен | Оператор задаёт допустимый возраст базы; новое обновление проходит упаковку/проверку снова                  |
| API/4 workers/PG/Rabbit/Redis/frontend | Совместно используют оставшийся ресурс стенда                     | Итоговый бюджет проверяют по ACC на целевой площадке                                                        |
| GPU/VRAM                               | В раннем CPU-профиле не используются                              | H100, совместимость драйвера и квоты — незакрытая проверка PAR/OFF; CPU fallback не объявлен условием сдачи |

Новый модуль добавляет в поставку образ с зафиксированным image ID, версии/источники/лицензии/размеры локальных ресурсов, проверку готовности и миграции. Его startup и рабочий сценарий проверяют в той же закрытой сети. Runtime-загрузка зависимостей не допускается. Обновление модели меняет lock/manifest; отсутствие модели должно давать явную причину отказа. Новый MAT-выпуск должен иметь подтверждённое право переноса regression fixtures: исторический экспорт специально отказывается переносить новые паспорта/отчёты, чтобы не включить в комплект приватные цитаты документов. После появления такого контракта он заменяет этот ограниченный экспорт, сохраняя review hashes и обязательный approve gate.

Комплект первого этапа переносит реализованное ядро: образы, локальные OCR-модели, сигнатуры ClamAV, точный исторический каталог/утверждённые правила и инфраструктуру. Он не заявляет полное покрытие 132 правил, завершённые HYP/GOLD/ML или проверку H100. [План](../openspec/RELEASE_PLAN.md) и [границы/права](operations/foundation-decisions.md) сохраняют эти различия.

## Подготовка в разрешённой сетевой среде

На машине сборки нужны Docker, Node.js ≥22.18, исходники с Bun lockfile и существующие локальные модели/сигнатуры. Подготовка может получать образы/зависимости; запуск переданного комплекта не скачивает их.

```sh
node scripts/offline/bundle.mjs build .test-output/offline/foundations-20260927 foundations-20260927 inspector-ai
```

Если точный каталог уже сохранён в проверенном комплекте, пятым аргументом можно передать его директорию. Сборщик проверит manifest и возьмёт только `catalog.json`, не обращаясь к рабочей БД. Образы собираются из текущих исходников, локальные модели/сигнатуры по-прежнему читаются из указанных source volumes. Это позволяет повторить сборку при выключенной рабочей установке без копирования её данных.

Последний аргумент — имя исходного Compose-проекта. Чтение БД производится транзакцией REPEATABLE READ READ ONLY, только для справочников/утверждённых правил. Пользователи, credentials, документы, parse artifacts и решения в bundle не копируются. Исторические авторы/время утверждения и идентификаторы правил сохраняются как provenance; это не новый approve и не доказательство качества правил. Новый код допуска MAT работает для всех новых версий.

Папка назначения должна быть пустой. В ней появятся `images.tar`, `assets`, `catalog.json`, `compose.json`, инструменты установки и `manifest.json` с image IDs, размерами и SHA-256 каждого поставляемого файла. Зафиксируйте SHA-256 самого manifest отдельно вместе с передачей. Копирование нового runtime.env в передаваемый комплект запрещено: он создаётся уже у получателя.

## Установка на пустом стенде

Предпосылки: Linux Docker Engine с Compose v2 (либо Docker Desktop с Linux containers), x86-64, Node.js ≥22.18, свободные RAM/disk для закреплённого профиля. Начальная проверка использует CPU parser; обязательный GPU-профиль официальной сдачи принимается отдельно после PAR-device. Фактические размеры и image IDs берутся из manifest, аппаратные ограничения — из отчёта прогона, не из количества CPU в названии стенда.

```sh
node tools/bootstrap.mjs . inspector-offline 18080
```

Команда сначала сверяет файлы и image IDs. Если хотя бы одного точного образа нет, выполняется `docker load`; после любой ветви все IDs проверяются повторно, выбранная ветвь записывается в отчёт. Затем создаются уникальные локальные секреты, запускается закрытый контур, восстанавливаются модели/сигнатуры, применяются миграции и создаётся начальный администратор существующей deployment-командой. Затем восстанавливается точный каталог. Существующий отличающийся каталог не перезаписывается; повтор установки с теми же данными идемпотентен. Параметр проекта изолирует контейнеры/volumes; не указывайте имя рабочей установки.

Адрес приложения — `http://127.0.0.1:18080`. Секреты/пароль начального `release.admin` доступны только в созданном `<project>.runtime.env`; скрипт печатает путь, а не значения. Администратор не становится инспектором и не получает чужие документы. Нового инспектора назначают штатными средствами управления доступом.

Все сервисы имеют `pull_policy: never`; build отсутствует. Модельный API отключён в исходном ядре и не указывает на внешний URL. Ядро использует только сеть `internal`. Frontend дополнительно подключён к ingress bridge для публикации порта на `127.0.0.1`: Docker Engine 29 не публикует порт контейнера только на internal bridge.

Поставочный `offline-runtime` frontend перед запуском Nginx закрывает исходящий IPv4/IPv6 правилом OUTPUT DROP; разрешены ответы на входящие соединения, loopback и внутренний backend:3000. Внешний DNS отключён. Затем entrypoint удаляет NET_ADMIN/NET_RAW из bounding set и запускает Nginx с no-new-privileges. NET_ADMIN нужен только для установки правил; ошибка настройки завершает запуск. Стенд должен поддерживать контейнерные iptables/ip6tables. Frontend без этой защиты на внешней сети валидатор не принимает. Smoke проверяет фактический доступ с хоста, firewall/capabilities и отказ внешнего HTTP/DNS отдельно от здоровья контейнеров. При смене IPv4 backend frontend нужно пересоздать: адрес фиксируется при старте, а несовпадение приводит к отказу доступа.

Ошибка модели, отсутствующий файл, hash mismatch или недоступный сервис прерывают установку; успешный HTTP health не заменяет функциональную проверку.

`<project>.installation.json` фиксирует digest комплекта, время, состав восстановленного каталога и режим runtime. Сквозной smoke, отсутствие внешнего соединения и независимый docker load проверяются отдельно и записываются в [evidence OFF](../openspec/changes/add-offline-release-bundle/evidence.md). Проверка полного релиза остаётся ACC, а данные рабочего стенда не считаются её результатом.
