# MAT-A: паспорт и проверка допуска

Версия контракта: `matrix-review-v1`, 27.09.2026. Основание: MTR-01/02/07 и задачи 1.1–1.4 в `add-reviewed-matrix-release`. Продолжение 27.09: подключены интерфейс администратора, численная политика v1 и закреплённые выпуски. Ремонт предметных правил и полный выпуск 132/132 ещё не приняты; точный охват — в [отчёте реализации](IMPLEMENTATION_2026-09-27.md).

## Снимок существующих правил

`mat-a-legacy-inventory-2026-09-27.json` получен из рабочей БД одной транзакцией `REPEATABLE READ READ ONLY`. Он содержит MatrixImport/MatrixRow/RuleVersion, без документов объектов, токенов, паролей и содержимого артефактов. Имена импортировавших пользователей исключены; технические UUID авторов исторических правил сохранены. Никакие рабочие версии не переутверждались.

Снимок содержит 132 уникальных кода P001–P132, 104 версии правил и 13 записей `approved` для 12 параметров: P001/P002/P003/P004/P007/P009/P015/P019/P022/P023/P056/P058. У P002 остались две approved версии: v2 и v5; существующий worker выбирает последнюю по номеру версии. У 12 выбранных версий 11 comparison; P004 не имеет comparison. Предыдущая ошибка P019 с номером пункта `1.` не считается исправленной на основании inventory. Seed содержит только P002/P007/P015 и не восстанавливает эту БД.

В `mat-a-legacy-manifest-2026-09-27.json` сохранены hashes итогового PDF, XLSX, легенды, JSONL, всего inventory и каждой approved версии/плана/comparison. `legacy_review` явно содержит неизвестные паспорт/основания/регрессию и `corpus_accuracy: null`. Восстановление этого точного исторического снимка на пустой разрешённой БД — отдельная операция поставки OFF; оно не означает нового утверждения и не даёт права обойти gate новым правилам. Файл inventory нельзя форматировать без обновления его byte hash в manifest.

Дополнительно сохранён канонический JSON hash inventory для переноса между LF/CRLF. Исторический hash JSONL относится к LF; текущий Windows-файл содержит CRLF, но после явной нормализации hash совпадает, как и все 132 raw-строки. Проверка из корня: `node docs/matrix/verify-mat-a-inventory.mjs`. Она только читает данные, проверяет оба вида hash и отдельно сообщает, сохранены ли исходные байты.

## API и права

Все операции находятся под существующим `ADMINISTRATOR` guard в `/api/v1/admin/matrix`. Новые полномочия не добавляются. Контекст автора и request id устанавливает сервер; клиент не передаёт автора отчёта.

| Операция                        | Назначение                                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `GET review-contract`           | Исполняемые JSON Schema полей `passport` и `regression`, версия 1                                                |
| `GET rules/:ruleId/review`      | История паспортов и последних 100 отчётов; отсутствие исторического review явно обозначено                       |
| `POST rules/:ruleId/passport`   | Добавить неизменяемую редакцию паспорта draft; идентичный повтор возвращает прежнюю запись                       |
| `POST rules/:ruleId/regression` | Исполнить проверенные fixtures текущего паспорта, сохранить серверный отчёт; клиентский `passed/report` запрещён |
| `POST rules/:ruleId/approve`    | Существующий маршрут, теперь требует прошедшую регрессию точного текущего содержания                             |

Схемы и типы находятся в `backend/src/modules/extraction/matrix-review-contract.ts`, исполнение — `matrix-regression.ts`. OpenAPI указывает маршрут полной JSON Schema. Для больших корпусов нельзя снимать общий HTTP body limit: MAT-A принимает ограниченные контрольные fixtures, а не загружает целые корпуса через admin API.

Порядок для нового правила: создать draft → получить ID исходной MatrixRow → сохранить паспорт → передать контрольные fixtures → проверить сохранённый report → вызвать approve. Dry-run и ответы LLM остаются диагностикой/предложением. Batch больше не вызывает approve; `matrix:seed` создаёт только отсутствующие draft, не меняя старые версии.

## Паспорт и неизвестные основания

Паспорт содержит `schema_version`, `matrix_row_id`, проверяемую величину `quantity`, `applicability`, `scope`, стадии `sources`, `unit`, `rounding` и обязательные `branches`. Сервер добавляет точную связь с импортом, hashes JSONL/XLSX/raw-строки, кодом параметра и исходным триггером. Клиент не подменяет эти поля пересказом модели. Raw MatrixRow остаётся неизменной.

Каждая ветвь содержит собственный id, `operator`/`version`, `basis_required`, nullable `basis` и четыре категории примеров. Основание хранит ссылку, редакцию, locator, известные даты применимости. Неизвестное основание остаётся `null`. Если оно необходимо ветви либо comparison задаёт численный допуск/порог/округление, approve блокируется без основания. Неизвестные quantity/applicability/scope также блокируют допуск. Unit сверяется с подтверждённой целевой единицей. Строка `rounding` должна точно совпадать с JSON явной политики CMP; произвольная неподдержанная формулировка не допускается.

В категориях `positive`, `negative`, `boundary`, `uncertain` значение `null` означает обязательный пример. Непустая строка — явно записанное основание неприменимости категории; полностью освободить ветвь от примеров нельзя. Основание исключения сохраняется в отчёте и hash паспорта. Категория uncertain должна действительно содержать неопределённый исход, а не переименованный match.

## Контрольные примеры и отчёт

Fixture содержит id/branch/category, provenance (`synthetic` или `curated`, reference, permission), хешированные ParseArtifact inputs с ролями expected/actual и вручную заданные ожидания. Для curated обязателен источник разрешения. Каждый input проходит существующую строгую проверку ParseArtifact; заявленный artifact hash сверяется с каноническим JSON.

Ожидания задают точные `status/value_raw/value/unit/evidence` для каждого input, включая page, block, bbox, quote, table/structural locator, и `verdict` для сравнения. Runner вызывает существующие `executePlan` и `evaluateGroup`, а не принимает присланный результат. Отсутствующий пример, несовпадение значения/единицы/локатора/вывода или неизвестный исполнитель запрещают успешный отчёт.

Отчёт фиксирует hash плана/comparison/applicability/паспорта, hashes fixtures, версии исполнителей, ожидаемые и фактические результаты, ошибки, категории/исключения и автора серверной записи. `corpus_accuracy` всегда `null`: эта инженерная регрессия не заменяет независимую оценку ACC. Синтетические примеры помечаются даже при успешном отчёте. Приёмка реального предметного правила требует разрешённых эталонов и проверки оснований владельцем партии; MAT-A не заявляет качество текущих 12 правил.

## Порт для CMP/C07/GEO/C09

Сейчас выполняются только `extraction` с `extraction-engine-v3` и `comparison` с `comparison-engine-v3`. Численная ветвь требует [точной политики](NUMERICAL_POLICY.md), единиц с локаторами и основания допуска/округления. В паспорт можно записать будущую ветвь, но отсутствие точного исполнителя возвращает `unsupported_operator_version` и блокирует её допуск. Декларация версии сама по себе не включает алгоритм.

Владелец нового оператора предоставляет версию и детерминированный адаптер, добавляет его в runner, расширяет версионированную схему fixture/expected для собственных evidence и проверяет категории примеров. При несовместимом изменении повышаются версия контракта/исполнителя и fingerprint; прежний report не подходит для нового approve. CMP выполняет подтверждённые конверсии, округление и интервальную арифметику; извлечение реальной погрешности и приёмка на корпусе остаются открытыми. У C07 остаются дерево условий и presence, у GEO — масштаб/GeometryResult, у C09 — временные источники и события. Для разработки не требуется полный MAT-F.

## Хранение и конкурентность

Миграция `20260927010000_matrix_review_gate` добавляет RulePassport/RuleRegressionReport и запрещает UPDATE/DELETE их записей триггерами. Исторические RuleVersion без review читаются как раньше. Изменяется только ограничение времени утверждения deprecated-версий: теперь можно сохранить первоначальные approvedBy/approvedAt вместо их удаления; существующие строки не переписываются.

Создание draft, паспорт, публикация report, approve и reject используют один PostgreSQL advisory lock по параметру. Вычисление регрессий выполняется вне транзакции, затем повторно проверяются hash правила и последний passport. Approve проверяет текущую исходную строку, содержание паспорта, hash плана и версии исполнителей. Изменение любого из этих входов требует нового отчёта. Утверждение, снятие прежней active версии и audit фиксируются одной транзакцией; аудит содержит IDs/hashes паспорта и отчёта.

Миграция проверяется на отдельной случайной тестовой БД. Рабочая БД использована только для inventory; применение production-миграции принадлежит шагу развёртывания.
