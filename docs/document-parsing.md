# Парсинг документов: запуск ветки

Ветка `feat/document-parsing` включает безопасную загрузку ING и обработку PAR.
Для запуска нужны Git, Docker Engine с Compose и доступ в интернет при первой
сборке образов и загрузке моделей. Во время обработки Python-сервис работает в
изолированной сети; оригиналы доступны ему только для чтения.

## Первый запуск

```sh
git fetch origin
git switch --track origin/feat/document-parsing
cp .env.example .env
```

Если локальная ветка уже существует, используйте `git switch feat/document-parsing`
и `git pull --ff-only`. В PowerShell вместо `cp` можно использовать `Copy-Item`.
При обновлении существующей установки сохраните её `.env` и добавьте недостающие
переменные из примера.

В `.env` задайте три **разных** случайных секрета длиной не менее 32 символов:
`JWT_SECRET`, `JWT_REFRESH_SECRET`, `PARSER_TOKEN`. Последний используется только
между backend и локальным Python-сервисом. Секреты не коммитятся. Удобная команда
для генерации одного значения, если установлен Node.js:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Подготовьте модели отдельно от документов, затем запустите приложение:

```sh
docker compose --profile tools run --rm --build parser-models
docker compose up -d --build
docker compose ps
```

Первый шаг скачивает девять закреплённых моделей PP-StructureV3 в volume `parser-models`
и проверяет SHA-256 всех 27 файлов. Используется русский распознаватель
`eslav_PP-OCRv5_mobile_rec` и детектор `PP-OCRv5_mobile_det` с пределом 1536 px.
Повторный запуск использует сохранённые модели. Runtime монтирует этот volume
только для чтения. Миграции БД применяет сервис `migrate`, оригиналы и результаты
сохраняются в отдельных volumes. Не удаляйте volumes при обновлении.

Откройте [http://localhost:8080](http://localhost:8080). Первоначальное назначение
ролей описано в [README](../README.md): регистрация сама по себе не даёт прав
на чужие объекты, администратор не получает доступ к документам автоматически.
Если порт занят другим приложением, задайте в `.env`, например, `FRONTEND_PORT=8082`
и повторите `docker compose up -d backend frontend`; адрес интерфейса станет
`http://localhost:8082`, backend получит соответствующий разрешённый Origin.

## Что проверить в интерфейсе

1. Войти инспектором, создать или открыть назначенный объект.
2. Загрузить PDF, DOCX или XML. После безопасного приёма каждый файл получает
   отдельное фоновое задание; ранее загруженные необработанные файлы также подхватываются.
3. Дождаться результата в разделе обработки. Закрытие вкладки не отменяет работу.
4. Открыть документ. В новом PDF-результате выбрать «Области»: границы и список
   показывают текст, таблицы, графику и неопределённые зоны. Выбор зоны открывает
   её содержимое или причину пропуска. Во вкладке «Таблицы» проверить строки и столбцы,
   во вкладке «Весь документ» — извлечённый текст, включая шапку и заключение.
   Перейти к странице и нажать на текстовый фрагмент или ячейку:
   выделение должно совпасть с его положением на странице. Для DOCX/XML показывается
   воспроизводимое представление содержимого, а оригинал можно скачать отдельно.
5. Для проблемного результата прочитать причину. Технический сбой и низкое качество
   распознавания различаются. Доступный повтор использует сохранённый оригинал.
6. После завершения обработки загрузить улучшенный скан при необходимости.
   Это новый источник; прежний оригинал и его история не перезаписываются.

По решению владельца этап PAR переводит текущий процесс в `PARSING`, затем после
сохранения всех исходов файлов — в `PENDING`. Результаты файлов остаются доступны.
`READY` требует настоящего протокола и на этом этапе не выставляется. Классификация,
комплектность и проверки по Матрице относятся к следующим изменениям.

PDF сначала размечается Paddle по оригинальному изображению. В text/table
областях пригодный native-текст извлекается напрямую; OCR читает непокрытые
строки и сканы. Native-таблицы восстанавливаются по геометрии PDF, растровые —
компонентами PP-StructureV3. Graphic/unknown сохраняются без OCR. Их native-надписи
доступны в полном тексте, но исключены из обычного списка фрагментов.
Полный текст и отобранные фрагменты ещё не являются доказательствами для Матрицы.

Качество выделения областей пока ограничено: модель может пропустить подпись
или принять план за таблицу. Поэтому исходный класс, способ обработки и причины
доступны в просмотрщике; неизвестный тип не заменяется догадкой. Автоматический
редактор и VLM не подключены. Старые результаты открываются с сообщением об
отсутствии разметки; для получения областей нужен новый запуск обработки.

## Настройки и диагностика

- `PARSER_FILE_TIMEOUT_SECONDS` — предел одной попытки обработки файла, по умолчанию
  600 секунд. Автоматических попыток не более трёх; ручной повтор создаёт новый цикл.
- `PARSER_MODEL_READY_WAIT_SECONDS` — непрерывное ожидание готовности моделей,
  по умолчанию 300 секунд. После него сохраняется техническая ошибка с обычным
  ручным повтором. Прогресс и проверенные checkpoints не обнуляются при ожидании.
- `PARSER_CPU_THREADS` — число потоков OCR, по умолчанию 2. Compose ограничивает
  Python-сервис двумя CPU и 4 ГБ памяти. Эти настройки не являются подтверждением
  целевой производительности ТЗ.
- Redis хранит только кеш. Его потеря не удаляет опубликованные результаты.
- Модели, Python-пакеты, шрифт и конфигурация входят в версию обработки; несовместимый
  результат не используется как подходящий кеш.

```sh
docker compose logs --tail=100 parser parsing-worker worker
docker compose ps
```

Если `parser` не готов, сначала проверьте завершение команды подготовки моделей,
`PARSER_TOKEN` и доступную память Docker. При обновлении моделей заново выполните
шаг подготовки, затем пересоздайте `parser` и `parsing-worker`. Документы в логи
не выводятся; для диагностики используйте идентификаторы файла/задания и код ошибки.

Качество OCR и ограничения текущей реализации фиксируются в
[отчёте PAR](../openspec/changes/add-document-parsing/evidence.md).
Высокая уверенность модели не доказывает правильность числа или знака: значимые
фрагменты доступны для проверки по оригиналу. Общая независимая приёмка C24
проводится отдельно.

PP-StructureV3 включён в рабочий сервис по решению владельца. Общий OCR-текст
сохраняется вместе с результатом разбора ячеек; это два представления одной страницы,
поэтому отдельные фрагменты могут повторяться. Исходный HTML модели не выполняется:
просмотрщик создаёт таблицу из текста и проверенных индексов/объединений ячеек.
Непригодная сетка отклоняется с `TABLE_STRUCTURE_REJECTED`, доступный текст остаётся.
Это правило отсекает часть ложных таблиц, но не гарантирует понимание чертежей.

В [предварительном эксперименте](pp-structure-v3-experiment.md) паспорт получил
две таблицы, но ошибка в знаке сохранилась. Уверенность OCR не заменяет сверку
значимых чисел с изображением. Старые результаты доступны с прежним названием
движка; для нового разбора нажмите «Повторить обработку» у файла.

## Разработка с API и frontend на хосте

Используйте отдельный режим из README: установите Bun 1.4.2, зависимости и
`backend/.env`/`frontend/.env`. Добавьте в `backend/.env` `PARSER_TOKEN`,
`PARSER_URL=http://127.0.0.1:8090`, `REDIS_URL=redis://127.0.0.1:6379`.
Перед запуском создайте каталоги `backend/var/documents/originals`, `derived`
и `quarantine`. На Linux выполните
`export LOCAL_UID=$(id -u) LOCAL_GID=$(id -g)` перед командами Compose:
parser и validator получат доступ к bind mounts от имени текущего пользователя.
На Windows используются значения по умолчанию.

```sh
docker compose --env-file backend/.env --profile tools run --rm --build parser-models
docker compose --env-file backend/.env -f compose.yaml -f compose.dev.yaml up -d --build postgres rabbitmq redis clamav validator validator-proxy parser parser-proxy
bun run --cwd backend prisma:deploy
bun run build
```

В трёх терминалах из корня проекта:

```sh
bun run dev
bun run --cwd backend worker
bun run --cwd backend parsing:worker
```

Интерфейс доступен на порту 5173. Локальный proxy публикует parser только на
127.0.0.1; сам Python-сервис остаётся в изолированной сети. При пересоздании
parser перезапустите `parser-proxy`, чтобы Nginx обновил адрес контейнера.
