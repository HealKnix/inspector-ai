## 1. Область действия и порядок работы

Этот файл определяет правила разработки и сопровождения всего репозитория. Локальные `AGENTS.md` могут уточнять правила своего каталога, но не должны незаметно ослаблять требования к безопасности, целостности данных и совместимости API.

Перед изменениями изучи корневой и локальные `AGENTS.md`, `README.md`, `package.json`, lock-файл, конфигурацию инструментов и код затрагиваемого сценария. Сначала найди существующее решение, затем расширяй его. Не создавай параллельную реализацию уже решённой задачи.

Вноси минимальные законченные изменения. Не переписывай соседние модули, не меняй стек и не обновляй major-версии зависимостей без необходимости и явного согласования. Не отменяй чужие изменения в рабочем дереве.

Пиши код для людей, которые будут его сопровождать: понятные имена, явные зависимости, небольшие функции, предсказуемый поток данных. Не вводи абстракции, универсальные фабрики и дополнительные архитектурные слои «на будущее».

При расхождении задания, документации и фактического контракта явно укажи конфликт. Не маскируй неопределённость выдуманными требованиями. Примеры структуры каталогов и организации кода ниже являются инженерными рекомендациями, а не спецификацией предметной области или внешнего API. Существующие публичные контракты нельзя менять без проверки совместимости.

После работы опиши сделанные изменения, выполненные проверки и оставшиеся ограничения. Не утверждай, что тесты, сборка или интеграция работают, если соответствующие проверки не запускались.

## 2. Назначение продукта и терминология

Полное наименование: «Интеллектуальный сервис для автоматической сверки трёх массивов строительной документации: проектной, рабочей и исполнительной». Краткое наименование в интерфейсе: «Инспектор ИИ».

Сервис выполняет автоматизированную камеральную проверку документации объектов капитального строительства: проектной документации (ПД), рабочей документации (РД), исполнительной документации (ИД).

Основные возможности: выявление несоответствий по 132 контролируемым параметрам; верификация результатов инспектором с решением и обоснованием; обмен документами и результатами через API, включая целевую интеграцию с ИАИС «Разрешения и нарушения» («РиН»); контроль комплектности и инкрементальная дозагрузка до финализации протокола.

После принятия документов сервер возвращает `process_id`. Анализ выполняется асинхронно. Клиент получает статус и результаты отдельными запросами по Pull-модели. Закрытие вкладки или отмена HTTP-запроса не должны отменять уже принятую серверную обработку.

Различай автоматическую находку, результат верификации инспектором и техническую ошибку. Завершённый анализ не означает отсутствие нарушений, завершённую верификацию или финализированный протокол. Это смысловые различия, а не перечень значений статусов.

### Роли и разграничение доступа

На платформе предусмотрены три роли:

| Роль | Подтверждённое назначение |
| --- | --- |
| Инспектор | Просмотр документации и результатов проверок; верификация выявленных несоответствий с фиксацией решения и обоснования. |
| Администратор | Управление параметрами проверки и нормативной базой. |
| ML-инженер | Доступ к логам и данным дообучения. |

Эта таблица фиксирует назначение ролей, а не полную матрицу разрешений на все операции. Машинные коды ролей, возможность их совмещения, область видимости данных и права на отдельные действия определяются документацией. Не добавляй другие роли и не назначай дополнительные полномочия по предположению. В частности, права на загрузку, финализацию, экспорт и управление пользователями нельзя автоматически выводить из названия роли.

Не считай администратора обладателем всех прав по умолчанию. Его назначение не означает автоматического права верифицировать результаты от имени инспектора. Доступ ML-инженера к логам и данным дообучения сам по себе не даёт прав изменять решения инспектора, нормативную базу, запускать дообучение или развёртывать модели.

Проверяй разрешения на backend для каждой защищённой операции и конкретного ресурса. Frontend отображает доступные разделы и действия на основании авторизованного контекста, но скрытие элементов не заменяет серверную проверку. Роль нельзя принимать на доверии из тела запроса, URL или клиентского store. При отсутствии подтверждённого разрешения не предоставляй его автоматически.

Корневой `package.json` должен быть приватным и объявлять `workspaces: ["frontend", "backend"]`. Корневые scripts координируют workspace-команды; приложения сохраняют собственные scripts и зависимости. [S2]

Frontend не импортирует backend-код, Prisma Client и серверные переменные окружения. API связывает приложения через явный контракт. Генерацию клиентских типов из OpenAPI можно использовать при наличии воспроизводимого процесса; сгенерированные файлы не редактируются вручную.

Не создавай дополнительный workspace или отдельный микросервис без реальной потребности. API и worker могут запускаться разными процессами из одного backend-workspace.

Структура задаёт границы ответственности, а не обязательный набор пустых папок. Создавай каталоги по мере появления кода. Допускаются обоснованные упрощения, сохраняющие понятное расположение файлов.

`api/client.ts` содержит настроенный Axios-клиент. `api/endpoints` — типизированные HTTP-функции без React и UI. `api/hooks` — query/mutation-хуки. `api/types` — транспортные DTO, ответы и ошибки API. Ключи запросов храни согласованно в API-слое.

`components` содержит компоненты, используемые в разных частях приложения. Страничные компоненты остаются в `pages/<page>/components`, пока не появились независимые потребители. Локальные хуки, типы, схемы и функции размещай рядом с владельцем, а не в глобальных каталогах.

`hooks` предназначен для действительно общих React-хуков, не являющихся API-хуками. `lib` — для общих функций и настройки библиотек. `const` — для общих констант. `types` — для общих frontend-типов, не дублирующих транспортные DTO. `store` — для общего клиентского состояния. `layouts` — для каркасов страниц. `routes` — для маршрутов и их композиции.

Страницы не импортируют внутренности других страниц. Общие компоненты не зависят от страниц и конфигурации маршрутов. Не допускай циклических импортов. `index.ts` используй как небольшой публичный интерфейс модуля; не создавай общий barrel-файл, экспортирующий всё приложение.

## 6. React и читаемость компонентов

`main.tsx` отвечает за запуск приложения и подключение глобальных стилей. `App.tsx` остаётся тонкой точкой композиции маршрутов и оболочки. Провайдеры выноси отдельно. Не размещай в `App` загрузку документов, polling, обработку результатов, формы, таблицы и бизнес-правила.

По умолчанию используй функциональные компоненты и хуки; классовый Error Boundary допустим для обработки ошибок рендера. Компонент должен отвечать за понятную часть интерфейса; при росте разделяй его по ответственности, а не механически по числу строк. Такой подход соответствует модели декомпозиции React. [S3]

Уже при 200–300 строках оцени необходимость разделения. Компоненты на 500–1000 строк должны быть декомпозированы, если только размер не обусловлен исключительным и документированным случаем. Не переноси всю сложность в один огромный `usePage` вместо огромной страницы.

Отделяй отображение, управление взаимодействиями и чистые преобразования данных. Хук должен инкапсулировать связную логику и возвращать небольшой понятный интерфейс. Не создавай универсальные компоненты с десятками флагов для несвязанных сценариев.

Не используй `useEffect` для вычислений, которые можно выполнить при рендере, и для действий, относящихся к конкретному пользовательскому событию. Эффекты нужны для синхронизации с внешними системами; подписки, таймеры и создаваемые ресурсы должны освобождаться. Не отключай Strict Mode ради сокрытия повторных эффектов.

Не добавляй `memo`, `useMemo` и `useCallback` повсеместно. Оптимизируй измеренную проблему или обоснованно дорогую операцию. Для списков используй устойчивые идентификаторы, а не индекс изменяемого массива.

## 7. Состояние, формы и маршрутизация

Распределяй состояние по владельцу:

| Вид состояния | Где хранить |
| --- | --- |
| Документы, процессы, результаты, серверные статусы | TanStack Query |
| Поля, ошибки и состояние формы | React Hook Form |
| Локальное раскрытие, выбор, состояние модального окна | `useState` или `useReducer` |
| Общее клиентское состояние между независимыми частями UI | Zustand |
| Ссылка на процесс, фильтры, сортировка, пагинация для навигации | URL и React Router |

Не копируй query-данные в Zustand или локальный state без отдельной причины. Не создавай собственный кеш запросов поверх TanStack Query. Производные значения вычисляй из источника данных.

Zustand-store должен иметь ограниченную ответственность. Используй селекторы. Не сохраняй в browser storage документы, результаты анализа, токены и персональные данные без отдельного решения по безопасности. Для сохраняемых пользовательских предпочтений предусматривай версию и сброс состояния.

Формы реализуй через React Hook Form и Zod. Схемы держи рядом с формой; типы выводи из схем, когда это применимо. Для управляемых компонентов используй адаптацию через `Controller`, если обычная регистрация не соответствует их API.

Клиентская валидация улучшает интерфейс, но не заменяет серверную. Показывай ошибки рядом с полями, сохраняй введённые значения при сетевом сбое, блокируй повторную отправку на время запроса. Обоснование решения инспектора валидируй после удаления внешних пробелов.

React Router отвечает за навигацию. Глубокая ссылка на процесс должна работать после перезагрузки. Не используй URL как хранилище конфиденциальных сведений. Не запускай одну загрузку данных одновременно в router-loader и query-хуке без общего механизма кеширования.

## 8. API-клиент и Pull-модель

Все HTTP-вызовы к backend проходят через `api/client.ts` и `api/endpoints`. Настрой общий base URL, таймауты и нормализацию ошибок. Компоненты не создают свои Axios instances и не конструируют URL эндпоинтов вручную.

HTTP-функции возвращают данные контракта, а не `AxiosResponse`. Критичные ответы проверяй по runtime-схеме, а не только типизируй через generic Axios. Ошибки не преобразуются в пустой успешный ответ. Интерцепторы не показывают UI, не содержат доменную логику и не создают бесконечные повторы. Механизм авторизации подключай согласно контракту, не придумывай refresh-flow заранее.

Ключи запросов должны учитывать идентификатор процесса, параметры выборки и доступные по контракту признаки актуальности результата. Не вводи отсутствующее в контракте поле версии ради ключа запроса. При смене пользователя, его прав или другого подтверждённого контекста доступа исключай доступ к кешу предыдущего контекста. После мутации адресно обновляй или инвалидируй затронутые запросы.

Polling статуса реализуй через `refetchInterval` TanStack Query, а не через независимые `setInterval` в компонентах. Запускай его только для доступного `process_id`. Условия продолжения, остановки и возобновления polling после дозагрузки определяй по документированному контракту мониторинга. Не придумывай терминальные статусы и не определяй их по похожим названиям. Пока контракт не предоставлен, не зашивай предполагаемый жизненный цикл в query-хуки. [S4]

Учитывай скрытую вкладку, потерю сети, восстановление соединения и уход со страницы. Интервал должен настраиваться; соблюдай серверные рекомендации по частоте запросов. Ограничивай повторы и не повторяй автоматически постоянные ошибки доступа или валидации. Помни, что остановка `retry` сама по себе не отключает интервальный polling. [S4]

Передавай `AbortSignal` из query-функции в Axios. Для отменяемой загрузки управляй сигналом отдельно; не считай отмену клиентского запроса гарантией отмены уже выполненной серверной операции. [S5]

Не повторяй мутации загрузки, решения и финализации автоматически без серверной идемпотентности. После неоднозначного сетевого сбоя сначала уточняй состояние операции.

Отделяй прогресс передачи файла от прогресса анализа. Не показывай искусственные проценты обработки. Если сервер сообщает только этап, показывай этап согласно контракту. Если документация предусматривает показ исторических результатов, явно обозначай их актуальность. Не выдавай результат предыдущей обработки за результат текущего комплекта и не финализируй протокол по результату, не относящемуся к фиксируемым документам.

## 9. HeroUI v3, Tailwind CSS v4 и интерфейс

HeroUI v3 — основная UI-библиотека. Сначала используй подходящий компонент библиотеки; собственную реализацию создавай при отсутствии нужной возможности. Не подключай вторую UI-библиотеку и не оборачивай каждый HeroUI-компонент без дополнительной ценности.

Проверяй реальный экспорт, props, события и composition API в установленной v3. Не выдумывай компоненты по аналогии с другой библиотекой. Сохраняй клавиатурную навигацию, управление фокусом и доступные имена элементов.

Для новой Vite-конфигурации используй `@tailwindcss/vite`. Базовый порядок импортов глобального CSS: [S1] [S6]

```css
@import "tailwindcss";
@import "@heroui/styles";
```

Не переноси конфигурацию Tailwind v3 автоматически. Общие цвета, типографику, отступы и другие дизайн-токены определяй централизованно. Не собирай динамические utility-классы из неполных строк; используй явные варианты.

Интерфейс и пользовательские сообщения — на русском языке. Идентификаторы кода — на английском. Используй единые названия ПД, РД, ИД, «проверка», «несоответствие», «обоснование», «протокол».

Для каждого экрана предусмотрены технические состояния интерфейса: ожидание ответа, отсутствие данных, ошибка запроса, отсутствие доступа и отображение полученных данных. Это состояния UI, а не значения доменного статуса или API. Отображение хода проверки, комплектности, результатов и протокола должно опираться на предоставленную документацию; не добавляй от себя бизнес-статусы или поддержку частичных и исторических результатов.

Критические ошибки и ограничения показывай непосредственно в контексте действия, а не только уведомлением. Отсутствие результата и технический сбой нельзя представлять как отсутствие несоответствий. Подписи и визуальные признаки бизнес-статусов связывай только с документированными значениями. Статус передавай текстом и визуальным признаком, не одним цветом.

Дозагрузка должна показывать категорию ПД/РД/ИД, состояние каждого файла и понятную причину отказа. Финализация требует явного подтверждения последствий. Таблицы должны оставаться читаемыми при длинных названиях; пагинация и фильтры не должны незаметно исключать результаты из итоговых счётчиков.

## 10. Архитектура backend

Используй модульную архитектуру NestJS с разделением по предметным областям. Пример:

```text
backend/
├── prisma/
│   ├── schema.prisma
│   └── migrations/
├── test/
└── src/
    ├── main.ts
    ├── worker.ts
    ├── app.module.ts
    ├── config/
    ├── common/
    ├── infrastructure/
    │   ├── prisma/
    │   ├── rabbitmq/
    │   └── storage/
    └── modules/
        ├── processes/
        ├── documents/
        ├── analysis/
        ├── findings/
        ├── protocols/
        ├── audit/
        └── integrations/
            └── rin/
```

Это ориентир, а не требование создать все модули заранее. Модуль может содержать controllers, services, DTO, локальные типы и тесты. `common` не должен становиться складом несвязанных функций.

Контроллеры принимают и валидируют входные данные, вызывают прикладной сценарий и возвращают ответ. Сервисы реализуют сценарии и бизнес-правила. Доступ к данным и внешним системам изолируется через понятные зависимости. Не создавай repository-обёртку над каждой Prisma-операцией без пользы.

Тяжёлый анализ выполняется worker-процессом, а не внутри HTTP-запроса. RabbitMQ используется для фоновых заданий, а не как база статусов. PostgreSQL хранит долговечное состояние процессов, запусков, результатов и решений.

Валидируй HTTP DTO, сообщения очереди, конфигурацию и ответы внешних сервисов во время выполнения. TypeScript-типы не заменяют эту проверку. Для backend придерживайся единого механизма валидации NestJS; не смешивай несколько подходов без необходимости.

## 11. Версии документов, запусков и результатов

### Статусы и переходы

Все бизнес-статусы документов, обработки, результатов, решений инспектора и протокола, если такие статусы предусмотрены, должны браться из предметной документации, которая будет добавлена в проект. Этот раздел намеренно не содержит примерных состояний, машинных значений или схем переходов.

Не создавай собственные enum, строковые литералы, справочники статусов и переходы ни на frontend, ни на backend. Не считай общепринятые названия состояний частью контракта. Не превращай смысловые описания в этом файле в отдельные поля статуса без документированного основания.

После появления документации используй точные значения, определения и допустимые переходы из неё. На их основе согласованно реализуй серверную валидацию, типы API, схемы, отображение, polling, разрешённые действия и тесты. Переходы проверяются на backend; frontend не выводит разрешение операции только по подписи статуса.

Если сервер вернул значение вне поддерживаемого контракта, обрабатывай это как несовместимость данных: не сопоставляй его с ближайшим известным статусом, не показывай успех и не разрешай зависящие от статуса действия. Пользовательское сообщение о невозможности определить состояние не является новым бизнес-статусом. Неизвестное значение не должно запускать бесконечные повторные запросы.

### Идентификаторы и версионирование

Из исходных требований подтверждено возвращаемое поле `process_id`. Остальные идентификаторы, поля версий, состав сущностей и связи между документами, обработкой и результатами определяются документацией. Не вводи в API или схему БД предполагаемые поля и не приписывай `process_id` дополнительную семантику.

Порядок обработки дозагрузки также определяется документацией: сохранение или изменение `process_id`, создание новых запусков, версий и исторических результатов нельзя выбирать по предположению. Подтверждённое требование — возможность инкрементальной дозагрузки до финализации протокола; оно само по себе не задаёт конкретную модель версионирования.

При реализации документированной модели обеспечивай прослеживаемость результата до фактически использованных документов, параметров и нормативной базы. Не подменяй незаметно данные, на которых уже основаны результаты или решения. Защищай актуальные данные и финализированный протокол от перезаписи запоздавшим или повторно обработанным заданием. Конкретный механизм реализуй в соответствии с утверждённой моделью, не добавляя для этого выдуманные публичные поля.

Инкрементальная дозагрузка не означает, что достаточно анализировать только новые файлы: изменения могут затрагивать сравнение с ранее загруженными документами. Правила повторного анализа и повторного использования результатов бери из документации. При отсутствии таких правил не обещай инкрементальный пересчёт и не принимай старые результаты за актуальные; зафиксируй недостающие требования.

## 12. Надёжность очереди и асинхронной обработки

Проектируй обработчики с учётом повторной доставки RabbitMQ. Идемпотентность должна обеспечиваться идентификатором задания и ограничениями БД, а не только флагом сообщения или проверкой в памяти процесса. [S7]

Не допускай разрыва «процесс сохранён, задание потеряно». Базовый подход — transactional outbox: запись запуска и намерения отправить задание сохраняются в одной транзакции PostgreSQL, отдельный отправитель доставляет событие в RabbitMQ. Эквивалентный механизм допустим при проверяемой гарантии восстановления.

Сообщение содержит идентификаторы, версию схемы и контекст трассировки, а не бинарные документы. Используй устойчивые очереди, persistent messages и publisher confirms; проверяй маршрутизацию сообщения. Подтверждение брокера не означает завершение анализа. [S8]

Consumer подтверждает сообщение после долговечного сохранения результата или обработанного исхода. Не используй автоматическое подтверждение для критичных заданий. Ограничивай параллелизм и prefetch; настрой таймаут подтверждения с учётом длительности работы. [S8]

Повторы должны иметь предел, задержку и различать временные и постоянные ошибки. После исчерпания попыток сохраняй техническую причину сбоя и направляй задание в dead-letter-механизм; изменение доменного статуса выполняй только согласно документации. Не создавай бесконечную немедленную повторную постановку.

Предусмотри восстановление после падения worker, потерянного соединения и зависшего запуска. Если используются lease или heartbeat, просроченный worker не должен перезаписать результат нового владельца задания. Повторная доставка не создаёт дубликаты находок, решений и протоколов.

## 13. Загрузка и контроль комплектности

Проверяй на сервере допустимость типа файла, размер, количество, категорию документа и права пользователя. Не доверяй расширению и клиентскому MIME. Ограничения определяются конфигурацией и контрактом; не придумывай поддерживаемые форматы и лимиты. Для архивов ограничивай также распакованный объём и глубину вложенности. [S9]

Оригиналы храни через storage-адаптер вне публичной директории приложения. PostgreSQL хранит метаданные и ссылки; конкретное файловое или объектное хранилище выбирается отдельно. Не загружай большие файлы целиком в память без необходимости. Выдача оригинала требует проверки доступа. [S9]

Не смешивай факт передачи файла с результатом его анализа и не выводи из этого собственные доменные статусы. Документ допускается к обработке только после надёжного сохранения и необходимых проверок. Семантику приёма пакета и частичного отказа бери из документации; не сообщай об успешной загрузке всех файлов при отказе части из них. Очищай незавершённые загрузки и потерянные временные объекты.

Правила определения дубликатов и замены документов бери из документации. Совпадение имени само по себе не доказывает, что файлы одинаковы; совпадение содержимого не определяет их предметное назначение. Повтор уже принятой операции не должен создавать дополнительные последствия: механизм защиты согласуй с контрактом идемпотентности.

Комплектность рассчитывай по утверждённому перечню обязательных документов с учётом применимости. Наличие хотя бы одного файла ПД, РД и ИД не означает полный комплект. До получения перечня не формируй выдуманный список недостающих документов и не объявляй комплект полным. После дозагрузки обновляй предусмотренные контрактом сведения о комплектности и актуальности результатов.

## 14. Правила проверки, решения и финализация

### Контролируемые параметры

Подтверждено количество контролируемых параметров — 132, но их перечень и содержание ещё не предоставлены. Состав реестра, коды, описания, применимость, алгоритмы, нормативные основания и правила изменения бери из документации. Не создавай 132 фиктивные записи и не заполняй их предположениями. Не размазывай число `132` и перечень параметров по компонентам.

Не выдумывай нормативные ссылки, допуски и отсутствующие правила. До получения утверждённого реестра не заявляй покрытие неизвестных требований; отсутствие спецификации обозначай как ограничение реализации, а не как результат анализа. Нереализованная проверка не может возвращать успешный исход.

Допустимые исходы проверки и их машинные значения определяются документацией. Отсутствие данных, сбой выполнения и отсутствие реализации нельзя выдавать за выполненную проверку без несоответствий. Эти смысловые различия не задают новый перечень статусов. Отсутствующий документ может считаться отдельным нарушением только тогда, когда это следует из утверждённого правила комплектности.

Обеспечивай связь находки с проверяемым параметром и фактическими исходными документами. Состав и формат доказательств определяются документацией; заполняй их только реально полученными данными. Не создавай несуществующие ссылки, цитаты и значения уверенности. Для численных сравнений используй документированные единицы измерения, правила округления и допуски.

Управление параметрами и нормативной базой относится к роли администратора. Конкретные операции, порядок изменения и влияние изменений на уже выполняемые или завершённые проверки определяются документацией. Не меняй задним числом основания существующего результата; обеспечивай прослеживаемость внесённых изменений.

### Решение инспектора

Верификация относится к роли инспектора. Храни решение отдельно от автоматического вывода анализа и фиксируй его вместе с обоснованием. Перечень допустимых решений, их коды и правила изменения бери из документации; не ограничивай его самостоятельно придуманным набором. Для аудита фиксируй автора и серверное время. Автор определяется из проверенной авторизации, а не из произвольного поля запроса.

Не удаляй находки или историю только потому, что решение инспектора не совпало с автоматическим выводом. Если изменение решения предусмотрено документацией, сохраняй аудит. Правила переноса решений и повторной верификации после дозагрузки также определяются документацией; не применяй старое решение автоматически к изменившимся доказательствам.

### Финализация протокола

Финализация — серверно контролируемое действие, после которого дозагрузка в финализированную проверку недоступна. Состав фиксируемого протокола, его форма, условия финализации и разрешённые роли определяются документацией. Отключённая кнопка не заменяет серверную защиту.

Перед финализацией проверяй права и все документированные условия операции. Не добавляй собственные требования к числу решений, комплектности, исходам проверки и последовательности действий. Не выводи возможность или запрет финализации только из наличия несоответствий. Если существенные условия финализации ещё не определены, обозначай эту часть сценария как не реализованную по спецификации, а не разрешай действие по умолчанию.

Дозагрузка, изменение решений и финализация должны участвовать в согласованной защите от конкурентных изменений. Используй транзакции и блокировку либо проверяемую версию записи; простая последовательность «прочитать статус — затем записать» недостаточна. [S10]

Не изменяй незаметно уже финализированный протокол и данные, на которые он ссылается. Поздний worker и повторный запрос не должны изменить его содержание или создать дубликат. Порядок исправлений, пересмотра решений и повторных проверок бери из документации; не добавляй собственный сценарий повторного открытия.

## 15. HTTP API и интеграция с ИАИС «РиН»

Реализуй API по предоставленному контракту и отражай его в OpenAPI. Если контракт ещё не предоставлен, не создавай его предполагаемую версию в качестве действующей. Методы и адреса эндпоинтов, префиксы версий, HTTP-коды ответов, DTO, поля ошибок, пагинация, ограничения и авторизация должны соответствовать документации, а не примерам из похожих систем.

Подтверждён общий принцип: после загрузки документов система возвращает `process_id`, обработка выполняется асинхронно, статус доступен через эндпоинт мониторинга, а результаты получаются отдельным запросом по Pull-модели. Имена эндпоинтов и остальные детали обмена этим описанием не заданы.

Ответ о принятии операции возвращай только после её надёжной регистрации. Не выдавай пустой успешный результат за ещё не выполненный анализ. Наличие частичных и исторических результатов, условия их доступности и формат выдачи определяются документацией; не добавляй эти возможности без основания. Итоговые количества должны соответствовать данным и правилам выборки из контракта, а не только отображаемому фрагменту.

Подтверждённое внешнее поле `process_id` сохраняй без переименования. Во внутреннем коде допустим camelCase с явным преобразованием на границе. Не выдумывай остальные поля, коды ошибок и их HTTP-представление. Пользовательские сообщения не должны раскрывать внутренние данные и секреты.

Повторные запросы не должны создавать дубликаты операций и результатов. Конкретный механизм идемпотентности, область действия и срок хранения ключей бери из документации. Не добавляй предполагаемый обязательный заголовок или поле в публичный контракт. Если контракт предусматривает ключ, проверяй соответствие повторного содержимого исходной операции и обрабатывай конкурентные повторы согласованно.

UI и внешняя интеграция используют одни доменные правила и документированные проверки доступа, а не разные обходные реализации. Интеграцию «РиН» изолируй адаптером. Не выдумывай адреса, формат обмена, авторизацию, SLA и коды ошибок внешней системы. Пока спецификация интеграции отсутствует, не имитируй успешный обмен; допустима подготовка независимой технической инфраструктуры с явно обозначенной границей реализации. Недоступность внешней системы не должна уничтожать локальные документы и результаты.

## 16. Prisma и PostgreSQL

Схема Prisma и миграции фиксируют структуру БД, реализованную на основании подтверждённых требований, но не являются самостоятельным источником бизнес-правил. Не закрепляй в них выдуманные статусы, значения ролей и предметные сущности. Изменение схемы сопровождается миграцией, генерацией клиента и проверкой совместимости. Не редактируй уже применённые миграции; добавляй новые.

В production применяй подготовленные миграции через `prisma migrate deploy`. Не используй `db push`, `migrate dev` или reset как механизм обновления production. Миграции запускаются отдельным контролируемым шагом развёртывания, не одновременно каждым экземпляром API. [S11]

Обеспечивай инварианты ограничениями БД: внешними ключами, уникальностью и проверяемыми версиями. Добавляй индексы под реальные запросы процессов, документов, результатов и очереди outbox. Не используй небезопасную конкатенацию SQL; для raw-запросов требуется параметризация.

Транзакции должны быть короткими. Не выполняй внутри них анализ, загрузку в хранилище и сетевые обращения. Координация с хранилищем и RabbitMQ требует отдельных состояний и восстановления, а не предположения об общей транзакции.

Не выбирай все поля и связи без необходимости. Избегай N+1, неограниченных списков и неявного удаления связанных документов. Серверные даты храни согласованно в UTC; форматирование выполняй на границе интерфейса.

## 17. Безопасность и работа с ИИ

Реализуй разграничение доступа для трёх ролей из раздела 2. Проверяй права на backend при чтении статуса, результатов и файлов, дозагрузке, верификации, финализации, управлении параметрами и нормативной базой, доступе к логам и данным дообучения. Проверка должна учитывать конкретный ресурс и документированную область доступа. Знание `process_id` не даёт права доступа. Не считай CORS механизмом авторизации.

Используй единый серверный механизм проверки прав, а не разрозненные сравнения названий ролей. По умолчанию не предоставляй неподтверждённые права. Проверяй доступ независимо от того, доступна ли соответствующая кнопка в UI. Не добавляй обход авторизации для администратора, ML-инженера или тестовой интеграции.

Доступ ML-инженера к логам и данным дообучения не отменяет требований к защите документов и персональных данных. Объём доступных данных, возможность выгрузки и операции над ними определяются документацией; не предоставляй автоматически доступ к секретам, всем исходным документам или настройкам среды. Не включай пользовательские документы в данные дообучения без предусмотренного правилами проекта основания. Аудитируй значимые изменения параметров и нормативной базы, решения инспектора и операции с данными дообучения согласно документированным требованиям.

Секреты храни только на сервере. Переменные `VITE_*` попадают в клиентскую сборку и не должны содержать закрытые ключи или пароли. Для переменных окружения нужны проверка при старте и `.env.example` без настоящих секретов. [S12]

Загруженные документы, извлечённый текст и ответы модели — недоверенные данные. Инструкции внутри них не могут менять системные правила, права доступа или вызывать инструменты. Не исполняй макросы, скрипты и команды из документов. Изолируй обработку и ограничивай доступ к сети, ресурсам и файловой системе. [S13]

Вызывай анализатор через адаптер с явными входом и выходом. Проверяй ответ модели по схеме и сверяй ссылки на доказательства с реальными документами. Модель не может сама подтвердить нарушение от имени инспектора или финализировать протокол.

Передача документов внешнему провайдеру допускается только при явно выбранной конфигурации и разрешённом режиме обработки. Не подменяй недоступный анализ случайными находками или фиктивным успехом.

Не выводи необработанный HTML документов и модели. В логах не должно быть содержимого документов, токенов, полных персональных данных и секретных URL. Для диагностики используй безопасные технические метаданные и идентификаторы, предусмотренные реализованной моделью. Не добавляй ради логирования выдуманные поля в публичный контракт. Аудит значимых действий храни отдельно от технических логов.

## 18. Тестирование

Для сложного компонента, хука, функции и доменного сценария тесты обязательны. Сложность определяется ветвлениями, асинхронностью, состояниями и последствиями ошибки, а не числом строк. Исправление воспроизводимого дефекта сопровождай регрессионным тестом.

Основной runner — Vitest. Frontend-компоненты тестируй через React Testing Library и пользовательские действия; сеть изолируй согласованными mocks, например MSW. Backend-тесты запускай в Node-окружении. Для NestJS настрой совместимую обработку decorators и metadata; официальный вариант интеграции использует SWC. Проверяй не только чистые функции, но и создание Nest testing module. [S14]

Unit-тесты располагай рядом с кодом: `*.test.ts`, `*.test.tsx`; если backend уже использует `*.spec.ts`, сохраняй локальное соглашение. Интеграционные тесты можно хранить отдельно. Не вводи одновременно Jest и Vitest для одних задач без необходимости.

Тестируй предметные сценарии на основании подтверждённых требований и документированных контрактов. Отсутствие спецификации не компенсируй выдуманными статусами и ожидаемыми бизнес-ответами. По мере реализации обязательно покрывай следующие группы сценариев:

- Загрузка: категория, лимиты, дубликаты, частичный отказ, повтор запроса, дозагрузка до финализации и отказ после неё.
- Асинхронность: документированные условия запуска и остановки polling, поведение после дозагрузки, сетевые ошибки, повторная доставка, падение worker, запоздавший результат; безопасная обработка ответа вне поддерживаемого контракта без подстановки известного статуса.
- Предметная логика: комплектность, применимость параметров, недостаточные данные, техническая ошибка, доказательства, обоснование и аудит решения.
- Конкурентность: одновременные дозагрузка и финализация, изменение решения и финализация, повтор финализации, конфликт версий и идемпотентные повторы.
- Безопасность: отказ в доступе вне разрешённой области, защита файлов, некорректное сообщение очереди, опасный входной документ; разрешённые и запрещённые операции инспектора, администратора и ML-инженера по подтверждённой матрице, включая прямые API-вызовы в обход UI и отсутствие неявных прав администратора.

Проверки транзакций и ограничений выполняй на изолированном PostgreSQL, а не только на mocks Prisma. Поведение очереди проверяй интеграционно с RabbitMQ. Не используй production-базы, реальные документы пользователей и платные внешние вызовы в обычном тестовом прогоне.

Тесты должны быть детерминированными: управляй временем, случайностью и ответами сети; очищай QueryClient, stores, mocks и таймеры между тестами. Не полагайся на реальные задержки. Проверяй наблюдаемое поведение, не внутренние детали HeroUI и React.

Сборка и обычный запуск Vitest не заменяют отдельную проверку типов. Не снижай пороги покрытия и не отключай проверки ради прохождения CI. [S15]

## 19. TypeScript, ESLint, Prettier и Husky

Используй строгую типизацию. Не добавляй `any`, `@ts-ignore`, `@ts-nocheck` и принудительные приведения для обхода ошибок. Для недоверенных значений используй `unknown` и проверку. Исключения должны быть локальными и объяснёнными.

Имена React-компонентов и их файлов — PascalCase. Хуки начинаются с `use`. Каталоги и обычные модули — kebab-case; для backend сохраняй соглашения NestJS, например `processes.service.ts`. Не переименовывай существующий код массово ради косметической унификации.

Комментарии объясняют причины и ограничения, а не пересказывают код. Не оставляй мёртвый код, отладочные логи, неиспользуемые экспорты и бессрочные TODO. Не делай пустой `catch`, превращающий ошибку в успех.

Prettier отвечает за форматирование; ESLint — за ошибки и правила качества. Конфигурации не должны конфликтовать. Не отключай правила целиком ради одной строки.

Husky настраивается в корне. Pre-commit выполняет быстрые проверки затронутых файлов; для staged-файлов допустим `lint-staged`. Полный прогон типов, тестов и сборки выполняется в CI: локальные hooks не являются единственной защитой. [S16]

Не используй `--no-verify` и массовые исключения, чтобы скрыть неисправность. Сгенерированные файлы, артефакты сборки, coverage и пользовательские загрузки исключай из форматирования и коммита согласно назначению.

## 20. Docker, команды и готовность изменений

Docker-сборка должна учитывать корневой lock-файл и workspace-зависимости. Используй многоэтапные образы, воспроизводимую установку и закреплённые версии базовых образов. Не включай секреты, локальные загрузки и лишние dev-зависимости в runtime.

API и worker должны иметь отдельные команды запуска. PostgreSQL, RabbitMQ и файловое хранилище требуют долговечного хранения. Не считай порядок `depends_on` доказательством готовности сервисов: нужны healthchecks и обработка переподключения.

Предусмотри корректное завершение HTTP-сервера и worker, закрытие соединений и восстановление незавершённых заданий. Frontend в production отдаётся как сборка, а не Vite dev server; настрой fallback для маршрутов SPA без перехвата API-запросов.

Различай настройки времени сборки frontend и runtime-конфигурацию контейнера. Изменение окружения уже собранного контейнера не меняет автоматически значения `import.meta.env` в JavaScript. [S12]

В новом репозитории организуй единые корневые команды:

```text
npm run dev             # Запуск frontend и backend для разработки
npm run build           # Сборка обоих workspaces
npm run eslint          # ESLint
npm run prettier        # Форматирование
npm run lint            # Форматирование + ESLint
npm run typecheck       # Проверка TypeScript
npm run test            # Однократный прогон Vitest
npm run test:watch      # Режим наблюдения
npm run test:coverage   # Тесты с покрытием
```

Это целевые имена scripts, а не утверждение об их наличии. В существующем проекте сначала проверь `package.json`. Не запускай несуществующие команды и не добавляй `--if-present`, чтобы скрыть отсутствие обязательной проверки.

Изменение готово, когда реализован целевой сценарий и его ошибки, сохранены границы модулей, обновлены необходимые контракты и миграции, добавлены тесты сложной логики, пройдены доступные lint/format/typecheck/test/build-проверки и актуализированы инструкции запуска. При затронутой инфраструктуре дополнительно проверь Docker-сборку и интеграционные сценарии.

Перед завершением проверь, что изменения не вводят неутверждённые статусы, бизнес-данные, контракты или полномочия ролей. Не заявляй полную реализацию 132 проверок, готовность интеграции «РиН» или безопасность финализации без соответствующего кода и проверок. Непроверенные части и ограничения из-за отсутствующей документации перечисляй явно.
