# Контракты семи changes

Версия проекта контрактов: 17.09.2026. Это проект технических границ, а не утверждение о существующем API. Нормативное поведение задано в specs каждого change и в [PDF](../docs/requirements/SOURCES.md). При реализации схемы закрепляются в OpenAPI/JSON Schema и проверяются на границах Node/Python/frontend. Имена технических полей ниже не вводят новые бизнес-статусы или полномочия ролей.

Дополнение 26.09.2026: исходные границы семи частей ниже сохраняются. Все 24 активных changes, дальнейшие владельцы и зависимости этапов перечислены в [RELEASE_PLAN.md](RELEASE_PLAN.md) и [release-plan.json](release-plan.json). Контракты новых модулей описаны в их `design.md`/specs; их появление не означает автоматического согласования новых ролей, нормативов или внешних API. Начальные и завершающие этапы различаются, поэтому полный выпуск MAT/ACC/OFF не должен блокировать подготовку их ранних контрактов.

## Владельцы данных

### Решение владельца от 17.09.2026 для ING

Политика подтверждена владельцем в задаче реализации. Инспектор может создавать
объекты; создание транзакционно выдаёт ему явное назначение ObjectAccess.
Чтение объекта, приём, повтор приёма и выдача оригинала доступны инспектору
только при действующем назначении. Администратор управляет назначениями через
служебную команду с аудитом; это не даёт ему доступа к документам. ML-инженер
и пользователь с role=null не имеют прав на этот сценарий. Авторство отдельно
от назначения и после отзыва не позволяет читать объект.

Необходимая для ING часть общей зависимости C01 реализуется в той же ветке:
Process/Run/Job/Outbox, исходный InputManifest, доставка RabbitMQ и аудит.
Остальные обязательства C01, PAR и C24 этим решением не закрываются.

Наличие контейнера RabbitMQ и работающей авторизации не закрывает C01. Первые предметные миграции Object/ObjectAccess и API/UI объектов реализует ING, см. D0 его design и OBJ-01–03 его spec. Затем общие Process/Run из C01 и File из ING ссылаются на этот же Object; новые справочники объектов в других changes не создаются. C01 предоставляет политику полномочий, безопасное первоначальное назначение ролей и общие фоновые сущности. Полномочия не выводятся из названий ролей. Зависимость от C01 не требует ждать завершения всей платформы, чтобы начать объекты; приёмка загрузки всё равно использует реальные очередь/БД/аудит.

Базовая связь: Object ← ObjectAccess → User; Object ← File; Object ← Process ← Run. File.object_id обязателен, process_id загрузки должен относиться к тому же Object. Без object_id или с несовместимым процессом приём отклоняется; загрузка не создаёт объект автоматически. Общая политика действий и назначение на конкретный объект проверяются совместно.

## Снимки и версии

1. На приёме сохраняется `InputManifest`: `schema_version`, `object_id`, `process_id`, `run_id`, отсортированные `file_id/file_hash`, известные версии правил/модели/набора данных/ожидаемого состава и решений. Канонический JSON даёт `input_manifest_hash`; поля, ещё неизвестные до OCR, в него не дописываются.
2. PAR выдаёт артефакты с версиями parser/OCR/renderer/config и идентификатором исходного manifest. ID разрешает части, реквизиты и применимые редакции. После этого INC фиксирует `ResolvedInputSnapshot`: ссылки на исходный manifest и использованные артефакты, выбранные документы/части/редакции, цепочки замен, решения и версии разрешения источников. Канонический JSON даёт `resolved_input_hash`.
3. EXT/GEO могут готовить промежуточные результаты по версии артефакта. Публикация окончательной доказательной группы и передача на сравнение требуют согласованной пары hash и полных версий. Неизвестная версия возвращается явно, а не подставляется из текущей конфигурации.
4. Каждая содержательная дозагрузка, уточнение или подтверждение нового перечня создаёт новый Run. Кеш по hash хранит только контекстно независимые артефакты; перенос результата/решения требует совпадения всех оснований. Старый протокол сохраняет собственную пару hash.

Ожидаемый состав — самостоятельный перечень требований к объекту; ни один из двух снимков не подменяет его.

## Форматы обмена

Канонический JSON начального InputManifest сериализуется в UTF-8 без пробелов:
ключи каждого объекта сортируются лексикографически, порядок массивов сохраняется
(files предварительно сортируется по file_id), неизвестные версии представлены null.
Нефинитные числа и значения вне JSON запрещены. Hash воспроизводится после чтения
из PostgreSQL JSONB, который не сохраняет исходный порядок ключей.

| Контракт                    | Обязательное содержание                                                                                                         | Ошибка / условие отказа                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Принятие файла              | object/process/run, file_id, server SHA-256, размер, формат, автор/время, исход приёма                                          | Чужой объект, лимит, опасный/повреждённый файл, конфликт повторного ключа |
| Locator                     | file_id/hash, artifact/version, физическая страница; лист отдельно; bbox/polygon [0;1], transform; structural path для DOCX/XML | Координаты не соответствуют оригиналу или отсутствует версия отображения  |
| Идентификация поля          | raw/normalized, кандидаты, locator, метод/версия, confidence при наличии, причина конфликта/отсутствия                          | Неоднозначность не превращается в принятую редакцию                       |
| Extraction / GeometryResult | тип/значение/единица/область, локаторы и качество, версии; геометрия добавляет опору/калибровку                                 | Неподдержанный план, неизвестный масштаб или недостаточные доказательства |
| EvidenceGroup               | object/rule/version/scope, роли expected/actual, связанные редакции/утверждение, пара hash                                      | Нельзя публиковать группу с неподтверждённым источником как сравнение     |
| CompletenessResult          | версия перечня/правил/входов, исполненные требования и причины, выбранные источники, nullable-агрегаты                          | Неизвестный состав не даёт FULL; missing не становится finding            |
| Инкрементальное задание     | старый/новый Run, затронутые группы и причины, версии, fencing                                                                  | Неполные основания запрещают перенос решения; поздняя запись отклоняется  |

Взаимодействие с Python проходит через проверяемый внутренний контракт Node. Python не меняет предметные таблицы напрямую. Большие артефакты передаются разрешёнными storage handles; полные документы не помещаются в события и логи.

## HTTP и интерфейс

Общие поля ответа: версия схемы, контекст объекта/процесса/Run; ошибки имеют машиночитаемый код и понятную причину без содержимого чужого объекта. Чтение текущего состояния и исторического результата явно различается. Пагинация не меняет серверные общие счётчики.

| Операция                             | Предлагаемая поверхность                                                                                                                | Владелец                                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Создание и выбор объекта             | `POST /api/v1/objects`, `GET /api/v1/objects`, `GET /api/v1/objects/{object_id}`; только разрешённые действия и доступные объекты       | ING                                      |
| Приём                                | `POST /api/v1/documents/upload` — object_id, optional process_id, client_upload_id, files с client_file_id/original_name/content_base64 | ING                                      |
| Восстановление приёма                | Идентичный повтор upload с тем же ключом; сохранённый ответ содержит process_id/run_id и индивидуальные исходы                          | ING                                      |
| Оригинал / производное представление | Авторизованный endpoint файлов; оригинал и производный artifact имеют разные идентификаторы                                             | ING / PAR                                |
| Мониторинг                           | `GET /api/v1/processes/{process_id}` — business status, технический исход/прогресс, текущий Run и разрешённые действия                  | Контракт C01/INC; PAR наполняет прогресс |
| Реестр / результат                   | `GET /api/v1/processes/{process_id}/documents` и `/results`, явно заданный Run и версии результата                                      | ID / EXT / COM через общий процесс       |
| Уточнения                            | Versioned mutation карточки с основанием; `409` при несовместимой версии                                                                | ID                                       |
| Ожидаемый состав                     | Versioned чтение/подтверждение состава; неизвестная полнота — nullable с причиной                                                       | COM                                      |

Точные пути новых операций, помимо upload и согласованных общих маршрутов, фиксируются в OpenAPI при первой задаче владельца; эта таблица не требует нескольких независимых контроллеров для одного URL. P1 согласует общую схему, P2 использует существующий API-клиент. `/api/auth/*` сохраняется.

Upload: `202` после сохранения оригиналов и транзакционной регистрации; ошибки `400/401/403/409/413/422` описываются примерами. Лимиты — 50 000 000 байт на файл и 200 000 000 байт суммы всех переданных файлов. JSON/base64 декодируется до общего body-parser. Дополнительно ограничиваются wire-size, число файлов/метаданные и временная область; конкретные технические потолки проверяются на допустимом предельном пакете. Превышение пакета отменяет приём целиком. Повтор ключа scoped по пользователю/объекту/client_upload_id проверяет fingerprint содержимого и значимых метаданных; optional process_id включён во fingerprint, а не меняет scope после первого ответа.

## События и общая очередь

Уточнение ING от 18.09.2026, подтверждённое пользователем: одинаковый SHA-256 в одном object_id не создаёт повторный File/Run/Job даже с новым ключом, именем или другим назначенным пользователем. Результат файла — `accepted=false`, `error=duplicate_file`, `existing_file_id`. Смешанный пакет с новыми файлами получает `202`; при отсутствии новых файлов возвращается `422`, process_id/run_id=null. Receipt и доступ проверяются как обычно. Аудит считает duplicates отдельно от rejected. В другом объекте те же байты допускаются. Уникальный реестр object_file_contents заполняется триггером File и сохраняет ссылки на самые ранние исторические оригиналы, не удаляя ранее созданные дубли.

Envelope: `schema_version`, `event_id`, `event_type`, `occurred_at`, `object_id`, `process_id`, `run_id`, применимые `job_id/file_id`, версии входов, correlation id и краткая безопасная причина. Идемпотентный ключ потребителя включает event_id и тип эффекта. C01 обеспечивает outbox/delivery/ack после commit и fencing; владельцы capability определяют семантику своих событий.

| Событие (рабочее имя)                       | Производитель    | Потребитель                                                           |
| ------------------------------------------- | ---------------- | --------------------------------------------------------------------- |
| `documents.accepted`                        | ING              | PAR через C01                                                         |
| `documents.admission.rejected`              | ING              | C23 через C01; только коды причин и число отказов, без duplicate_file |
| `parsing.finished` / `parsing.exhausted`    | PAR              | ID / C23; INC обновляет технический исход                             |
| `document.clarified`                        | ID               | INC                                                                   |
| `expected-composition.confirmed`            | COM              | INC                                                                   |
| `extraction.finished` / `geometry.finished` | EXT / GEO        | Планировщик INC / COM                                                 |
| `input.resolved`                            | INC              | Извлечение / сравнение после проверки версии                          |
| `external-documents.after-finalization`     | Входной порт INC | C23; протокол не изменяется                                           |
| `file.integrity-failed`                     | ING              | C23 и блокировка достоверного использования                           |

Email/Telegram требует реального адаптера C23, ограниченных повторов доставки и наблюдаемой ошибки канала. Долговечное событие в функциональном change не означает, что доставка уже реализована.

## Разрешения процесса и решение по восстановлению

| process_status из PDF | Дозагрузка | Верификация        |
| --------------------- | ---------- | ------------------ |
| PENDING               | да         | нет                |
| PARSING               | нет        | нет                |
| READY                 | да         | да                 |
| VERIFYING             | да         | да, до финализации |
| COMPLETED             | да         | нет                |
| FINALIZED             | нет        | нет                |

Сервер проверяет разрешение вместе с изменением версии. Это матрица двух действий, а не разрешение любых прочих операций. READY выставляет владелец протокола только после его реального сохранения. Финализация использует единый transaction/version port с загрузкой, уточнением и публикацией; её предметные условия определяет C12.

**LC-08 — частично определено для PAR владельцем 18.09.2026.** При обработке текущего Run процесс имеет `PARSING`; после сохранения исходов всех его файлов (включая исчерпание попыток) возвращается в `PENDING`. Технические результаты файлов хранятся отдельно и остаются видимыми. `READY` по-прежнему требует сохранённого протокола. Повтор использует существующий оригинал и новый ограниченный цикл попыток; улучшенный скан принимается как новый неизменяемый оригинал и новый Run по правилам ING. Предыдущий источник не перезаписывается; предметное разрешение замен принадлежит ID/INC. Детальный технический контракт PAR: [implementation-contract.md](changes/add-document-parsing/implementation-contract.md).

При приёме новых файлов в разрешённом для загрузки состоянии ING атомарно создаёт текущий Run и переводит процесс в `PENDING`: статус предыдущего Run не переносится на новые входные данные. Затем PAR начинает обработку нового Run.

Остальная часть LC-08 остаётся открытой до реализации соответствующей части INC. PDF не задаёт полную таблицу переходов. Владелец процесса и предметный владелец должны зафиксировать:

| Событие                                          | Что требуется определить и проверить                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Исчерпаны попытки OCR                            | Технический исход Run, допустимое действие восстановления, владелец перехода; запрет ложного READY и тупика PARSING  |
| Обработана только часть файлов                   | Условия продолжения, показ неполного результата и право исправления; пропуски не считаются отрицательными проверками |
| Нужна редакция / утверждение                     | Разрешение уточнения, версия решения и способ продолжить тот же процесс новым Run                                    |
| Запрошен повтор / замена повреждённого источника | Различение технического retry и новой загрузки; соблюдение матрицы PDF                                               |
| Настоящий протокол сохранён                      | Предусловия READY с точной парой hash, обработка устаревшего результата                                              |

Подтверждённый переход PAR включён в его версионированный контракт и тесты. Он не определяет переходы последующих стадий, `COMPLETED` или новый публичный `FAILED`. Остальные решения включаются в контракт и табличные тесты INC; формальная готовность OpenSpec artifacts не снимает открытые обязательства.

## Параллельная работа и завершение

### Реализованное дополнение MAT/CMP от 27.09.2026

`RuleSetRelease` хранит неизменяемый состав частичной или полной партии: каталог, точные RuleVersion, паспорта/отчёты и версии исполнителей. Выбор партии меняется атомарно с аудитом; Run закрепляет её до начала вычисления. Утверждение отдельного правила не изменяет выполняющийся Run. Исторический `legacy_capture` сохраняет техническое происхождение без нового предметного допуска; у старых Run без ссылки состав не выдумывается. Контракт/API: [RULE_SET_RELEASE.md](../docs/matrix/RULE_SET_RELEASE.md).

`decimal-units-v1` дополняет существующий comparison и Extraction.numerical точными десятичными значениями, источником единицы, явной политикой процентов/нуля/округления и трассой. Старые скалярные ответы читаются без подстановки этих оснований. Категории используют подтверждённую версионированную карту порядка. Новый numeric-draft без политики и основания допуска не проходит MAT gate. Контракт: [NUMERICAL_POLICY.md](../docs/matrix/NUMERICAL_POLICY.md). Наличие оператора не означает приёмку строк матрицы; см. [срез реализации](../docs/matrix/IMPLEMENTATION_2026-09-27.md).

### Зависимости владельцев

ING → PAR → ID → EXT; PAR → GEO; ID + EXT + GEO → COM → INC. GEO и EXT используют общую схему, но не требуют второй реализации алгоритма друг друга. После фиксации контрактов UI, алгоритмы и владельцы правил могут готовить свои части одновременно.

Границу завершения каждого change задаёт его `design.md` и `tasks.md`. Контрактные fixtures допустимы для разработки, но реальное хранилище/очередь/БД/парсеры проверяются там, где соответствующая задача их реализует. Общее прохождение с реальными C06/C10/C12/C20, качеством, нагрузкой и восстановлением сохраняется в [SHARED_BACKLOG.md](SHARED_BACKLOG.md); эти обязательства входят в тот же двухнедельный релиз.
