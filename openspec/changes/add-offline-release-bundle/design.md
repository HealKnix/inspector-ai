## Context

Текущий Compose запускает локальный parser с read-only моделями; download_models.py отдельно скачивает веса. При этом OCR использует CPU, опциональный LLM по умолчанию указывает внешний URL, а правила существуют преимущественно в БД стенда. Наличие Dockerfile не доказывает холодный офлайн-старт.

## Goals / Non-Goals

**Goals:** проверяемый комплект для Linux/Docker/NVIDIA Container Toolkit, работающий без внешних запросов; одинаковые версии правил и моделей после чистой установки.

**Non-Goals:** включение рабочих документов/секретов в образ; обещание эксклюзивной GPU; незаявленная смена Node/Bun; runtime-установка зависимостей.

## Decisions

1. **Подготовка и запуск разделены.** Release job в разрешённой сетевой среде собирает образы и пакеты моделей/сигнатур. Комплект содержит digest каждого образа, версии/лицензии/хеши весов, конфигурацию, миграции, MAT ruleset и инструкции. Чистая установка загружает готовые образы; офлайн-пересборка является отдельным режимом и требует всех базовых образов/зависимостей.
2. **Один bootstrap без копирования рабочей БД.** Создать новую БД, применить миграции, импортировать утверждённые справочники и portable ruleset MAT, настроить разрешённую начальную учётную запись. Повтор bootstrap идемпотентен. Сопоставить количество/версии/хеш правил с release manifest; не ограничиваться наличием 132 строк каталога.
3. **Сетевой запрет проверяется технически.** В release-профиле внешние URL отвергаются до запуска обработки. Локальный модельный сервер подключается только при выбранной лицензированной модели; disabled-модуль не маскируется как работающий. Проверяется сетевой журнал при холодном запуске, парсинге, поиске, обучении и экспорте.
4. **GPU и квоты задаются профилем.** H100 предоставляется контейнеру хостом; драйвер внутрь образа не включается. PAR владеет совместимым OCR/CUDA и выбором device, OFF — подключением/проверкой профиля и общим бюджетом CPU/RAM/VRAM. CPU fallback не условие хакатонного допуска; отсутствие нужного GPU даёт явную диагностику.
5. **Антивирус остаётся обязательным.** Поставить разрешённый снимок сигнатур, документировать дату и обновление при следующем release. Отсутствие/непригодность сигнатур не обходится отключением ClamAV. Правило актуальности согласуется с оператором среды.

## Этапы и зависимости

1. Инвентаризация текущих runtime-входов, лицензий и ресурсов; первый технический bundle существующего ядра.
2. Packaging образов/весов/правил и проверка manifest.
3. Bootstrap, запрет egress, GPU-профиль и диагностика.
4. Холодная установка на пустые volumes и полный smoke; повтор установки/восстановления.
5. Выпуск итогового комплекта всех заявленных функций, инструкция и передача через установленный канал.

Ранняя упаковка не ждёт всех features. OFF-final требует выбранные версии PAR/MAT/ML/HYP и остальных включённых capabilities; ACC проверяет тот же digest. Не создаётся цикл «весь релиз нужен, чтобы начать packaging».

## Risks / Trade-offs

- [Веса доступны, лицензия непригодна] → фиксировать лицензии до включения в комплект.
- [Зависимость скрыта в кеше] → чистые volumes и блокированный DNS/egress при проверке.
- [На новой машине только три seed-правила] → сравнить фактический ruleset manifest после bootstrap.
- [GPU занята другой командой] → фиксировать квоту/нагрузку в замерах и ограничивать конкуренцию, не обещать скорость по названию GPU.

## Migration Plan

Новый release-профиль не меняет dev-среду. Испытания выполняются на выделенном стенде/volumes. Обновление рабочей установки требует backup и проверки совместимости; rollback использует сохранённые образы/конфигурацию и согласованное восстановление из HARD.
