## Context

См. proposal.md. `backend/src/modules/verification/protocol-builder.ts` хранит внутреннее представление counts/findings; `verification.service.ts` отдельно хранит решения и снимки. `frontend/src/pages/protocols/*` и `store/protocols.ts` используют demo. Приложение 2 прочитано: содержит паспорт объекта, загрузку, статистику, непроверенные параметры, нарушения, гипотезы и резолютивную часть; его автоматические санкции/согласие ИИ не соответствуют итоговому PDF и не переносятся как правила.

## Goals / Non-Goals

Цель — единый экспортный снимок, независимо проверяемый по источникам и доступный во всех форматах. Владелец локальной финализации остаётся VER, доставки — обмен, обучения — GOLD/ML. Экспорт не проводит повторный анализ и не принимает решения за инспектора.

## Decisions

1. Расширить projection существующего Protocol, а не создавать второй источник решений. Проекция закрепляет object/process/run/protocol/version, input manifest и hashes, версии матрицы/rules/model/dataset, snapshot completeness, finding/evidence/decision. Неизвестные сведения явно отсутствуют с причиной; нельзя подставлять текущую модель или редакцию вместо исторической. Альтернатива собирать PDF из live-таблиц отклонена из-за смешения версий.
2. Сначала составить таблицу соответствия «поле PDF/совместимого образца → поле снимка → источник → поведение при отсутствии». Сохранить паспорт/даты/версию/статус, статус загрузки, сценарий и сводку, но разделить пять таблиц по §9.2. Риск означает очередь проверки. Резолютивная часть содержит лишь сохранённое решение уполномоченного лица; шаблонные предписания не генерируются.
3. JSON — каноническая экспортная модель, PDF/DOCX/XML — её представления с версией схемы/шаблона и хешем. Для незавершённого протокола явно показывать предварительность; выдача не финализирует его. Политика доступа использует существующий ObjectAccess; новый расширенный доступ требует отдельного решения.
4. Формирование тяжёлых файлов вынести в существующий worker/outbox при подтверждённой необходимости; повтор использует ключ protocol/version/format/template. Оригиналы и экспорт закрыты. Поздний render не заменяет артефакт другой версии. Проверять доступ и перед созданием, и перед выдачей.
5. H: реестр API, JSON/PDF и schema-compatible выход оценщика после подтверждения версии submission_schema. H также включает реальные SUSPICION и model/dataset manifest обязательного заявленного контура HYP/GOLD/ML: контрактная fixture проверяет форму проекции, а отдельный offline-прогон подтверждает реальный путь гипотезы, экспертного feedback и закреплённых версий до экспорта. Интеграция H не ждёт дополнительных форматов F; неполные исторические сведения обозначаются явно, но это не разрешает закрыть обязательную H-функцию без поставщика. F: DOCX/XML, расширение поставщиков полного ТЗ и полная визуальная сверка образца. Medium-форматы не объявляются обязательным условием offline-проверки High; §11 JSON/PDF всё равно измеряется в общей приёмке.

## Risks / Trade-offs

- Неполный model/dataset manifest → согласовать интерфейс с владельцами и не выдумывать исторические значения.
- Статусы или проценты из старого образца искажают смысл → тестировать отдельные категории, знаменатели и отсутствие автоматических санкций.
- Большие таблицы/длинные реквизиты → визуальная проверка всех страниц PDF/DOCX, повтор заголовков, ссылки на evidence и отсутствие обрезки.
- Адаптер оценщика теряет отрицательные/неприменимые случаи → отдельные контрактные fixtures; внутренняя модель и метки инспектора не изменяются ради внешнего формата.

## Migration Plan

Добавить версионированную схему проекции и, если нужно, аддитивные поля/артефакты; старые протоколы читать без пересчёта. Подключить страницы API, затем форматы по фазам. Откат отключает новый renderer/выдачу, не удаляя версии, исходники и уже выданные артефакты. Приёмка с VER/INC проверяет экспорт старой версии после дозагрузки и после перезапуска без сети.
