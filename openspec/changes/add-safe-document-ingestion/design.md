## Context

См. [proposal.md](proposal.md) для мотивации и [spec](specs/document-ingestion/spec.md) для поведения. В backend/prisma/schema.prisma есть только User и AuthSession; RolesGuard проверяет роли, но не назначения на объекты. Frontend содержит auth-маршруты и /app без реестра объектов. Поэтому базовая предметная структура и путь её создания входят в ING. Наличие контейнера RabbitMQ не доказывает готовность C01. Изменения сохраняют /api/auth/*, текущий React-клиент и Bun workspaces. Источники — [PDF и приложения](../../../docs/requirements/SOURCES.md).

До завершения: других функциональных changes нет; общие зависимости C01 в [SHARED_BACKLOG.md](../../SHARED_BACKLOG.md). Интерфейсы можно разрабатывать по согласованным контрактам до готовности зависимостей, но интеграцию закрывают на реальных компонентах.

## Goals / Non-Goals

**Goals:** реализовать связанный путь создания/выбора объекта и приёма документов. Object, ObjectAccess, File и UploadReceipt принадлежат ING; Process/Run/Job/Outbox, общая политика полномочий и аудит — C01. ING создаёт начальный InputManifest по общему контракту. ID использует эти Object/File и не создаёт вторые таблицы. Производные файлы регистрируют их производители через storage-порт.

**Non-Goals:** полный паспорт и бизнес-статусы объекта, удаление/перенос документов между объектами, интеграция РиН; OCR, редакции, комплектность и протокол находятся в соседних changes.

## Decisions

[Общий контракт](../../CONTRACTS.md) фиксирует владельцев, поля, версии и порядок интеграции. Технические решения ниже — проект реализации; подтверждённые роли и бизнес-статусы берутся из PDF.

### D0. Объекты и назначения перед первой загрузкой

Политика согласована пользователем 17.09.2026: инспектор создаёт объект с явным
исходным назначением себе; чтение/загрузка требуют назначения. Администратор
управляет назначениями служебной командой с аудитом без доступа к документам.
ML-инженер и role=null исключены. Необходимая часть C01 включена в эту ветку
по прямому разрешению пользователя; подробности — в CONTRACTS.md и evidence.md.

Технический минимум схемы, предлагаемый для реализации в ING:

| Сущность                                            | Поля и ограничения                                                                                      | Назначение                                                                                      |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Object (Prisma ConstructionObject, таблица objects) | Серверный UUID id, обязательный name, created_by → User, created_at/updated_at                          | Устойчивая идентичность объекта; название не используется как уникальный ключ                   |
| ObjectAccess (таблица object_access)                | object_id → Object, user_id → User, granted_by → User, created_at; уникальная пара (object_id, user_id) | Явное назначение на объект, проверяемое вместе с правом действия; новых бизнес-ролей не создаёт |
| File                                                | Обязательный object_id → Object плюс существующий план неизменяемого оригинала                          | Каждый факт принятия относится к одному объекту                                                 |
| Process/Run                                         | Process.object_id → Object; Run → Process, File/manifest согласованы с этой принадлежностью             | Общие модели C01 используют тот же Object; отдельного справочника объектов в C01 нет            |

Автор объекта — атрибут аудита, не автоматическое назначение полномочий. Создание и исходные назначения выполняются транзакционно по согласованной политике C01; права на создание и выдачу/отзыв доступа не выводятся из названия роли. ING предоставляет прикладной сервис выдачи/отзыва назначений с проверкой полномочий и аудитом. Общая административная панель управления пользователями не входит в этот change. Политика определяет, кто получает исходное назначение; её согласование остаётся явной задачей до открытия API. Это существующая зависимость C01, а не повод подставлять ADMINISTRATOR как универсальное разрешение.

API этого change: POST /api/v1/objects, GET /api/v1/objects и GET /api/v1/objects/{object_id}. Создание принимает название, сервер назначает идентификатор и автора; список с пагинацией отфильтрован по доступу. Тело запроса не позволяет произвольно выдать себе роль или назначение. Неизвестный и недоступный объект обрабатываются без раскрытия чужих данных. Точные схемы/ошибки фиксируются в OpenAPI вместе с upload до реализации.

UI расширяет существующий /app: список и пустое состояние, действие создания при разрешении, карточка выбранного объекта и загрузка в её контексте. Deep link содержит object_id; backend повторно проверяет его. Ручной ввод UUID и seed одного фиктивного объекта не являются приёмкой этого сценария.

Ссылочная целостность обеспечивается FK; сервер до публикации оригинала проверяет доступ и совпадение объекта с process_id, а в транзакции принятия повторно проверяет изменяемые разрешения/версию. Если object_id дублируется в связанных таблицах, ограничения БД исключают несовместимую пару process_id/object_id. Ссылки на объект не используют каскадное удаление принятых документов; API удаления и переноса отсутствуют. Одинаковый hash в двух объектах может переиспользовать физический blob, но не одну запись назначения/приёма File.

Основание и альтернатива: создание объектов в отдельном общем backlog оставляло первый пользовательский сценарий без точки входа. Включение Object/ObjectAccess в ING даёт проверяемый путь «создать объект → выбрать → загрузить». Полный паспорт или отдельный восьмой change для этого минимума не требуются.

### D1

Сохранить /api/auth/*; POST /api/v1/documents/upload принимает object_id, optional process_id, client_upload_id, client_file_id/original_name/content_base64. 202 возвращается после сохранения оригиналов и транзакционной регистрации; 400/401/403/409/413/422 описываются OpenAPI.

Основание и рассмотренная альтернатива: Отдельный versioned API не ломает существующую авторизацию; ответ до commit создавал бы ложное принятие.

### D2

1 МБ = 1 000 000 байт. Сумма 200 МБ включает все отправленные файлы. Превышение пакета отменяет весь приём; индивидуальные ошибки допускают приём остальных. Если допустимых файлов нет, process_id успеха не создаётся.

Основание и рассмотренная альтернатива: Единая десятичная граница устраняет разные трактовки MB. Частичный приём при превышении пакета нарушил бы атомарный отказ DI-03.

### D3

Потоковый JSON/base64-декодер должен сработать до общего body-parser. Ограничить wire-size, метаданные и временную область; согласовать Nginx и upload-timeout клиента. Обычные auth/polling-запросы сохраняют короткие лимиты.

Основание и рассмотренная альтернатива: Обычный JSON body-parser и синхронный base64 целого пакета создают несколько копий 200 МБ. Multipart проще, но не принят как замена JSON-контракту PDF.

### D4

Антивирус выполняется до постоянного хранения и парсинга; недоступность сканера закрывает допуск. Имена не являются путями, DOCX/XML не разрешают внешние сущности и код.

Уточнение по исправлению дефекта, подтверждённому пользователем 17.09.2026:
код qpdf 3 означает успешный разбор с предупреждениями и не является причиной
`unsafe_format`. В обоих проходах (`--check` и `--json`) применяется
`--warning-exit-0`; ошибки чтения, timeout и ограничения ресурсов сохраняют отказ.
После разбора обязательно проверяются страницы и запрещённое активное содержимое.
Оригинальный PDF не нормализуется и не перезаписывается.

Основание и рассмотренная альтернатива: Немедленная публикация до сканера допускает опасный файл к потребителям. Временный карантин изолирует этот интервал.

### D5

Область ключа повтора: пользователь + объект + client_upload_id; process_id входит в fingerprint запроса как optional вход, а не создаёт новую область после первого ответа. Fingerprint включает содержимое и значимые метаданные, а порядок файлов канонизируется по client_file_id. Повтор возвращает первоначальный ответ даже после смены состояния процесса; новая операция снова проходит матрицу разрешений.

Основание и рассмотренная альтернатива: Ключ с созданным process_id менял бы область между первым запросом и повтором, порождая дубликат. Проверка доступа остаётся обязательной и при повторе.

Уточнение D5 по подтверждению пользователя 18.09.2026: новый ключ запроса не разрешает повторное принятие тех же байтов в объект. `object_file_contents` хранит уникальную пару object_id/SHA-256 и FK на первоначальный File с теми же object_id/hash. Миграция выбирает самый ранний File по created_at/id, сохраняя исторические дубли. INSERT-триггер File регистрирует hash атомарно; уникальность действует и при прямой записи в БД. Ссылки неизменяемы. Поиск выполняется после проверки доступа, затем повторяется под блокировкой объекта в короткой транзакции принятия. Внутри пакета сохраняется один оригинал на hash. Известные дубли не публикуются заново; неподтверждённый blob проигравшего конкурентного запроса удаляется после достоверного commit. Неопределённый результат commit обрабатывает прежний сборщик сирот.

Ответ дубликата: accepted=false, error=duplicate_file, existing_file_id, сообщение. `202` означает наличие новых принятых файлов; `422` означает отсутствие новых файлов, включая пакет из одних дублей. Process/Run остаются null без новых входов. Аудит отдельно считает accepted/duplicates/rejected; дубли не являются событием небезопасного отказа. UI показывает нейтральное сообщение и скачивание существующего оригинала через защищённый endpoint. Повреждённый оригинал остаётся заблокированным, повтор не подменяет историю и сообщает о восстановлении.

### D6

Storage и PostgreSQL не имеют общей транзакции: publish оригинала → транзакция принятого File/Run/InputManifest/Outbox; сборщик проверяет отсутствие ссылок перед очисткой осиротевшего оригинала. Исходный SHA-256 не меняется.

Основание и рассмотренная альтернатива: Транзакция БД не откатывает storage. Компенсационная очистка допускается только для неподтверждённых объектов, чтобы не потерять уже принятый оригинал.

## Risks / Trade-offs

- Память и сетевые таймауты JSON/base64 → потоковый декодер до body-parser, отдельные лимиты и измерение через реальный proxy.
- Нет общей транзакции storage/БД → outbox, идемпотентное принятие и безопасная уборка сирот.
- Недоступна общая зависимость → контрактные проверки допускают подготовку, но не закрывают задачи реальной интеграции.

## Migration Plan

1. Согласовать политику действий с C01 и первым шагом ING добавить Object/ObjectAccess. Затем согласовать FK общих Process/Run C01 к этому Object и обязательный File.object_id в ING. Эти миграции упорядочиваются до первого upload; не нужно ждать завершения всего C01, чтобы начать таблицы и UI объектов. Существующие User/AuthSession не пересоздаются.
2. Поставить аддитивные миграции и ограниченно включить capability в разрешённой тестовой среде. Сохранить текущую авторизацию и прежние оригиналы.
3. Выполнить компонентные проверки из tasks.md на реальных зависимостях. Указать команды, версии, корпус и ссылки на отчёты в evidence.md, создаваемом при реализации.
4. При откате остановить новые операции/потребителей capability и вернуть совместимую версию приложения; не удалять исходники, аудит, принятые jobs и историю снимков. Незавершённые jobs сохраняются до совместимого возобновления.

## Acceptance boundary

Начать с пустой предметной БД при действующей авторизации и согласованных назначениях: создать объект через API/UI, выбрать его, загрузить файл и после перезагрузки увидеть связь с тем же объектом. На реальных storage/API/БД/очереди проверить FK и изоляцию второго объекта, несовместимый process_id, скачивание с тем же hash, восстановление ответа и индивидуальные отказы. Ручная вставка объекта в БД не заменяет этот сценарий. OCR-потребитель для этой приёмки не нужен; факт очереди проверяется без фиктивного результата анализа.

Готовность design/specs/tasks означает готовность плана. Все задачи остаются открытыми до реализации и проверок. Совместные сценарии настоящего сравнения, протокола, финализации, 132/132 и количественные требования общего релиза остаются в C24; никаких новых отметок выполнения при разделении не ставится.
