# Приёмка add-safe-document-ingestion

Дата: 17.09.2026. Ветка: `feat/safe-document-ingestion`.

## Объём реализации

Выполнен путь «пустой реестр → создание объекта → явное назначение → загрузка →
receipt → повторное открытие → скачивание исходных байтов». Политика доступа и
включение необходимых зависимостей C01 подтверждены пользователем в задаче.

Миграции создают `objects/object_access`, Process/Run/RunInput, File/UploadReceipt,
Job/Outbox/AuditEvent. Составные FK связывают один object/process/run, оригиналы,
manifest, receipt и аудит защищены от изменения триггерами. User/AuthSession и
`/api/auth/*` сохранены. Служебная команда первоначального назначения администратора
и последующего управления ролями/назначениями исключает ручную вставку объектов.

Оригиналы публикуются после ClamAV и структурной проверки. PDF проверяется qpdf;
DOCX — ограниченным ZIP/XML-парсером, XML — defusedxml без DTD/внешних сущностей.
Валидатор изолирован сетью, read-only mount и лимитами ресурсов. Storage не
раздаётся через Nginx. События содержат только безопасные идентификаторы и коды.

## Стенд и воспроизводимость

Windows, Node.js 24.16.0, Bun 1.4.2; Docker Desktop/Linux containers.
PostgreSQL 17.6, RabbitMQ 4.1, ClamAV 1.4.3, Python 3.12.12, qpdf 11.3,
defusedxml 0.7.1, Nginx 1.28.0. Использованы реальные сервисы, без платных API.

```sh
bun install --frozen-lockfile
bun run --cwd backend test:services
bun run --cwd backend test:integration
bun run test
bun run typecheck
bun run build
node node_modules/eslint/bin/eslint.js backend/src backend/test frontend/src eslint.config.mjs
docker build -t inspector-ingestion-backend --target runtime -f backend/Dockerfile .
docker build -t inspector-ingestion-frontend -f frontend/Dockerfile .
openspec validate add-safe-document-ingestion --strict
node openspec/verify-planning.mjs
```

Интеграционный стенд использует `compose.ingestion-test.yaml`; тестовый Nginx
конфиг генерируется из production `frontend/nginx.conf`, меняется только upstream.
Каждый прогон создаёт новую БД `ingestion_<uuid>` и применяет все миграции с нуля.
Порты, очистка стенда и команды администратора описаны в README. Одновременно
запускается один интеграционный прогон; отдельный корпус не является обычным тестом.

Основные доказательства находятся в [интеграционных тестах](../../../backend/test/ingestion.test.ts),
[потоковых тестах](../../../backend/src/modules/documents/upload-stream.test.ts),

- Пустой реестр, автор из сессии, самоназначение через DTO запрещено, role=null,
  администратор и чужой инспектор не получают документы. Назначение/отзыв с аудитом,
  повтор выдачи не создаёт дубль; неизвестные User/Object отвергаются FK.
- PDF/DOCX/XML определяются по содержимому даже при неверном расширении; повреждённый
  PDF, XXE, встроенный исполняемый файл DOCX и безопасная EICAR-строка отвергнуты.
  Недоступный ClamAV закрывает допуск. Смешанный пакет сохраняет только допустимые входы.
- Ровно 4 × 50 000 000 байт проходят через настоящий Nginx: HTTP 202 и четыре файла.
  200 000 001 байт дают 413 без новых входов; один файл 50 000 001 байт даёт 422.
- Для потокового декодера пакета 200 МБ: baseline RSS 90 632 192, peak RSS
  215 343 104, прирост 124 710 912 байт. Это замер одного процесса/профиля, не SLA
  всего стенда и не нагрузочная приёмка 100 инспекторов.
- Параллельные идентичные запросы возвращают одинаковый receipt и один Process;
  изменённое содержимое с прежним ключом — 409. Replay в PARSING работает, новая
  дозагрузка в PARSING и подмена process_id другого объекта запрещены.
- Два объекта с одинаковыми байтами сохраняют разные File/storage handles;
  ошибочные прямые вставки с несовместимой принадлежностью отвергнуты БД.
- Обрыв тела очищает карантин без процесса. Потеря ответа после commit восстанавливается
  через receipt; повтор не дублирует приём. Реальный отказ filesystem и намеренная
  ошибка PostgreSQL до commit не оставляют принятых File/Run/Job. Сборщик удаляет
  старый orphan и сохраняет старый оригинал, на который ссылается БД.
- RabbitMQ получает persistent-сообщение после commit. При недоступности брокера
  outbox сохраняется и доставляется после восстановления. Worker использует lease
  и fencing token; возможный повтор доставки обязан обработать будущий потребитель.
- Изменённый тестовый оригинал обнаруживается контролем целостности: первоначальный
  hash не изменён, скачать повреждённый файл нельзя, событие `file.integrity-failed`
  сохранено в outbox. Неизменяемый manifest также защищён триггером. Его SHA-256
  вычисляется по каноническому JSON; повторное вычисление из сохранённого JSONB
  даёт тот же hash независимо от порядка ключей PostgreSQL.

Браузерная проверка Playwright CLI: регистрация тестового пользователя через API,
назначение INSPECTOR служебной командой, вход, пустой реестр, создание объекта
«Корпус 1 — проверка загрузки», выбор XML, результат приёма и список оригиналов.
После reload восстановились сессия, deep link объекта, receipt и реестр.
Скриншот сохранён локально в `output/playwright/object-documents.png`.
Отдельные UI-тесты проверяют восстановление receipt без повторной отправки,
различение передачи/серверной проверки и повторный выбор того же файла.

## Корпус документов

Отдельный opt-in прогон выполняется по каталогу участников
`ХАКАТОН_УЧАСТНИКАМ_ГОТОВО_К_ПЕРЕДАЧЕ/01_ДОКУМЕНТАЦИЯ`: 366 PDF и 6 DOCX,
8 264 265 033 байта. XML проверяется синтетическими корректными и опасными fixtures.
Hidden/GOLD-разметка не используется. Исходные документы не изменяются и не
передаются внешним сервисам. Набор не является независимым тестом качества OCR.

Команда из корня: `node backend/test/admission-corpus.mjs <каталог>` с окружением
`CORPUS_LOGIN/CORPUS_PASSWORD/CORPUS_API`. Каждый принятый файл скачивается через
авторизованный API и сверяется с SHA-256 исходника. JSONL содержит относительный
путь, размер, исходный/скачанный hash и индивидуальный исход; сами документы не
попадают в Git. Для этого прогона использованы четыре экземпляра того же валидатора
и `CORPUS_CONCURRENCY=4`. `CORPUS_REPORT` позволяет продолжить локальный отчёт.

Первоначальный прогон до исправления обработки предупреждений qpdf:
**167 приняты** (161 PDF и все 6 DOCX), **205 отклонены**.
У всех 167 скачанных оригиналов SHA-256 совпал с исходником. Индивидуальные
результаты и хеши находятся в [corpus-results.json](corpus-results.json).

| Причина отказа                                                   | Файлов |
| ---------------------------------------------------------------- | -----: |
| `unsafe_format`: структурная проверка или запрещённое содержимое |    169 |
| `file_too_large`: файл более 50 000 000 байт                     |     27 |
| HTTP 413: одиночный файл превысил лимит пакета 200 000 000 байт  |      6 |
| `scanner_limit`: достигнут внутренний лимит ClamAV               |      3 |

При прогоне исправлен timeout клиента ClamAV: ожидание 130 секунд согласовано
с `MaxScanTime=120000` мс. Четырнадцать исходных временных отказов перепроверены
с проверкой неизменности исходного SHA-256: 9 приняты, 3 отклонены структурной
проверкой, 2 достигли лимита сканера. В итоговом отчёте временных отказов сканера нет.

В первоначальном прогоне qpdf exit code 3 (предупреждения без ошибок) ошибочно
означал отказ. На части исходников диагностирована несогласованность счётчика
PDF-объектов; это не вирусная детекция. Пользователь подтвердил исправление
17.09.2026. Приведённые выше числа и `corpus-results.json` сохранены как история
того прогона и не описывают результат исправленного валидатора. Весь корпус
после исправления повторно не прогонялся.

## Исправление ложного отказа PDF

17.09.2026 исправлен дефект в обоих проходах qpdf: восстановимые предупреждения
без ошибок (`exit 3`) больше не превращаются в `unsafe_format`. Параметр
`--warning-exit-0` применяется к `--check` и `--json`; ошибки чтения, ограничения
ресурсов и проверка запрещённого активного содержимого остаются обязательными.
Исходные байты не нормализуются и не переписываются.

- Новый интеграционный тест с синтетическим PDF и неверным `/Size` до исправления
  воспроизвёл HTTP 422 вместо ожидаемого 202. После пересборки валидатора тест
  принимает файл и проверяет побайтовое совпадение скачанного оригинала и SHA-256.
- Два дополнительных случая отклоняют PDF с JavaScript/OpenAction: с корректной
  структурой и с тем же предупреждением `/Size`. Существующий случай нечитаемого
  PDF также прошёл проверку отказа.
- Полный интеграционный прогон на реальных сервисах: **14/14 прошли**, старт
  17.09.2026 в 10:57 МСК. TypeScript backend, ESLint затронутых тестов, Docker build
  валидатора, OpenSpec strict validate и `verify-planning.mjs` прошли.
- Отдельно, вне обычных тестов, проверен указанный пользователем оригинал:
  `Новослободская/Новослободская/Исполнительная документация/Ограждение котлована. БСС/АОСР №1А-БСС от 24.02.2026.pdf`.
  Исправленный изолированный валидатор вернул `{"format":"PDF"}`; размер
  9 705 336 байт и SHA-256
  `4e26b26409e2c59cd116b9f8dc789e6b4614000938ba83a519578e1214ae22d6`
  до и после проверки совпали. Это повтор структурной проверки конкретного файла,
  а не новый полный прогон корпуса.

Сохранённые receipts не переписываются: после обновления валидатора ранее
отклонённый файл следует отправить через «Новый пакет» с новым `client_upload_id`.
Повтор старого запроса возвращает его исторический результат по контракту
идемпотентности.

## Дедупликация содержимого (18.09.2026)

По подтверждению пользователя повторные байты в одном объекте запрещены независимо
от имени, ключа запроса и назначенного пользователя. `object_file_contents`
обеспечивает уникальность object_id/SHA-256 с FK на исходный File. Триггер защищает
и прямые записи. Миграция сохраняет существующие File/Run/receipt, выбирая самый
ранний оригинал. Известные дубли не публикуются, конкурентные неподтверждённые
копии удаляются после commit. Дубли возвращают existing_file_id; UI позволяет
скачать оригинал, а аудит отдельно считает дубли и отказы.

Проверено:

- Backend unit: 46/46, frontend: 29/29; типы, ESLint и production build проходят.
- Интеграция: 17/17 на изолированных PostgreSQL/RabbitMQ/ClamAV/validator/storage.
  Новый ключ после повторного входа, переименование, другой назначенный пользователь,
  дубли внутри смешанного пакета, иное содержимое с прежним именем, другой объект,
  отзыв доступа, восстановление receipt и блокировка повреждённого оригинала.
- Детерминированная гонка: оба запроса публикуют временные оригиналы до commit;
  ответы 202/422 с одним File/Process/Job и одной оставшейся физической копией.
- Прямое создание второго File с тем же object_id/hash отвергнуто PostgreSQL.
  Миграция повторно применена в откатываемой тестовой транзакции к состоянию
  с историческими дублями: обе записи и RunInput сохранены, реестр указывает
  на самый ранний File.
- Пакет 4 × 50 МБ продолжает проходить реальный Nginx; синтетические XML теперь
  различаются содержимым, чтобы проверка размера не превращалась в проверку дублей.
- OpenSpec strict validate и verify-planning.mjs проходят.

Логи: `.test-output/dedup-{backend-tests,frontend-tests,integration,typecheck,lint,build}.log`.

После проверок локальный Compose обновлён с сохранением пользовательских данных.
Миграция применена успешно. Отдельная ручная проверка ранее загруженного файла
на тестовом объекте пользователя через localhost:8080 вернула duplicate_file,
existing_file_id и process_id/run_id=null; число файлов осталось 3 → 3.
Эта проверка не входит в автоматические тесты и не перезаписывает исходники.
Результат сохранён в `.test-output/live-duplicate-result.json`.

## Что эта приёмка не закрывает

Не выполнены OCR/PAR, Document/Revision/идентификация, извлечение, комплектность,
геометрия, протокол, общая lifecycle/LC-08 и потребители результатов с fencing.
`PENDING` и зарегистрированное задание не выдаются за завершённый анализ.
События для C23 долговечны, но Email/Telegram-адаптеры не заявлены реализованными.

Открыты C24: межмодульные и hidden-test метрики, нагрузка 100 инспекторов и p95,
TLS внешнего ingress, шифрование носителей/backup, полное аварийное восстановление,
эксплуатационный аудит и общее решение Node.js/Bun. Сохранён существующий Bun
runtime Docker; локальные интеграционные тесты выполнены под Node.js.
