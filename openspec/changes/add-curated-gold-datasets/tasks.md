# C15. Курируемые версии GOLD

Владелец: P1 хранение/права, P3 методика данных, P2 интерфейс, P4 предметная проверка. Вход — существующие версии решений VER. Выпуск данных предшествует полноценному train/eval ML.

## 1. Происхождение, доступ и методика

- [ ] 1.1 Зафиксировать контракт примера с immutable decision/evidence/snapshot, причиной, экспертом и версиями. Проверка: контракт восстанавливает обе стороны доказательства без обращения к текущему изменяемому finding.
- [ ] 1.2 Получить перечень разрешённых объектов, методику split и назначение куратора/издателя; записать решение в контракт доступа. Проверка: явно перечислены разрешённые операции, до назначения публикация запрещена.
- [ ] 1.3 Описать критерии включения положительных и отрицательных меток и исключения автоматических match/неполных исходов. Проверка: таблица примеров покрывает все статусы и отсутствие экспертного решения.

## 2. Кандидаты в набор

- [ ] 2.1 Добавить хранение кандидатов, кураторских решений и версий без изменения истории VER. Проверка: миграции сохраняют существующие решения, ссылки не допускают чужой объект.
- [ ] 2.2 Подключить идемпотентный сбор из новых и разрешённых исторических решений. Проверка: повтор события не создаёт вторую метку, исторические записи не утверждаются автоматически.
- [ ] 2.3 Реализовать проверку полноты доказательств, происхождения, причин и пригодности класса. Проверка: потерянный фрагмент, неизвестная версия, SUSPICION и автоматический отрицательный match отвергаются с разными причинами.

## 3. Курирование

- [ ] 3.1 Добавить защищённый API списка, карточки, принятия и возврата кандидата с контролем версии. Проверка: конкурентное решение получает конфликт, пользователь без полномочия не выполняет mutation.
- [ ] 3.2 Создать интерфейс проверки доказательств и причин с переходом к разрешённым источникам. Проверка: куратор видит происхождение метки и ограничения, чужие оригиналы не открываются через deep link.
- [ ] 3.3 Обработать пересмотр инспекторского решения как новую версию кандидата. Проверка: опубликованный ранее набор не изменяется; новая метка ссылается на причину исправления.

## 4. Выпуск и экспорт

- [ ] 4.1 Реализовать object-group split с проверкой всех редакций/представлений и отчётом совпадений байтов между группами. Проверка: пересечение train/validation/test блокирует выпуск.
- [ ] 4.2 Добавить неизменяемый выпуск dataset_version с составом, хешами, версиями и классами. Проверка: повторное чтение после новых решений даёт прежний manifest hash.
- [ ] 4.3 Реализовать минимальный разрешённый экспорт и верификацию его ссылок/хешей. Проверка: экспорт восстанавливается в изолированном контуре, не включает hidden GOLD, секреты или неразрешённые оригиналы.
- [ ] 4.4 Добавить сводку объёма и покрытия по объектам/классам/категориям. Проверка: число подтверждённых нарушений не используется как единственный признак пригодности датасета.

## 5. Приёмка

- [ ] 5.1 Выпустить реальный разрешённый набор с положительными и отрицательными экспертными примерами. Проверка: все метки имеют экспертное и кураторское происхождение, split и hashes проверены независимым повтором.
- [ ] 5.2 Проверить права, конкурентность, повтор доставки и исправление после выпуска на изолированной PostgreSQL/очереди. Проверка: тесты и фактические команды записаны в evidence.md, история неизменна.
- [ ] 5.3 Передать опубликованную версию runner ML и зафиксировать интерфейс её чтения. Проверка: runner принимает ровно выбранный manifest, неподтверждённый черновик отвергается.
