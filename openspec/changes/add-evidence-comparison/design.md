# Дизайн: предварительное сравнение expected/actual

Срез добавляет вердикт сравнения поверх уже собранных EvidenceGroup (EXT),
не меняя движок извлечения и не вводя решения инспектора.

## Решения

### Сравнение — спека версии правила, а не код параметра

`rule_versions.comparison` (колонка существует со схемы EXT) хранит проверенную
JSON-спеку. Новая версия правила обязана нести comparison заново: спека
неизменяема внутри версии, как и план. Новая approved-версия меняет
ruleset fingerprint → переизвлечение и пересборка групп идут существующим
механизмом EXT без отдельного контура доставки.

Основание и альтернатива: спека как часть версии правила сохраняет
аудируемость «чем сравнивали» наравне с «что искали». Отдельная таблица
сравнений дублировала бы жизненный цикл версии.

### Минимальный набор операторов покрывает триггеры матрицы

- `equals` — нормализованное равенство текста; числа сравниваются численно
  («несоответствие отметки», P009 ±0.000);
- `numeric_delta` — `|actual − expected| ≤ tolerance_abs` или
  `≤ tolerance_pct · |expected|` (P002 «дельта > 1%»);
- `no_decrease` / `no_increase` — порядковое сравнение (P055 «понижение
  класса бетона», P058 «уменьшение толщины»);
- `threshold` — нормативная граница на само значение без пары
  (P048 «проступь < 300 мм»).

Основание: триггеры matrix-132 в свободной форме описывают ровно эти
семантики — равенство, допуск, направленное ухудшение, нормативная граница.
Генерацию спеки из текста триггера LLM'ом срез не делает: comparison задаёт
администратор при создании версии и утверждает вместе с планом.

### Вердикт вычисляется при сборке группы и персистится

`rebuildGroups` после формирования members вызывает чистую функцию
`evaluateGroup(members, spec)` и сохраняет результат в
`evidence_groups.verdict` вместе со снимком спеки и версией движка
сравнения. Чтение вердикта не пересчитывает его — ответ API отражает
сохранённое состояние цикла.

Основание и альтернатива: вычисление на чтении не оставляет
аудируемого «что было показано», а персист в момент сборки фиксирует
вердикт вместе с ruleset_hash той же транзакции.

### Стадия — снимок на момент извлечения; протухание чинится циклом

`extractions.stage` остаётся снимком классификации на момент цикла.
`recover()` дополнительно ставит новый цикл извлечения артефакту, чья
последняя succeeded-классификация дала стадию, отличную от сохранённой в
извлечениях (`IS DISTINCT FROM`). После переизвлечения снимок сходится с
классификацией — повторных циклов не возникает. Переисполнение дёшево:
извлечение — regex/таблицы по уже сохранённому артефакту.

Основание: джойн «живой» классификации в сборке групп разорвал бы
инвариант снимка и оставил бы список извлечений с устаревшей стадией —
рассинхрон ролей группы и строк UI.

### Исходы вердикта — явные, без выдумывания

`match`, `discrepancy`, `expected_missing`, `actual_missing`,
`expected_ambiguous`, `actual_ambiguous`, `not_comparable`,
`no_comparison`. Отсутствие источника стадии (`expected_missing`/
`actual_missing`) — легитимный исход «источник не передан», а не
нарушение; `ambiguous` стороны сохраняет альтернативы для инспектора;
несовместимые единицы дают `not_comparable`, а не численный mismatch.

### Область сравнения

`scope_key` остаётся `""`: параметр сравнивается атомарно по объекту.
Разнесение по корпусам/секциям/осях — отдельная задача; до неё несколько
различных значений внутри одной стадии честно дают `*_ambiguous`.

## Ограничения среза

- Вердикт предварительный: не создаёт CANDIDATE/NEGATIVE_VERIFIED/
  CONFIRMED_VIOLATION и не входит в протокол (C07/C24).
- Одна группа = один параметр объекта; многозначные параметры
  (лестницы, корпуса) сравниваются без разнесения по области.
- Спеку сравнения задаёт администратор; LLM-драфт сравнения не
  предлагается и не утверждается автоматически.
