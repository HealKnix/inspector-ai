# Предварительное сравнение expected/actual

Владелец: сравнение поверх EXT. Нумерация локальная. Разделы 1–5 сохраняют
11 выполненных задач исторического среза и его evidence. Текущее разделение
редакций/областей уже поставлено ID; возврат к пустому scope не планируется.
Новое выполнение начинается с раздела 6, по [execution-plan.md](execution-plan.md).

## 1. Контракт и движок сравнения

- [x] 1.1 Контракт `ComparisonSpec` (`equals`, `numeric_delta` abs/pct,
      `no_decrease`, `no_increase`, `threshold` min/max) с валидацией в стиле
      `validateExtractionPlan`: whitelist полей, неотрицательные допуски,
      `min < max`, отклонение неизвестных полей. Проверка: unit-тесты на
      принятие/отклонение каждой формы.
- [x] 1.2 Чистый движок `evaluateGroup(members, spec)`: выбор
      expected/actual по роли и статусу `extracted`, попарное сравнение,
      исходы match/discrepancy/expected_missing/actual_missing/
      expected_ambiguous/actual_ambiguous/not_comparable/no_comparison,
      проверка единиц через `normalizeUnit`, детали `pairs[]` со ссылками на
      извлечения и дельтой. Проверка: unit-тесты покрывают каждый исход,
      несколько actual, уточнение класса («В40» vs «В40 F150 W6»),
      несовместимые единицы.

## 2. Данные и пайплайн

- [x] 2.1 Миграция: `evidence_groups.verdict JSONB` + поле в Prisma-схеме.
      Проверка: `prisma migrate deploy` на живой БД, обратная совместимость
      (старые строки без вердикта читаются).
- [x] 2.2 `ApprovedRule` несёт `comparison`; `approvedRules()` валидирует
      спеку при загрузке (невалидная → отсутствует). Проверка: fingerprint
      не меняется от смены спеки без новой версии.
- [x] 2.3 `rebuildGroups` вычисляет `evaluateGroup` и пишет вердикт со
      снимком спеки, версией движка и временем. Проверка: upsert
      идемпотентен, вердикт соответствует members той же транзакции.
- [x] 2.4 `recover()`: новый цикл извлечения, когда последняя
      succeeded-классификация дала стадию, отличную от `extractions.stage`.
      Проверка: после LLM-классификации PD роли группы обновляются без
      ручных действий; цикл не повторяется, когда стадия сошлась.

## 3. Админ-API и аудит

- [x] 3.1 `createDraft` принимает необязательный `comparison` с
      валидацией; `approve` валидирует спеку повторно; события аудита
      фиксируют `has_comparison`. Проверка: невалидная спека → 400, версия
      не создана; утверждённая спека видна в ответе версии.

## 4. Интерфейс

- [x] 4.1 Zod-схема вердикта и поле `verdict` в `evidence-groups`
      (аддитивно); блок сверки в карточке объекта: статус-чип, expected vs
      actual со ссылками на страницы, дельта, warnings. Проверка: инспектор
      видит «предварительный» характер вердикта; группы без спеки помечены
      «сравнение не настроено».

## 5. Проверки и доказательства готовности

- [x] 5.1 Правила с comparison для демо-параметров: P009 `numeric_delta`
      (abs 0,01), P022 `equals` (v3 — текстовый слой КЖ содержит «l»
      вместо римской I), P002 `numeric_delta` 1% (v5 regex по «Суммарная
      поэтажная площадь объекта»; v3/v4 отклонены — срезка разрядов и
      колонка ГПЗУ). Проверка: спеки сохранены, циклы переизвлечения
      прошли. P055/P061/P062 не заведены — см. ограничения в evidence.md.
- [x] 5.2 Живой прогон на корпусе «Новослободская» (ПЗ, ПЗУ, АР, КЖ1.1.1,
      СВГ, АОСР №1РЗ — все 6 файлов распарсены и классифицированы):
      вердикты сверены с эталоном отчёта —
      P009 `match` (159,95 = 159,95, expected слит из ПЗ/ПЗУ/АР),
      P022 `discrepancy` (ПД «II» vs КЖ «l» — дефект текстового слоя),
      P002 `expected_ambiguous` (ПЗ 13 997,9 vs ПЗУ 13 999,7).
      Проверка: evidence.md содержит команды, ответы API, ограничения;
      mocks не закрывают интеграцию.
- [x] 5.3 Применимые проверки репозитория (vitest, typecheck backend и
      `tsc -b` frontend, eslint, prettier) и пересборка всех backend-образов
      (backend + workers). Проверка: результаты записаны в evidence.md.

## 6. Этап A — политика нормализации и совместимости

- [x] 6.1 Зафиксировать новую версию numerical-policy и результата вместе с ранним паспортом C05/C18: размерность, единица, её источник, округление, abs/pct и нулевой expected; проверка: примеры старой/новой пары валидируются, неподтверждённая бизнес-политика не получает default.
- [x] 6.2 Добавить decimal-нормализацию со сохранением raw и provenance без эвристической замены `1/l/I`; проверка: знак, запятая/точка, разделители тысяч, отрицательное значение и неоднозначное чтение дают ожидаемые результаты.
- [x] 6.3 Ввести строгую политику отсутствующей единицы/безразмерности и устранить неявное заимствование при слиянии; проверка: `1000` без единицы и `1000 м` не дают match, подтверждённая единица заголовка имеет свой locator.

## 7. Этап B — преобразование и неопределённость

- [x] 7.1 Реализовать версионированный whitelist преобразований совместимых единиц с сохранением коэффициента/степени; проверка: мм↔м, см²↔м², объём и несовместимые размерности покрыты независимыми численными ожиданиями.
- [x] 7.2 Подключить новую численную политику ко всем пяти существующим операторам; проверка: равенство/допуск/направление/threshold, знак и нулевой expected воспроизводятся на decimal-границах, EPSILON не расширяет предметный допуск.
- [ ] 7.3 Сохранять альтернативы числа/единицы и реальную неопределённость измерения; проверка: интервал через границу, конфликт OCR и отсутствующая опора дают `not_comparable`, confidence не используется как погрешность.
- [x] 7.4 Добавить трассу raw → normalized → converted → сравнение с версиями и основаниями; проверка: обе стороны восстанавливаются до своих локаторов, процент/доля преобразуются только по явному правилу.

## 8. Этап C — публикация и представление
