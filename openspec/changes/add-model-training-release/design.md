## Context

C16. В текущем приложении есть Python OCR и model/config fingerprints, но нет реестра обучающих запусков, датасетов и допуска моделей. [Proposal](proposal.md) описывает результат. C15 должен предоставить опубликованный набор; протоколы/Run уже умеют хранить версии.

## Goals / Non-Goals

**Goals:** повторяемая локальная итерация от датасета до артефакта, сравнение с baseline, ручной допуск, контролируемое переключение и rollback.

**Non-Goals:** автоматическое улучшение модели по каждому решению; публикация по одному F1; переобучение всего стека одновременно; обучение на hidden test.

## Decisions

1. **Первую обучаемую компоненту выбирает ограниченный validation-эксперимент.** Фиксируются задача, лицензия, исходные веса, бюджет GPU и доступные метки. Предпочтение без измерения конкретной модели/архитектуры не закрепляется. Обучение оформляется существующим job/worker-контрактом; Python не пишет предметные таблицы напрямую.
2. **Реестр запуска хранит полную воспроизводимость.** dataset/matrix/base-model/code/config/seed/environment hashes, параметры, метрики и хеш выходного артефакта. Повтор может дать численно близкий результат при недетерминированном GPU; предел воспроизводимости явно описывается, байтовое равенство не обещается без проверки.
3. **Допуск содержит два уровня.** Validation решает, можно ли передать candidate model независимому оценщику. Публикация для полного ТЗ требует всех порогов §14 и отсутствия падения Recall категории более 2 п.п. или роста FPR более 2 п.п. Ответ hidden evaluator — отчёт, а не выдача hidden GOLD разработчикам. Хакатонная демонстрация итерации не выдаётся за промышленный допуск.
4. **Approve/reject — отдельное подписанное решение ответственного.** Полномочие назначается явно; роль ML-инженера не равна праву публикации. Отсутствие метрики обязательной категории блокирует допуск.
5. **Версия закрепляется на старте Run.** Переключение применяется только к новым запускам. Rollback меняет указатель принятой версии и проходит health/smoke; история и старые результаты остаются воспроизводимыми. Автопубликация отвергнута.
6. **Обучение не вытесняет проверку документов.** Отдельный бюджет ресурсов/расписание и мониторинг; параметры concurrency измеряются на целевой GPU. Необходимый набор весов включается в OFF.

## Этапы и зависимости

1. Выбор ограниченной обучаемой задачи и baseline; контракт версий/прав.
2. Реестр и локальный train/eval runner на GOLD.
3. Метрики, сравнение категорий и независимый отчёт приёмки.
4. Ручной допуск, deployment pointer и откат.
5. Одна полная воспроизводимая итерация и демонстрация отказа в допуске/rollback.

Методика ACC нужна до эксперимента; окончательный ACC требует выпущенного кандидата, а не наоборот. Полная приёмка системы не является зависимостью запуска train/eval.

## Risks / Trade-offs

- [Недостаточно примеров категории] → сохранить ограничение и блокировать соответствующее заявление о готовности.
- [Одна метрика скрывает регрессию] → проверки каждой обязательной категории и FPR отдельно.
- [Модель загружена не полностью] → переключение после integrity/readiness/smoke, предыдущие веса доступны.

## Migration Plan

Добавить реестр аддитивно; текущие веса зарегистрировать с фактическим происхождением, без фиктивного approval. Сначала train/eval без deployment, затем ручной допуск. Откат сохраняет новые артефакты и аудит.
