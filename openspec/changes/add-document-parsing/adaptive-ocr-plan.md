# Адаптивный OCR: утверждённый план от 18.09.2026

## Граница внедрения

Сначала выполняется отдельный эксперимент PP-DocLayout_plus-L на исходном
изображении без маскирования текста и без OCR. Включение автоматического
исключения графики в рабочем парсере зависит от результата. При провале
условий результатом этапа служит отчёт с конкретными ошибками; адаптивный
маршрут остаётся невключённым. VLM и редактор областей не входят в итерацию.

Корпус: все 20 страниц пользовательского PDF, ранее проверенные паспорт и
исполнительная схема, растровые копии контрольной текстовой страницы и плана,
синтетические PDF с таблицей, смешанным содержимым, повреждённым Unicode,
CropBox и четырьмя поворотами. До inference сохраняется ожидаемая разметка.
Исходники, извлечённый текст и изображения остаются локально вне Git.
Отчёт содержит исходные классы/оценки/bbox Paddle, наложенные границы,
ошибки выделения, время и память при действующих CPU/RAM-ограничениях.

Условия перехода: рамка текстовой страницы не становится таблицей;
сопровождающие план таблицы, заголовки и пояснения доступны отдельно;
план не поглощает таблицы; конфликты и неуверенность становятся явными
неопределёнными областями; соблюдены ресурсные ограничения.

## Маршрутизация после успешной проверки

Порядок: структура PDF → исходный рендер → области → привязка native-текста
→ выборочное распознавание → сохранение. Категории: текст, таблица,
графическая область, неопределённая область. У модели нет отдельного класса
строительного чертежа или основной надписи; расположение не доказывает их тип.

В текстовых/табличных областях детектор строк проверяет native-покрытие без
распознавания символов. Стартовые параметры: корректный Unicode, допустимые
координаты и направление, покрытие строки не менее 90% с допуском 2 пикселя.
Это критерий маршрутизации, не метрика точности. При полном покрытии текст
извлекается напрямую; при частичном — OCR только непокрытых строк.
OCR использует исходный PDF-crop без автоматического повышения DPI/повторов.

Native-таблица разбирается ограниченным областью PyMuPDF; неудача структуры
сохраняет текст с предупреждением и не запускает OCR хорошего текста.
Растровая таблица использует компоненты PP-StructureV3 на отдельном фрагменте.
Графические и неопределённые области сохраняют изображение и native-надписи
без OCR. Конфликты границ не разрешаются молчаливым поглощением.
Линии/рамки/векторы сами по себе не запускают OCR всей страницы.

Адаптер к закреплённой версии управляет этапами с одним набором моделей;
полный PPStructureV3.predict() в адаптивном маршруте не используется.
Координаты возвращаются к исходной отображаемой странице; CropBox+Rotate
проверяются отдельно. Whitespace-only текстовые OCR-блоки удаляются,
пустые ячейки настоящих таблиц сохраняются.

## API и просмотрщик после успешной проверки

PAR расширяется добавочной версионированной разметкой областей: bbox,
исходный класс/оценка Paddle, маршрут, причины пропуска. Каждый новый PDF-блок
связан с областью и имеет признак включения в основное представление.
Полный raw/normalized текст, включая native-надписи графики, сохраняет смысл.
Отбор для представления не означает признание доказательством для матрицы.

Режим «Области» показывает границы, список, содержимое или объяснение пропуска.
Основной список исключает надписи графики/неопределённых областей; полный текст
доступен с ясным описанием состава. Различаются отсутствие таблицы,
неподтверждённая структура и непрочитанные ячейки. Плановый пропуск графики
не означает плохое качество или пустой документ. Старые артефакты читаются
с указанием отсутствия разметки; новый профиль требует полных связей.
Код/настройки/модели входят в fingerprint; несовместимые checkpoints не берутся.

## Независимые исправления исполнения

Claim и ожидание моделей не обнуляют прогресс. Перед продолжением проверяются
сохранённые страницы; во время проверки показывается последний подтверждённый
прогресс. После проверки счётчик отражает действительные checkpoints;
повреждение или смена версии объясняют повторную обработку без искусственного
удержания старого числа. API хранит этап, время прогресса, причину ожидания
и следующую попытку. UI различает определение областей, извлечение текста,
распознавание, ожидание моделей и возобновление.

Непрерывное models_not_ready ограничено 300 секундами, затем техническая
ошибка и обычный ручной повтор. Ожидание не расходует три реальные попытки.
Сохраняются fencing, неизменяемый оригинал и PARSING → PENDING после исходов
всех файлов. Health не перезапускает дочерний процесс, уже сообщивший ready.

## Проверка и выпуск

Проверяются отсутствие OCR графики/unknown и покрытого native-текста,
чтение сканов рядом с графикой, сохранность native-знаков, пустые блоки,
координаты, понятные ограничения, legacy, возобновление и deadline ожидания.
После применимых тестов обновляются спецификация/инструкции; приложение
пересобирается, разрешённые контрольные документы обрабатываются повторно
без удаления оригиналов, изменения публикуются в feat/document-parsing.
Если layout-проверка не прошла, условные задачи внедрения не отмечаются
выполненными; публикуются отчёт и независимо проверенные исправления.
