# Проверка add-document-parsing

Дата: 18.09.2026. Ветка: `feat/document-parsing`. Запуск для участников:
[docs/document-parsing.md](../../../docs/document-parsing.md).

## Объём

Реализованы отдельные долговечные задания файлов, локальный Python/PaddleOCR,
чтение PDF/DOCX/XML, полный извлечённый raw/normalized текст, страницы PNG,
блоки/ячейки/локаторы, качество и версии. Backend проверяет схему, хеши оригинала,
артефакта и PNG, геометрию, текущий Run и право worker на публикацию. Пользователь
видит прогресс, причины проблем, страницы, поиск, выделение и ручной повтор.

Решение владельца: текущий процесс `PARSING → PENDING` после всех исходов файлов,
включая исчерпание попыток. `READY` без протокола не выставляется. Успешные файлы
не теряются из-за ошибки соседнего. Повтор использует тот же оригинал и новый
ограниченный цикл; повтор HTTP request_id не создаёт второй цикл. Новые входные
файлы создают новый текущий Run в PENDING. Исходные байты не перезаписываются.

Ветка также содержит предпосылку ING и её существующие изменения. Общие C01/C23
реализованы только в необходимых для PAR границах: outbox, доставка, lease/fencing,
аудит, безопасные события и структурные логи длительности/попыток/cache hit.
Отправка уведомлений администратору и общая система мониторинга остаются в C23.

## Локальная оценка PaddleOCR

Использован разрешённый validation-корпус из рабочего каталога и отдельно созданные
синтетические документы. Hidden test не использовался. Документы, извлечённые
тексты, PNG, учётные данные стенда и закрытые отчёты не включены в Git.

Структурно прочитаны все 39 разрешённых DOCX/XML (21 + 18): непустой текст,
363–12384 символа на файл; обнаружены 22 текстовых фрагмента ячеек.
Проба ориентации на трёх разрешённых изображениях и четырёх поворотах дала 12/12
верных ортогональных направлений. Это маленькая проверка выбора поворота,
а не показатель точности распознавания документов.

Воспроизводимые синтетические файлы создаёт
[generate_synthetic.py](../../../backend/document-parser/tests/generate_synthetic.py).
Реальные модели запускаются через killable Supervisor в
[benchmark.py](../../../backend/document-parser/benchmark.py). Генератор, manifest
и результаты должны использовать каталог вне репозитория:

```sh
python backend/document-parser/tests/generate_synthetic.py --output /private/par-input
python backend/document-parser/benchmark.py --source-root /private/par-input --manifest /private/par-input/manifest.json --output /private/par-result --models /models
```

CER/WER считаются только при переданном вручную проверенном truth; без него
`accuracy: null`. Оценка confidence модели не выдаётся за измеренную точность.

Финальная синтетическая проба на Windows Python 3.12.10 с Arial (те же версии
моделей/пакетов, отдельно версионированный renderer):

| Случай                                               | Время обработки | CER  | WER |
| ---------------------------------------------------- | --------------- | ---- | --- |
| DOCX только с изображением, 1 страница               | 3,503 с         | 0/37 | 0/6 |
| Текстовый PDF с CropBox, 1 страница                  | 0,815 с         | 1/37 | 1/6 |
| Смешанный PDF, скан с CropBox/Rotate 90°, 2 страницы | 6,132 с         | 2/37 | 1/6 |

Инициализация моделей заняла 41,715 с при параллельной сборке контейнеров.
В смешанном случае truth относится к странице скана. Сохранились ошибки похожих
кириллических/латинских знаков; автоматическое исправление шифров не выполняется.
Все три артефакта прошли реальные схемы backend и frontend. Эти 37 символов на
случай не дают основания объявить достигнутой точность на строительном корпусе.

## Реальный путь API → очередь → Python → storage → viewer

На изолированном стенде свежая БД применяет миграции; отдельные API и два Bun
worker используют реальный RabbitMQ, Redis, ClamAV, validator и Python Docker.
Четыре принятых документа разрешённого корпуса прошли с первой попытки финального
цикла. Время ниже — полный вызов обработки из worker, а не только OCR:

Fingerprint Linux-прогона:
`7612ce51732ff6ed9a86baf5fa992ea48a562ab213e367912e6026f0f973fe17`.

| Тип                      | Время    | Страниц представления | Символов raw_text | Блоков | Исход       |
| ------------------------ | -------- | --------------------- | ----------------- | ------ | ----------- |
| Паспорт PDF              | 53,976 с | 1                     | 1073              | 55     | LOW_QUALITY |
| Исполнительная схема PDF | 60,208 с | 1                     | 2395              | 57     | LOW_QUALITY |
| Полный акт DOCX          | 5,087 с  | 9                     | 12275             | 171    | LOW_QUALITY |
| Акт XML                  | 3,421 с  | 10                    | 5309              | 220    | OK          |

У схемы получены 57 предполагаемых ячеек с TABLE_GEOMETRY_UNVERIFIED: это не
подтверждение правильности интерпретации чертежа. DOCX содержит инструкции полей
и неподдерживаемые элементы; причины видны. Отдельный исходный PDF-акт был отклонён
ещё ING как unsafe_format; это ограничение приёма не обходилось ради OCR-теста.

После обработки API вернул PENDING. Для всех четырёх файлов повторно скачаны
оригиналы и проверено совпадение SHA-256; JSON и PNG доступны через защищённые
маршруты. Повтор запроса retry с тем же request_id вернул то же задание.
Redis действительно получил ключ hash+fingerprint. Повторная загрузка того же
XML в другой объект переиспользовала страницы, сохранив отдельные file/run/artifact
связи. После остановки Redis сохранённые JSON и PNG остались доступны; SHA PNG
проверен. Redis затем запущен снова.

В браузере проверены вход, восстановление страницы после reload, видимость
статусов/причин, поиск текста, выбор фрагмента и масштаб. Скриншоты и полные
отчёты хранятся локально вне коммита. Отдельные тесты покрывают остановку polling
при ошибке схемы/прав и смену Run, а также привязку изображений к версии артефакта.

## Дополнительная проверка PP-StructureV3

По запросу владельца 18.09.2026 выполнен отдельный локальный эксперимент на
тех же PNG паспорта и исполнительной схемы; SHA-256 копий совпал с исходными
сохранёнными изображениями. Это разрешённый validation, не hidden-приёмка.
Воспроизводимая команда, зависимости и веса закреплены в
[experiments/README.md](../../../backend/document-parser/experiments/README.md),
наблюдения и условия дальнейшей интеграции — в
[отчёте](../../../docs/pp-structure-v3-experiment.md).

PP-StructureV3 / PaddleOCR 3.7.0, PaddleX 3.7.2, PaddlePaddle 3.3.1,
Python 3.12.10 / Windows, CPU: два логических процессора, MKLDNN выключен.
Сохранён русский `eslav_PP-OCRv5_mobile_rec`; основная проба использует прежний
mobile detector с пределом 1536 px. Новые layout/table-модели скачивались
отдельно; инференс использовал локальные файлы и запрет сетевых соединений.
Модельный lock содержит 30 файлов, включая три файла дополнительного server
detector. Наличие этих весов не означает успешный прогон с ними.

- Паспорт: две таблицы, 21 ячейка, форма 2×3 и 5×3 подтверждена по изображению;
  prediction 74,050 с. Ошибка потери минуса и ошибки единиц сохранились.
- Схема: одна ошибочная таблица на почти весь чертёж, 35 HTML-ячеек; prediction
  104,932 с. Подписи, штамп и ведомость перемешались. Это отрицательный результат
  по структуре схемы, несмотря на наличие чисел в тексте.
- Server detector / 3072 px: остановлен вручную после наблюдённого пика
  9 962 450 944 байт памяти; завершённого результата нет. Отдельная запись
  `resource-aborted` отличает это от таймаута и успеха. Для production-лимита
  4 GiB эта конфигурация непригодна без дальнейшей переработки.

Время prediction включает ленивую загрузку вложенного OCR таблиц. Процессы
запускались последовательно, без прогревочного инференса. Эти наблюдения не
являются общей нагрузочной метрикой. Полные JSON/таблицы/текст, ручная разметка,
исходные PNG, конфигурации и снимки выполненного runner сохранены локально вне
Git; публичный отчёт содержит только технические наблюдения.

Прежний `LocalOCR` повторён в той же среде и на тех же PNG: паспорт 31,220 с,
схема 60,601 с (prediction без начальной загрузки, только OCR). Первый режим
PP-StructureV3 требует дополнительного времени для разметки/таблиц; измерения
не смешиваются с прежними Docker/PDF таймингами.

Проверены шесть границ runner: очистка HTML с сохранением Unicode/пустых
ячеек/spans, отказ путям внутри Git, реальное прекращение зависшего child,
запрет сети, отказ непустому каталогу результата и полнота/целостность
закреплённых моделей. Отдельный read-only review подтвердил неизменность
рабочего Python-кода и его зависимостей на момент отдельной пробы. Эксперимент
исключён из Docker-образа. Последующее подключение по решению владельца описано
ниже; историческая baseline-команда использует сохранённый legacy_ocr.py.

## Подключение PP-StructureV3 к рабочему приложению

По следующему явному запросу владельца PP-StructureV3 стал рабочим OCR-процессором.
Закреплены девять моделей / 27 файлов, mobile1536 + eslav, 96 Linux/Python 3.11
зависимостей. Runtime загрузил модели в изолированной сети Compose, read-only
rootfs и моделях, с прежним лимитом 4 GiB / 2 CPU. Конфигурация и код меняют
fingerprint; JSON версии OCR-конфигурации заменён её SHA-256, чтобы соблюсти
границу длины версии 256 символов. Формат артефакта остаётся schema_version=1.

Адаптер сохраняет исходные overall OCR-строки и независимое чтение таблиц.
Ячейки имеют проверенные индексы, spans и координаты исходного PNG. Некорректные
пересечения/оси отклоняют сетку, сохраняя текст и TABLE_STRUCTURE_REJECTED.
Ограничение по площади страницы исключено: корректная полноформатная таблица
проходит. При отсутствии надёжного преобразования строк вложенного OCR таблицы
используется bbox всей таблицы и отдельный structural_path.

28 Python-тестов прошли на Windows и внутри окончательного Linux-образа
(8,309 с в контейнере), включая все повороты, CropBox, merged/empty cells,
конфликтующую геометрию, сохранение текста, полный размер таблицы и fingerprint.
Семь проверок отдельного экспериментального runner прошли. Replay сохранённых
PP-результатов прошёл строгую backend-схему: паспорт — 79 блоков, 21 ячейка,
две таблицы; схема — 158 блоков, ноль принятых ячеек и явное предупреждение.
Replay не считается новым OCR-прогоном или измерением производительности.

Живой запуск выявил отказ при прогреве моделей после таймаута старого большого
PDF: HTTP 503 MODELS_NOT_READY ошибочно расходовал попытки следующих файлов.
Исправление различает точный ответ `models_not_ready`/`retryable:true` со статусом
503 и обычную недоступность/невалидный ответ. Отказ до принятия задания использует
существующую отсрочку capacity с fencing; прочие ошибки сохраняют ограниченные
повторы. Ранее неуспешные файлы запущены новым циклом через публичный retry API,
их история не переписана. По отдельному решению владельца пять прежних загрузок
удалены из локального стенда, четыре новых тестовых оригинала сохранены.

Окончательный живой прогон выполнен через обычные upload/retry API, RabbitMQ,
Linux Python-процессор и хранилище. Все четыре файла завершились в новом цикле
с первой принятой попытки; процесс вернулся из PARSING в PENDING:

| Документ                 | Страницы представления | Символы исходного текста | Блоки |          Ячейки | Качество    |
| ------------------------ | ---------------------: | -----------------------: | ----: | --------------: | ----------- |
| Паспорт PDF              |                      1 |                     1820 |    79 | 21, две таблицы | LOW_QUALITY |
| Исполнительная схема PDF |                      1 |                     6922 |   158 |               0 | LOW_QUALITY |
| Акт DOCX                 |                      9 |                    12275 |   171 |               0 | LOW_QUALITY |
| Акт XML                  |                     10 |                     5309 |   220 |               0 | OK          |

Число символов включает сохранённые альтернативы OCR и ячейки, поэтому это
объём результата, а не метрика точности. DOCX/XML используют структурное
извлечение; наличие версии OCR в общем fingerprint не означает OCR всего
содержимого. Для схемы сетка отклонена с TABLE_STRUCTURE_REJECTED, текст
сохранён. Потеря минуса в контрольном значении паспорта остаётся видимой;
значение не исправлялось эвристикой. SHA-256 скачанных оригиналов совпал с
входными файлами во всех четырёх случаях.

В настоящем браузере проверены вход, четыре результата, версия движка,
просмотр обеих таблиц, выбор ячейки и соответствующее выделение на скане.
Снимок экрана проверен визуально. Полный текст содержит шапку и заключение
паспорта в исходном и нормализованном вариантах. Для схемы видны сохранённый

## Границы рабочего парсера

- Любой OCR сохраняет `OCR_UNVERIFIED`; сомнения и непрочитанные области видны.
  LOW_QUALITY/ABSTAIN — качество извлечения, не нарушение Матрицы.
- DOCX/XML показываются в воспроизводимом структурном представлении, отличном
  от пагинации Word. Исходный файл доступен отдельно; удалённый/вставленный текст
  и инструкции полей сохраняются раздельно с явными предупреждениями.
- Растровые таблицы разбираются PP-StructureV3, native-PDF без OCR сохраняет
  геометрический разбор линий. Рукопись, печати, произвольный наклон и сложные
  схемы надёжно не поддержаны. Классификация документов, извлечение предметных
  значений, комплектность, геометрические проверки и протокол относятся к
  следующим changes.
- C24 остаётся открытой: независимый корпус и количественная точность,
  field-level exact match, требования времени для 100/500 страниц,
  нагрузка/восстановление всего развёртывания и 132/132 правила не объявлены
  пройденными. Малая локальная проверка не заменяет эту приёмку.
