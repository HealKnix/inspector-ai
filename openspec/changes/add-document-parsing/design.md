## Context

См. [proposal.md](proposal.md) для мотивации и [spec](specs/document-parsing/spec.md) для поведения. ING реализует объекты, назначения доступа, неизменяемые оригиналы, Process/Run/Job, outbox и publisher RabbitMQ. Это не закрывает C01: потребитель, попытки, fencing и Python-порт реализуются здесь. Изменения сохраняют /api/auth/*, текущий React-клиент и Bun workspaces. Источники — [PDF и приложения](../../../docs/requirements/SOURCES.md).

До завершения: [ING](../add-safe-document-ingestion/proposal.md); общие зависимости C01 в [SHARED_BACKLOG.md](../../SHARED_BACKLOG.md). Интерфейсы можно разрабатывать по согласованным контрактам до готовности зависимостей, но интеграцию закрывают на реальных компонентах.

## Goals / Non-Goals

**Goals:** определить границы данных, взаимодействия и доказательства результата capability document-parsing. Page, ParseArtifact и RenderedArtifact принадлежат PAR. Python возвращает данные; Node проверяет schema/run/fencing и сохраняет результат. Viewer PAR переиспользуют ID, EXT, GEO и COM.

**Non-Goals:** Классификация стадий/редакций принадлежит ID; извлечение параметров — EXT; измерение расстояний — GEO. Здесь не формируются findings и READY.

## Decisions

Решения пользователя и техническая схема уточнены 18.09.2026 в [implementation-contract.md](implementation-contract.md). Один файл имеет отдельное фоновое исполнение; Run-level Job остаётся совместимым родителем. Сохраняются весь извлечённый raw/normalized текст, блоки, таблицы, локаторы, качество и версии. PaddleOCR — первый проверяемый кандидат. Подтверждён переход `PARSING → PENDING` после долговечных исходов всех файлов текущего Run; `READY` здесь не формируется.

Реализация использует PaddleOCR 3.7.0 / PaddlePaddle 3.3.1, PyMuPDF, детерминированный
структурный renderer DOCX/XML и Redis. Рабочий PP-StructureV3 использует девять
моделей; все 27 файлов закреплены SHA-256.
Ориентацию выбирает локальный классификатор; CPU-задача выполняется в отдельном
завершаемом процессе с лимитами. Полный контракт и ограничения находятся в
[описании парсера](../../../backend/document-parser/README.md).

[Общий контракт](../../CONTRACTS.md) фиксирует владельцев, поля, версии и порядок интеграции. Технические решения ниже — проект реализации; подтверждённые роли и бизнес-статусы берутся из PDF.

### D1

Python >=3.11 получает только разрешённые storage handles и immutable InputManifest через внутренний контракт. Node валидирует ответ и сохраняет ParseArtifact с parser/model/renderer/config versions; Python не меняет предметные таблицы напрямую.

Основание и рассмотренная альтернатива: Запись Python напрямую в предметные таблицы обходит проверку версии и fencing. Валидируемая граница оставляет управление процессом в Node.

### D2

PDF: текстовый слой и OCR выбираются по странице/области. Сохраняются исходный текст и нормализованное представление, NFC и повторные пробелы не уничтожают значимые знаки. Рукописные/нечитаемые зоны сохраняют LOW_QUALITY/ABSTAIN и входят в coverage.

Основание и рассмотренная альтернатива: OCR всего документа дороже и может ухудшать текстовые страницы; чтение только текстового слоя теряет сканы. Выбор по областям сохраняет оба вида.

### D3

Система координат [0;1] — видимая область после CropBox/MediaBox/Rotate. Сохраняются transform и физическая страница отдельно от номера листа. DOCX/XML renderer детерминирован: версия, шрифты/конфигурация, structural path → rendered page/bbox.

Основание и рассмотренная альтернатива: Координаты исходного PDF без трансформаций не совпадут с viewer. Копирование bbox между форматами без отображения не проверяемо.

### D4

Ключ кеша включает file_hash и версии parser/OCR-model/renderer/нормализации и значимую конфигурацию. Кеш не содержит object-specific решений; потеря Redis не теряет исходники и долговечный результат.

Основание и рассмотренная альтернатива: Кеш только по hash вернул бы устаревший результат после смены модели. Кеш предметных решений создаёт перенос между объектами.

### D5

Timeout файла: первоначальная попытка + два повтора, затем сохранённый исход и событие для уведомлений C23. Закрытие браузера не отменяет job; ack после commit и fencing предоставляются C01.

Основание и рассмотренная альтернатива: Бесконечные повторы расходуют GPU и скрывают отказ. Надёжность общей очереди реализуется один раз в C01, а политика файла задаётся здесь.

### D6

Оценка OCR и таймингов на разрешённом validation-корпусе входит в change. Независимая hidden-приёмка и общая нагрузка остаются C24; локальная метрика не выдаётся за их прохождение.

Основание и рассмотренная альтернатива: Выбор OCR по hidden-набору исказит независимую оценку; локальный validation нужен для разработки и не заменяет C24.

### D7 — эксперимент PP-StructureV3

По запросу владельца от 18.09.2026 проверяется PP-StructureV3: предыдущий OCR
не восстановил таблицы паспорта и потерял значимый знак. Сравнение использует
те же сохранённые PNG и русский распознаватель. Структура строк/ячеек,
содержимое контрольных ячеек и время оцениваются отдельно. Исходники и полные
результаты остаются локально; в Git сохраняются команда, конфигурация и
обезличенные наблюдения. Эксперимент выполняется отдельно от рабочего
Python-сервиса; замена production-моделей требует проверки геометрии,
лимитов, артефактов и обновления fingerprint. Итог эксперимента фиксируется
в evidence.md, без заявления о прохождении C24.

### D8 — рабочий PP-StructureV3 по решению владельца

После рассмотрения метрик владелец явно запросил подключение PP-StructureV3
к приложению и запуск интерфейса для проверки. Используется проверенный
mobile detector / 1536 px, русский eslav recognizer и локальные layout/table
модели. Server detector / 3072 px исключён из рабочей конфигурации после
наблюдённого чрезмерного расхода памяти.

Адаптер сохраняет весь извлечённый OCR-текст и таблицы в контракте PAR v1.
Обратные координатные преобразования связывают ячейки с исходным PNG;
невалидная сетка не публикуется как достоверная таблица. Отбрасывание
сомнительной структуры сохраняет текст и явную причину качества. Уверенность
модели не отменяет OCR_UNVERIFIED: известная потеря значимого знака остаётся
ограничением, а не исправляется предположением. Viewer показывает обычный
текст и безопасные таблицы с доступом к оригиналу. Новые модели, зависимости
и конфигурация входят в fingerprint; запуски прежнего движка не выдаются за
результаты PP-StructureV3.

## Risks / Trade-offs

### D9 — адаптивный OCR после проверки областей

Утверждённый владельцем план находится в [adaptive-ocr-plan.md](adaptive-ocr-plan.md).
Layout работает по исходному изображению. Первый эксперимент не прошёл
условия качества; его результаты сохранены в отчёте. После ознакомления
владелец явно поручил внедрить обработку по областям, отложив повышение
качества. Это решение отменяет прежний запрет внедрения, но не объявляет
ошибки Paddle исправленными. VLM и редактор областей не добавляются.

PDF проходит layout, привязку native-текста и детекцию строк разрешённых
текстовых/табличных областей. Пригодный native-текст не распознаётся заново;
OCR получает только непокрытые строки или растровую таблицу. Graphic/unknown
сохраняются как изображение страницы с bbox и имеющиеся native-надписи.
Недостоверный класс, конфликт границ и неразмеченное содержимое дают unknown
с причиной. Это не гарантирует, что уверенно ошибочный класс table распознан
как чертёж: такое ограничение модели сохраняется и показывается пользователю.

PAR v1 получает добавочный region_schema_version=1 для нового PDF-профиля.
Области содержат исходный класс/score, метод, причины и состояние таблицы;
каждый блок связан с областью и имеет include_in_main. Полный raw/normalized
текст остаётся полным, включая исключённые из основного списка native-надписи.
Просмотрщик показывает области и объяснения пропусков, а старые артефакты
читает без выдуманной разметки. Проверки связей и маршрутизации обязательны;
отсрочка качества OCR не отменяет их.

- Плохой OCR или смешанная разметка страниц → validation по типам документов, coverage и явный abstention.
- Разные версии renderer/шрифтов → закреплённая конфигурация и проверка hash производных артефактов.
- Недоступна общая зависимость → контрактные проверки допускают подготовку, но не закрывают задачи реальной интеграции.

## Продолжение по аудиту 26.09.2026

Исходное состояние: региональный pipeline работает, но `pdf_parser.py` передаёт в table adapter смешанный native/OCR-вход; `pdf_regions.py` оставляет конфликтную область unknown, а `include_in_main` исключает её из основного текста. Диагностический отчёт `docs/OCR_QUALITY_2026-09-26.md` находится в родительской папке материалов; воспроизводимые обезличенные примеры и манифест корпуса должны войти в проверяемую поставку без зависимости от локального пути. 15/20 единиц — наблюдение одной таблицы, не оценка всего корпуса.

Выбранное продолжение: сохранять неизменяемые исходные блоки и происхождение каждого фрагмента ячейки; выбирать поддержанный текст по геометрии и исходным блокам, а конфликтующие кандидаты оставлять раздельно. Простая очистка строки после конкатенации не восстанавливает происхождение и не подходит. Восстановление структуры таблицы отдельно от качества распознавания: пустая ячейка и неустановленная связь с колонкой различаются.

Прежний запрет OCR graphic/unknown сохраняется. Отказ от структуры области с QR или подписью не удаляет её native-текст; безопасное чтение пригодных native-фрагментов по локаторам доступно ID/EXT независимо от фильтра основного viewer. Это не изменение класса области и не разрешение запускать VLM. Смена политики пересечений, расширяющая разрешённые OCR-области, требует отдельного решения и не входит в текущий ремонт.

GPU-профиль проверяется на том же локальном корпусе и закреплённых весах. Профиль содержит фактический device, версии runtime, память и fingerprint. Выбор CPU остаётся явным; незаметное переключение на внешний сервис запрещено. Критерии качества следуют ТЗ; дополнительные диагностические пороги публикуются как инженерные и не заменяют приёмку C24.

Миграция добавляет версию схемы происхождения и pipeline; старые артефакты читаются без выдуманного происхождения. Новый прогон создаёт новые артефакты, оригиналы и прежние протоколы сохраняются. Подробный порядок, входы и выходы — [execution-plan.md](execution-plan.md).

## Migration Plan

Реализация 27.09.2026: задачи 8.1–8.4 закрыты на [регрессиях и реальном CPU-прогоне](../../../docs/parsing-regressions/implementation-2026-09-27.md). Профиль `par-local-2 / paddle-regions-v2` добавляет происхождение фрагментов и `table_link`, ID/EXT используют общий отбор блоков. Артефакт остаётся schema 1 с добавочным marker происхождения. Старые данные и запечатанный стенд сохранены. Общий отчёт качества, GPU, выпуск нового Run и полный сценарий viewer остаются отдельными открытыми пунктами 8.5–8.8.

1. Согласовать схемы и владельца миграции до разработки. Добавлять только таблицы/поля своего слоя; общие таблицы изменяет владелец C01 по согласованному PR.
2. Поставить аддитивные миграции и ограниченно включить capability в разрешённой тестовой среде. Сохранить текущую авторизацию и прежние оригиналы.
3. Выполнить компонентные проверки из tasks.md на реальных зависимостях. Указать команды, версии, корпус и ссылки на отчёты в evidence.md, создаваемом при реализации.
4. При откате остановить новые операции/потребителей capability и вернуть совместимую версию приложения; не удалять исходники, аудит, принятые jobs и историю снимков. Незавершённые jobs сохраняются до совместимого возобновления.

## Acceptance boundary

Реальные файлы каждого поддерживаемого типа дают текст/структуру и корректные выделения; поворот/CropBox/нечитаемость/таймаут проверены, повторное чтение использует совместимый кеш.

Готовность design/specs/tasks означает готовность плана. Задачи получают отметку выполнения только после реализации и проверок; состояние реализации отражено в tasks.md и evidence. Совместные сценарии настоящего сравнения, протокола, финализации, 132/132 и количественные требования общего релиза остаются в C24; само разделение планов не подтверждает их выполнение.
