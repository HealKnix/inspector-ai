## Context

C23. Есть healthcheck, AuditEvent, durable outbox и integrity.service. Нет доказательства сквозных JSON-логов, централизованного поиска, всех метрик и доставки email/Telegram. Демо-показатели UI не являются источником SLI.

## Goals / Non-Goals

**Goals:** проследить одну обработку через API, очередь и Python; обнаружить отказ и доставить безопасное уведомление; измерять фактическое состояние.

**Non-Goals:** хранить полный текст документа в логах; пересоздавать аудит решений; заявлять SLA на основании статичного графика.

## Decisions

1. Единый JSON logging contract: timestamp, level, service, message, request_id, user_id; асинхронная операция сохраняет correlation/context без подмены системного события пользователем. Отдельные технические коды, отсутствие секретов/base64/полного текста; DEBUG выключен в production.
2. Prometheus собирает CPU/RAM/disk/RPS/latency/5xx/queue/sessions и ключевые стадии pipeline, Grafana отображает. Идентификаторы объектов/пользователей не становятся высококардинальными labels. ELK индексирует безопасные логи; аудит предметных решений остаётся в своей БД.
3. Retention: штатные INFO+ не менее 90 дней, события безопасности не менее года. Условия удаления и восстановление индексов проверяются управляемым временем, а не ожиданием 90 дней. Непосредственное хранение журналов действий координируется с AUD.
4. Notification consumer обрабатывает protocol.ready, исчерпание попыток, integrity и превышение порогов через существующий outbox; точное имя события сверяется с реализованным производителем. Ключ доставки включает event/канал/получателя. Повторы ограничены; ошибка остаётся наблюдаемой и доступной для разрешённого ручного повтора.
5. Адресаты и пороги конфигурируются до включения отправки. Реальная отправка тестируется только в согласованный тестовый канал. Недоступный Интернет официального офлайн-стенда не блокирует анализ: локальная ошибка доставки видна, результат обработки сохранён.

## Этапы и зависимости

1. JSON/correlation и словарь метрик по текущему ядру.
2. Prometheus/Grafana и ELK с retention.
3. Уведомления и ошибки доставки на разрешённых получателях.
4. Подключение остальных modules, реальные показатели UI.
5. Сквозная трассировка, аварийные сценарии и проверка отсутствия утечки.

OBS начинается с текущей платформы и расширяется по мере появления capabilities. Законченный сбор всех метрик проверяется в ACC; OBS не требует завершённого ACC до начала.

## Risks / Trade-offs

- [Документы в stack trace] → sanitization на границе, тесты чувствительных входов.
- [Лавина алертов] → группировка/подавление повторов и явные окна восстановления.
- [Не доставлен алерт о сломанном канале] → локальная метрика и доступная оператору история, независимый канал по конфигурации.

## Migration Plan

Сначала сбор без отправок, затем dashboards/retention, затем тестовые и рабочие получатели. Формат новых логов версионируется; старые индексные данные не переписываются. Отключение канала не удаляет события и результаты обработки.
