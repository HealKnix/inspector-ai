## Context

См. [proposal.md](proposal.md) для мотивации и [spec](specs/document-identification/spec.md) для поведения. В существующем коде есть auth, роли, Prisma и контейнер RabbitMQ; это не доказательство готовности C01. Новые предметные сущности отсутствуют. Изменения сохраняют /api/auth/*, текущий React-клиент и Bun workspaces. Источники — [PDF и приложения](../../../docs/requirements/SOURCES.md).

До завершения: [PAR](../add-document-parsing/proposal.md); общие зависимости C01, C05-C18 в [SHARED_BACKLOG.md](../../SHARED_BACKLOG.md). Интерфейсы можно разрабатывать по согласованным контрактам до готовности зависимостей, но интеграцию закрывают на реальных компонентах.

## Goals / Non-Goals

**Goals:** определить границы данных, взаимодействия и доказательства результата capability document-identification. Document, Revision, FileDocumentPart, FieldCandidate и Clarification принадлежат ID. Справочник значений и сопоставление с Матрицей версионируются с C05/C18. Событие уточнения содержит идентификаторы и версии, а не полный текст.

**Non-Goals:** File/storage принадлежат ING, Page/RenderedArtifact — PAR. Здесь не реализуются извлечение всех параметров, полнота объекта или верификация нарушений.

## Decisions

[Общий контракт](../../CONTRACTS.md) фиксирует владельцев, поля, версии и порядок интеграции. Технические решения ниже — проект реализации; подтверждённые роли и бизнес-статусы берутся из PDF.

### D1

Основная модель: File неизменяем; Document задаёт предметную идентичность; Revision задаёт применимость/утверждение; FileDocumentPart связывает файл и диапазон/структурную часть. Создание этих таблиц не дублирует File из ING.

Основание и рассмотренная альтернатива: Модель один файл = один документ теряет составные PDF и два представления акта. Разделение сохраняет идентичность при смене формата.

### D2

Собственные поля XML определяются полным путём и схемой. Титул/основная надпись/таблица изменений сильнее имени файла. Марка РД, вид ИД и раздел Матрицы — отдельные справочники, ВК не разрешается в ИОС2/ИОС3 без контекста.

Основание и рассмотренная альтернатива: Поиск первого похожего кода в XML смешивает акт и приложения; имя файла слабее собственных реквизитов.

### D3

Для каждого поля raw/normalized, locator, метод/версия, кандидаты/confidence при наличии и конфликт. Автопринятие определяется validation-политикой по полю; Exact Match 0,90 не служит порогом confidence.

Основание и рассмотренная альтернатива: Глобальный порог confidence не эквивалентен качеству Exact Match; политика по полям допускает частичное надёжное принятие.

### D4

Последняя применимая утверждённая редакция выбирается по документу/области/времени работ и доказательствам замены. Изменение отдельных листов сохраняет действие незаменённых. Approval хранит наблюдаемое значение и проверенную интерпретацию, неизвестность не превращается в утверждение.

Основание и рассмотренная альтернатива: Максимальный номер или время загрузки не доказывают актуальность и не учитывают частичную замену листов.

### D5

PDF/XML одного акта объединяются только при совпадении реквизитов/области и отсутствии содержательного конфликта. Шифр workDocumentationSectionCode в акте №52 является ссылкой на РД, а не собственным шифром акта.

Основание и рассмотренная альтернатива: Объединение по одному номеру или имени может смешать разные акты и их приложения. Совпадение существенных реквизитов и области сохраняет предметную идентичность.

### D6

Уточнение — отдельная immutable decision/version с автором из сессии, основанием и optimistic concurrency. Новая версия публикует событие для INC; старый машинный результат не переписывается. Визуальная подпись не является криптографическим подтверждением.

Основание и рассмотренная альтернатива: Перезапись машинного значения лишает аудит основания; отдельное версионированное решение сохраняет его и позволяет обнаружить конфликт. Визуальное распознавание подписи не проверяет электронную подпись.

## Risks / Trade-offs

- Неполные реквизиты и несколько редакций → принятие по полям, версии решений, спорные случаи без выдуманных значений.
- Скрытая утечка через общие представления → корпус разделяется по объектам/редакциям вместе с C24.
- Недоступна общая зависимость → контрактные проверки допускают подготовку, но не закрывают задачи реальной интеграции.

## Migration Plan

1. Согласовать схемы и владельца миграции до разработки. Добавлять только таблицы/поля своего слоя; общие таблицы изменяет владелец C01 по согласованному PR.
2. Поставить аддитивные миграции и ограниченно включить capability в разрешённой тестовой среде. Сохранить текущую авторизацию и прежние оригиналы.
3. Выполнить компонентные проверки из tasks.md на реальных зависимостях. Указать команды, версии, корпус и ссылки на отчёты в evidence.md, создаваемом при реализации.
4. При откате остановить новые операции/потребителей capability и вернуть совместимую версию приложения; не удалять исходники, аудит, принятые jobs и историю снимков. Незавершённые jobs сохраняются до совместимого возобновления.

## Acceptance boundary

На разрешённых документах и синтетических конфликтах корректно различены собственные/ссылочные реквизиты, редакции и части; инспектор видит доказательства и вносит конкурентно защищённое уточнение. Полная комплектность не требуется для приёмки ID.

Готовность design/specs/tasks означает готовность плана. Все задачи остаются открытыми до реализации и проверок. Совместные сценарии настоящего сравнения, протокола, финализации, 132/132 и количественные требования общего релиза остаются в C24; никаких новых отметок выполнения при разделении не ставится.
