# Снимки, дозагрузка и инкрементальность

Владелец: P1 backend + P2 процесс. Нумерация локальная; [SRC-x.y] указывает задачу исходного объединённого change, а не её текущий статус. [Карта переноса](../../SPLIT_MAP.md), [общие обязательства](../../SHARED_BACKLOG.md), [контракты](../../CONTRACTS.md).

Все задачи открыты: перенос и готовность планирования не означают реализацию. Backend/frontend/ML выполняются в рамках одного функционального change; завершение определяется его спецификацией.

## 1. Контракты и предпосылки

- [ ] 1.1 Проверить зависимости COM и C01; закрепить версии входных/выходных контрактов из CONTRACTS.md. Проверка: у каждой используемой сущности и миграции есть один владелец, отсутствующая зависимость явно отмечена.
- [ ] 1.2 [SRC-1.2] Описать process/results API с текущим Run, двумя hash снимков, доступными действиями и техническими исходами отдельно от business status. Проверка: schema явно различает неизвестное, старый результат и ещё не созданный протокол.
- [ ] 1.3 [SRC-1.6] Зафиксировать версии контрактов обмена с потребителями сравнения, протокола, финализации и внешнего источника; проверка: перечислены реальные поля/владельцы и отсутствующие реализации, ни одна заглушка не помечена интеграцией по ТЗ.
- [ ] 1.4 Зафиксировать согласованную таблицу переходов LC-08 с владельцем процесса и предметным владельцем: отказ, частичный результат, уточнение, повтор и продолжение. Проверка: каждое событие имеет предусловия/права/следующее состояние, соблюдает PDF и даёт проверяемый путь восстановления без выдуманного enum.

## 2. Реализация capability

- [ ] 2.1 [SRC-2.7] Подключить capability document-processing-lifecycle к общим проверкам доступа/аудиту C01 и безопасным событиям/метрикам C23. Проверка: изменение оставляет автора/версию/корреляцию, запрос чужого объекта отклонён, содержимое и секреты отсутствуют в логах; транспорт уведомлений не реализован повторно.
- [ ] 2.2 [SRC-8.1] Реализовать стабильный process_id, новые Run и пару InputManifest/ResolvedInputSnapshot. Проверка: OCR не меняет исходный manifest, перестановка массива не меняет hash, содержательное изменение создаёт новый hash и сохраняет старую пару.
- [ ] 2.3 [SRC-8.2] Реализовать граф зависимостей документов/редакций/решений/перечня от параметров; проверка: новая редакция затрагивает все зависимые старые сравнения, а не только новые файлы.
- [ ] 2.4 [SRC-8.3] Реализовать пересчёт затронутых групп и перенос только доказанно неизменных извлечений; проверка: дозагрузка схемы обновляет связанные результаты без безусловного полного прогона, история сохранена.
- [ ] 2.5 [SRC-8.4] Реализовать серверную матрицу действий PENDING/PARSING/READY/VERIFYING/COMPLETED/FINALIZED; проверка: табличные HTTP-тесты подтверждают все сочетания разрешений, PARSING и FINALIZED запрещают дозагрузку.
- [ ] 2.6 [SRC-8.5] Реализовать общий контроль версии/блокировку для загрузки, уточнений, публикации результатов и финализации; проверка: конкурентные сценарии не дают финализировать старый состав и затем приписать ему новый.
- [ ] 2.7 [SRC-8.6] Реализовать проверку версий и порт передачи входов/фиксации протокола для C10. Проверка: реальная БД отвергает неправильную пару hash и READY без сохранённого протокола; контрактная проверка порта не закрывает интеграцию C24 с настоящим потребителем.
- [ ] 2.8 [SRC-8.7] Реализовать входной порт внешнего адаптера и событие новых документов после FINALIZED. Проверка: обычные проверки приёма/доступа сохранены, финализированная проверка не меняется; реальный обмен C20 и доставка C23 остаются отдельными обязанностями.
- [ ] 2.9 Реализовать согласованный путь восстановления LC-08 и технические исходы Run/Job. Проверка: исчерпание попыток и требование уточнения не создают ложного READY и не оставляют пользователя без разрешённого действия.

## 3. Интерфейс

- [ ] 3.1 [SRC-9.1] Расширить существующий экран процесса актуальностью Run, разрешёнными действиями и путём восстановления. Проверка: перезагрузка не выдаёт старый протокол за новый, клиент соблюдает серверные разрешения.

## 4. Проверки и доказательства готовности

- [ ] 4.1 [SRC-11.9] Проверить конкурентную дозагрузку, уточнение, публикацию и порт финализации на реальной БД, а также поздний worker. Проверка: невозможна смена финализированного состава; совместный сценарий с настоящим C12 остаётся открытым в C24.
- [ ] 4.2 Проверить самостоятельный результат на реальных зависимостях: На реальной БД доказаны неизменяемость снимков, охват графа, повторная доставка, stale-result rejection и конкурентный transaction port. Отдельно отмечены ещё не выполненные совместные испытания C10/C12/C20 в C24. Проверка: evidence.md содержит команды, версии, результаты и ограничения; mocks не используются как доказательство закрытия реальной интеграции.
- [ ] 4.3 Выполнить применимые проверки существующего репозитория для изменённых частей (тесты, typecheck, build) и проверку OpenSpec. Проверка: результаты записаны в evidence.md, auth не сломан, отложенные обязательства C24 перечислены без отметки выполнения.

## 5. Безопасное внедрение выборочного исполнения

- [ ] 5.1 Добавить теневой расчёт плана графа и дифференциальное сравнение с полным запуском для 2.3–2.4. Проверка: новая редакция, ранее отсутствующий источник, уточнение, новый перечень и смена правила дают одинаковые содержательные результаты и основания решений.
- [ ] 5.2 Подготовить миграцию для прежних snapshots без графа: версия графа, причина консервативного пересчёта, совместимое чтение истории и отключение selective executor. Проверка: старый протокол неизменен, неизвестные зависимости не дают ложного reuse, откат не теряет принятые jobs.
- [ ] 5.3 Измерить инкрементальный сценарий относительно полного на фиксированном корпусе. Проверка: отчёт содержит количество пересчитанных/переиспользованных групп, причины, PAR отдельно, версии, оборудование и время; вывод о производительности соответствует реальным замерам.
