## Найденные и исправленные дефекты

1. `findAnchorHits` пропускал все `include_in_main=false` блоки. Контракт
   парсера использует флаг и для OCR-аудит-копий (пропускать — иначе дубли), и
   для skipped-регионов без замены (единственное доказательство). Фикс:
   пропускаем только при method ∈ {ocr, table_ocr, hybrid}; skipped — ищем.
   Регрессионный тест в `extraction-engine.test.ts` (16/16).
2. `approve` ставил `deprecated` старой версии, не очищая `approved_at` →
   нарушение `rule_versions_approval_check` (500). Фикс: deprecation обнуляет
   `approvedBy/approvedAt`; история утверждений остаётся в `audit_events`.
3. Dockerfile backend не поставлял `scripts/` и `matrix-132.xlsx` —
   `matrix:import` в контейнере не находил файлы. Добавлены COPY-строки.

## LLM-драфт (живой контур, OpenRouter)

`POST rows/P004/draft-llm` на артефакте ПЗ-вырезки:

- Модель `qwen/qwen3.8-27b` вернула regex-план за ~3.4 с; все предложенные
  якоря подтверждены по реальным блокам (`missing_anchors: []`),
  черновик v1 создан со статусом `draft`.
- Dry-run черновика → честный `ambiguous`: LLM-паттерн
  `строительный объем[^0-9]*([0-9][0-9\s\.,]*)` захватывал «3» из «м3»
  и соседние значения («1.», «3 73 080,00 5.1»). Движок не выбрал
  произвольное значение — все альтернативы сохранены с локаторами.
- Инспекторская итерация: ручной draft v2 с уточнённым паттерном
  (`в том числе:?\s*м?3?` перед группой) → dry-run `extracted`
  `73 080,00 m3` (стр. 7, p7-b63) → approve → воркер переизвлёк P004
  автоматически (ruleset-fingerprint сменился).
- LLM-черновик v1 так и остался `draft` — неутверждённые планы не
  исполняются. Цикл «LLM предлагает → dry-run проверяет → человек
  утверждает» работает как задумано.

Дефекты, найденные на живом LLM-вызове:

1. Reasoning-модель при `max_tokens=2000` обрезалась `finish_reason=length`
   с пустым content → `extraction_llm_invalid_result`. Фикс:
   `max_tokens=12000` + `reasoning.effort="low"` (провайдеры без опции её
   игнорируют).
2. Модель возвращала `"enum": []` для отсутствующих опциональных списков →
   валидатор отвергал план. Фикс: пустой массив опционального поля
   эквивалентен отсутствию (required-поля по-прежнему строгие).
3. Nginx `/api/` без `proxy_read_timeout` отдавал 504 за ~60 с при
   reasoning-ответах; backend-таймаут 60 с тоже был коротким. Фикс:
   `proxy_read_timeout 300s`, `CLASSIFICATION_LLM_TIMEOUT_MS` 240000
   (env/compose defaults).

## Массовый прогон матрицы (132 параметра), объект «Новослободская»

Скрипт `backend/scripts/batch-rule-drafting.mjs`: для каждой строки матрицы
`draft-llm` → черновик с comparison-спекой из текста триггера → dry-run по
артефактам объекта → авто-approve при `extracted > 0`. Re-login при 401,
backoff при 429, per-file fallback-драфтинг. Отчёты:
`.test-output/batch-pass{1..3}.json`, `batch-backfill2.json`.

Корпус: 6 файлов одним пакетом в один процесс
(`backend/scripts/upload-batch.mjs`, объект
`d58aab2c-99cf-4e95-b0f3-5b00747b2d8e`, процесс
`7b9bde52-170c-42c5-8b0c-aacd64d92138`): ПЗ, ПЗУ, АР (ПД×3), КЖ1.1.1, СВГ
(РД×2), АОСР (ИД), 131 стр. Парсинг/классификация succeeded по всем;
артефакты content-addressed — повторные загрузки тех же sha256
переиспользуют их без повторного OCR.

Итоги трёх проходов + backfill:

- approved-правил с планом+comparison: 12 из 132
  (P001, P002, P003, P007, P009, P015, P019, P022, P023, P056, P058 —
  у P004 спеку не удалось подтвердить dry-run'ом, правило осталось без
  comparison);
- `dry_run_no_extraction`: ~15 драфтов созданы, но не извлекли на корпусе;
- `draft_failed` (~105): подавляющее большинство — честный маркер
  «не найдено»: источники параметров (разделы ВК/ОВ/ЭС/ПП/ПОС, журналы,
  акты ИД) отсутствуют в корпусе. Это ограничение корпуса, а не движка.

Найденные и исправленные дефекты прогона:

1. `draftWithLlm` собирал окна `flatMap(...).slice(0,16)` — при
   сортировке артефактов по имени первый «болтливый» файл вытеснял окна
   остальных. Фикс: round-robin по артефактам + ранжирование окон по
   дословному имени параметра (`draftWindows`, юнит-тест
   `matrix-admin.draft-windows.test.ts`).
2. `extraction_llm_invalid_plan` уходил HTTP 500 — теперь 422 с
   логированием невалидного плана (модельный вывод, не текст документа).
3. Approved-правила без comparison давали вердикт `no_comparison` —
   backfill-путь в скрипте довешивает спеку новой версией.
4. Каждый файл, загруженный отдельным запросом, образует свой процесс —
   evidence-группы не видят членов других файлов. Для сверки файлы
   загружаются одним пакетом (см. `upload-batch.mjs`).

Вердикты сводного процесса (12 групп, по 6 членов — PD expected /
RD·ID actual):

- P009 `match`: отметка 159,95 совпала ПД↔РД (4 extracted-члена);
- P022 `discrepancy`: ПД «II» (стр. 12, p12-b72, quote+bbox) vs РД «l»
  (КЖ) → находка `CANDIDATE`;
- P002 `expected_ambiguous`: ПЗ и ПЗУ несут разные площади (13999,7 vs …) →
  `CLARIFICATION_REQUIRED`;
- `actual_missing` (P001, P003, P007, P023): значение есть в ПД, в РД/ИД
  нет — честный исход, не нарушение;
- `expected_missing` (P015, P019, P056, P058): значение только в РД/ИД.

Протокол (`POST /v1/objects/:id/protocol/generate`, v1): 132 находки —
`CANDIDATE` 1 (P022), `NEGATIVE_VERIFIED` 1 (P009), `CLARIFICATION_REQUIRED`
1 (P002), `MISSING_EVIDENCE` 129. Ни одно отсутствие/неоднозначность не
стало находкой-нарушением — семантика гейта соблюдена.

Ограничения прогона: авто-approve по «extracted>0» — демонстрационная
политика, в production нужен ревизионный гейт; comparison из текста
триггера — эвристика, не утверждённое доменное правило; геометрические
параметры (GEO) текстовым движком не покрываются.
