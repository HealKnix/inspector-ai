## Context

См. [proposal.md](proposal.md) для мотивации и [spec](specs/document-evidence-extraction/spec.md) для поведения. В существующем коде есть auth, роли, Prisma и контейнер RabbitMQ; это не доказательство готовности C01. Новые предметные сущности отсутствуют. Изменения сохраняют /api/auth/*, текущий React-клиент и Bun workspaces. Источники — [PDF и приложения](../../../docs/requirements/SOURCES.md).

До завершения: [ID](../add-document-identification/proposal.md); общие зависимости C05-C18 в [SHARED_BACKLOG.md](../../SHARED_BACKLOG.md). Интерфейсы можно разрабатывать по согласованным контрактам до готовности зависимостей, но интеграцию закрывают на реальных компонентах.

## Goals / Non-Goals

**Goals:** определить границы данных, взаимодействия и доказательства результата capability document-evidence-extraction. Extraction, Evidence и EvidenceGroup имеют общую схему с GEO. EXT владеет сборкой доказательной группы и reader RuleVersion; C05/C18 владеет Params/RuleVersion и их утверждением. Независимый JSON-контракт позволяет GEO готовить алгоритм до завершения EXT.

**Non-Goals:** Импорт, формализация и утверждение всех 132 конфигураций принадлежат C05/C18; сравнение — C06/C07, геометрические измерения — GEO. Полное покрытие 132 подтверждается в C18/C24 в том же релизе.

## Decisions

[Общий контракт](../../CONTRACTS.md) фиксирует владельцев, поля, версии и порядок интеграции. Технические решения ниже — проект реализации; подтверждённые роли и бизнес-статусы берутся из PDF.

### D1

Params/RuleVersion поступают из C05/C18: raw-строка, код, тип, единица, применимость, AND/OR источники и версии. Неоднозначный текст нельзя активировать; точка с запятой не задаёт оператор.

Основание и рассмотренная альтернатива: Исполнение произвольного текста Матрицы породило бы выдуманные правила. Конфигурацию утверждает отдельный владелец C05/C18.

### D2

Текстовые правила используют regex и семантические якоря с Sentence-BERT all-MiniLM-L6-v2 либо совместимым аналогом из §9.1. Правила проверяются на утверждённых примерах для каждого поддержанного типа.

Основание и рассмотренная альтернатива: Жёсткие шаблоны без семантических якорей не покрывают переформулировки; выбранный механизм соответствует §9.1, выбор совместимого аналога фиксируется бенчмарком.

### D3

Значение сохраняет raw/normalized, единицу, область работ, evidence locator, stage/code/revision/approval и версии. Геометрия — потребительский контракт GEO; EXT не реализует распознавание линий второй раз.

Основание и рассмотренная альтернатива: Нормализованное число без единицы/области нельзя надёжно сравнить; общий геометрический контракт исключает две несовместимые реализации CV.

### D4

EvidenceGroup объединяет сопоставляемые источники по объекту/правилу/области. Expected/actual назначаются при создании группы из проверенной семантики источников; это не вывод о нарушении.

Основание и рассмотренная альтернатива: Роли источников задаёт правило, а нарушение устанавливает отдельное сравнение. Их смешение превращает извлечение в ложный finding.

### D5

Выход содержит схему для Checks/Evidence_Fragments, input_manifest_hash и resolved_input_hash. Отсутствующий/неподдержанный план виден явно и не создаёт NEGATIVE_VERIFIED/CANDIDATE.

Основание и рассмотренная альтернатива: Результат без пары снимков невозможно безопасно перенести при дозагрузке. Пропуск правила не равен отрицательному сравнению.

## Risks / Trade-offs

- Движок готов раньше 132 конфигураций → отдельный полный реестр C18, общий выпуск не объявляется готовым.
- Ошибочные единицы или область → типизированный контракт и реальные примеры каждого поддержанного оператора.
- Недоступна общая зависимость → контрактные проверки допускают подготовку, но не закрывают задачи реальной интеграции.

## Migration Plan

1. Согласовать схемы и владельца миграции до разработки. Добавлять только таблицы/поля своего слоя; общие таблицы изменяет владелец C01 по согласованному PR.
2. Поставить аддитивные миграции и ограниченно включить capability в разрешённой тестовой среде. Сохранить текущую авторизацию и прежние оригиналы.
3. Выполнить компонентные проверки из tasks.md на реальных зависимостях. Указать команды, версии, корпус и ссылки на отчёты в evidence.md, создаваемом при реализации.
4. При откате остановить новые операции/потребителей capability и вернуть совместимую версию приложения; не удалять исходники, аудит, принятые jobs и историю снимков. Незавершённые jobs сохраняются до совместимого возобновления.

## Срез реализации от 19.09.2026

По решению владельца первый работающий срез включает минимальную часть зависимости C05/C18 в этой же ветке (прецедент: необходимая часть C01 реализована в ветке ING): импорт 132 строк каталога из `parameter_catalog_132.jsonl` с фиксацией SHA-256 источника и origin-хеша `matrix-132.xlsx` из SOURCES.md, таблицы `RuleVersion`/`Matrix*` и простейшее администрирование карточек правил. Полный реестр 132/132, подготовка планов всех разделов и отдельный capability `matrix-catalog` остаются в SHARED_BACKLOG.

Границы среза, которые не закрывают требования целиком:

- Происхождение на уровне File + стадия из классификации; Document/Revision и цепочки редакций открыты в ID (EX-04 в части редакций не закрыт).
- Семантические якоря v1 — словари синонимов внутри карточки правила; Sentence-BERT-совместимые эмбеддинги — отдельный spike.
- Типы планов v1 — `table_lookup`, `regex`, `cascade`; геометрические планы и адаптер C08 не реализуются.
- Извлечения и группы показываются инспектору; сравнение значений и вердикты принадлежат C06 и в срез не входят.
- Неутверждённый или неподдержанный план возвращает явную невозможность, а не отрицательный результат; LLM-черновики карточек не исполняются до утверждения администратором.

## Acceptance boundary

Движок исполняет утверждённые текстовые/табличные планы, отклоняет неподдержанный тип и возвращает проверяемые факты с версиями. Отдельный реестр C18 сохраняет обязательство всех 132 строк; отсутствие реального модуля сравнения не блокирует проверку самого извлечения.

Готовность design/specs/tasks означает готовность плана. Все задачи остаются открытыми до реализации и проверок. Совместные сценарии настоящего сравнения, протокола, финализации, 132/132 и количественные требования общего релиза остаются в C24; никаких новых отметок выполнения при разделении не ставится.
