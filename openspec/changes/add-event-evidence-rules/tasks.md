## 1. Этап A — контракты источников и допуска

Вход: ранний контракт add-reviewed-matrix-release и существующие Object/Run/ID/CMP. Предметная приёмка конкретной строки зависит от разрешённого источника; синтетическая механика и независимые строки не останавливаются из-за одного недоступного журнала.

- [ ] 1.1 Составить четыре паспорта P098–P101 с точными source/trigger из Матрицы и перечнем нужных полей/оснований; проверка: нет придуманного внешнего endpoint, срока действия или нормативного допуска.
- [ ] 1.2 Для предоставленных источников зафиксировать формат, версию, идентификаторы, часовой пояс, границы полноты и правила исправления; проверка: каждый вывод о возможности отрицательного ответа подтверждён документом/примером источника, неизвестность записана адресно.
- [ ] 1.3 Подготовить внутреннюю схему immutable snapshot/event/provenance и синтетический набор для import/time/replay; проверка: контракт не выдан за API оператора, версии/hashes/автор источника проверяются runtime-валидатором.

## 2. Этап B — офлайн-импорт и временные данные

- [ ] 2.1 Реализовать аддитивное хранение snapshots/events и связи с разрешённым объектом; проверка: PG запрещает чужие связи, исходные записи и hashes не меняются при нормализации.
- [ ] 2.2 Реализовать ограниченный локальный импорт предоставленного формата через private storage/авторизацию; проверка: неверная структура, превышение лимита и чужой объект отклонены, полный журнал не попадает в технические логи.
- [ ] 2.3 Добавить идемпотентность и версии исправлений/отмен; проверка: повтор файла не удваивает события, изменённое содержание не перезаписывает прошлую запись.
- [ ] 2.4 Реализовать нормализацию времён и поиск состояния на дату события; проверка: часовые пояса, границы интервала, поздняя доставка и неизвестная зона имеют детерминированные ожидаемые исходы без назначенного по умолчанию срока.
- [ ] 2.5 Реализовать связывание объект/ТС/рейс/место только по подтверждённым идентификаторам; проверка: два рейса одной машины, одинаковые названия полигонов и неоднозначная связь не объединяются произвольно.

## 3. Этап C — четыре предметных правила

- [ ] 3.1 Реализовать P098 по разрешению на дату начала работ в подтверждённом контексте; проверка: действующее/неприменимое основание и неполный реестр дают ожидаемые различимые исходы с локаторами.
- [ ] 3.2 Реализовать P099 по оснащению ГЛОНАСС/регистрации РНИС для рейса; проверка: отсутствие телеметрии не приравнивается отсутствию трекера, версии регистрационных данных учитываются во времени.
- [ ] 3.3 Реализовать P100 по конкретному выезду и связанному QR КПТС; проверка: QR другого рейса не засчитывается, неопределённое допустимое время задержки блокирует только соответствующий временной вывод.
- [ ] 3.4 Реализовать P101 по месту/времени выгрузки, ТРПО и реестровому основанию; проверка: изменение лицензии/перечня после рейса не меняет историческую применимость, неизвестная идентичность полигона остаётся unknown.
- [ ] 3.5 Прогнать все четыре правила через gate C18 с approved regression-отчётами; проверка: частичная выгрузка, отмена, конфликт и отсутствующий источник не дают ложного match/discrepancy, synthetic-only не закрывает предметную приёмку.

## 4. Этап D — общий pipeline и доказательства

- [ ] 4.1 Подключить событийные исходы к EvidenceGroup/протоколу с hashes/версиями/контекстом; проверка: одна контрольная точка принадлежит своему рейсу/месту, отсутствие события не теряет причину недостаточности.
- [ ] 4.2 Передать зависимости источник/запись → контрольная точка в INC и проверить новый Run при исправлении; проверка: late worker не публикует старый ответ, финализированный протокол не изменяется, допустимый более широкий пересчёт обозначен.
- [ ] 4.3 Добавить чтение событийных доказательств в существующую карточку инспектора; проверка: доступны исходная запись, состояние на дату и причина вывода, чужая запись недоступна через прямой API.

## 5. Этап E — реальная приёмка и поставка

- [ ] 5.1 Выполнить предметную проверку P098–P101 на разрешённых реальных журналах отдельно по каждому источнику; проверка: hashes/полнота/ожидаемые выводы утверждены, отсутствующие источники остаются конкретными незакрытыми строками.
- [ ] 5.2 Воспроизвести import → comparison → protocol на чистом стенде без сети и после повторного импорта; проверка: результаты и provenance совпали, повтор не создал дополнительные события/находки.
- [ ] 5.3 Пройти unit/integration/typecheck/build и OpenSpec strict, передать отчёты и версии C18/C24; проверка: evidence разделяет инфраструктурную готовность, реальную предметную приёмку и оставшиеся договорённости источников.
