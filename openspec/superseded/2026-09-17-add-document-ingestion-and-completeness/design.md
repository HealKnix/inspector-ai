## Goals / Non-Goals

**Goals:**

- Построить работающий вертикальный сценарий от исходных байтов до реестра актуальных документов, извлечений и результата комплектности; обеспечить весь §9.1, а не только загрузку и название раздела.
- Отделить техническое завершение задания от доменных статусов процесса и протокола.
- Дать модулю сравнения воспроизводимый контракт с доказательствами; выполнить совместные проверки до заявления полного соответствия.

**Non-Goals:**

- Не реализовывать остальные самостоятельные модули всего ТЗ внутри загрузчика. Полное соответствие сервиса остаётся межмодульной приёмкой.
- Не использовать содержимое документов как инструкции для моделей или приложения. Не исполнять макросы, вложенный код и внешние ссылки XML/DOCX.
- Не включать обязательный внешний CSV/JSON-манифест, ZIP/DWG/SIG в публичные входные форматы: §9.1 перечисляет PDF/DOCX/XML. Внутренний снимок входов обязателен и создаётся системой.

## Decisions

### D1. Граница модулей и обработка

Добавить NestJS-модули `objects`, `documents`, `processes` и `audit` по мере появления их сценариев. Повторно использовать существующие PrismaService, JwtAuthGuard, RolesGuard и механизм DTO-валидации; добавить проверку доступа к объекту. Роль без доступа к объекту недостаточна.

В `backend/src/infrastructure` разместить адаптеры storage, rabbitmq, antivirus и Redis. Node worker запускается отдельным процессом из того же backend-workspace и владеет заданиями/транзакциями. Python ≥3.11 размещается в `backend/ml` и запускается отдельным контейнером для OCR/NLP/CV с внутренним REST-контрактом. Это требует другого runtime, но не нового frontend/backend-workspace. Python не пишет непосредственно предметные таблицы; Node валидирует его ответ и сохраняет результат транзакционно.

```text
React / API client --> Nest upload --> quarantine / antivirus --> originals
                            |
                            v
                     PostgreSQL + Outbox
                            |
                            v
                       RabbitMQ --> Node worker --> Python OCR/NLP/CV
                                         |                 |
                                         v                 v
                                    PostgreSQL          Redis cache
                                         |
                                  Pull API / comparison
```

Альтернативы: тяжёлый анализ внутри HTTP-запроса нарушает Pull и связывает жизнь загрузки с OCR; отдельные микросервисы на каждый предметный модуль усложняют начальный репозиторий. Выбран модульный backend с отдельными runtime-процессами.

### D2. HTTP и транспорт оригиналов

Сохранить `/api/auth/*`. Новые контроллеры используют путь `v1/...` при существующем глобальном `/api`. Предлагаемый контракт change:

| Операция | Контракт |
|---|---|
| Приём | `POST /api/v1/documents/upload`: `object_id`, необязательный `process_id` для дозагрузки, `client_upload_id`, массив файлов с `client_file_id`, `original_name`, `content_base64` |
| Принятие | HTTP 202, `process_id`, идентификатор запуска и индивидуальные результаты приёма; возврат только после сохранения оригиналов и транзакции регистрации |
| Мониторинг | `GET /api/v1/processes/{process_id}`: документированный статус процесса, текущий запуск/снимок, доступные действия, технический прогресс, ошибки и комплектность |
| Реестр и результат | `GET /api/v1/processes/{process_id}/documents` и `/results`: документы, части, редакции, метаданные и доступные извлечения с явным контекстом запуска |
| Уточнение | `POST /api/v1/documents/{document_id}/clarifications`: уточняемые поля, версия исходной карточки и основание; автор берётся из сессии |
| Ожидаемый состав | Чтение и подтверждение версионированного состава в контексте процесса; отдельная операция от уточнения карточки документа |
| Оригинал | Авторизованная выдача оригинала как JSON с base64 в этом контракте; изображения/представления для viewer получают отдельный явно описанный контракт, без публичного доступа к storage |

Только upload-path и возвращаемый `process_id` заданы PDF; остальные пути/поля — предлагаемый контракт реализации. Полный набор схем, ошибок, пагинации и служебных полей фиксируется в OpenAPI до разработки клиента; произвольные строковые доменные статусы не добавляются.

JSON/base64 выбран для буквального выполнения §1.3. Multipart и прямая загрузка в объектное хранилище удобнее, но потребовали бы исключения из требования «все запросы и ответы JSON»; этот change такого исключения не вводит. Цена base64 — примерно 4/3 исходного объёма. Потоковое чтение/декодирование и ограниченная временная область обязательны; не создавать одновременно целые base64-строку и буфер пакета в памяти. Общий body-parser приложения не должен поглощать upload-запрос раньше специализированной обработки. Остальные JSON-маршруты сохраняют небольшие лимиты.

В контракте 1 МБ = 1 000 000 байт: пределы 50 000 000 на файл и 200 000 000 на сумму исходных файлов. Сумма включает все отправленные файлы, в том числе индивидуально отклоняемые. Лимит wire-body учитывает base64 и ограниченные метаданные; проверка сервером исходных байтов остаётся обязательной. Размер клиентского поля не является доказательством размера. Некорректный JSON/обрыв отклоняет незавершённый пакет. Превышение суммы отклоняет пакет целиком; прочие индивидуальные ошибки не запрещают принять корректные файлы. Если не принят ни один файл, успешный `process_id` не создаётся.

Предлагаемые классы ответов: 400 для неверной схемы, 401/403 для доступа, 409 для конфликта состояния/версии/повторного ключа, 413 для превышения размера всего пакета, 422 при отсутствии допустимых файлов. При частичном приёме — 202 с отдельными результатами, без сообщения «всё принято».

`client_upload_id` обеспечивает повтор операции в области пользователя, объекта и проверки. Повтор с тем же содержимым возвращает прежний результат, с другим — конфликт. Уникальность закрепляется БД; хеш содержимого вычисляется сервером. Срок хранения ключа — не меньше срока существования связанного процесса. Для нового процесса потеря первого ответа не должна создавать второй процесс.

Настроить лимиты/буферизацию/таймауты Nginx, upload-route и API-клиента согласованно. Таймаут передачи отделить от коротких polling-запросов; увеличить его под документированное время загрузки. Возобновление по частям не является обязательным поведением этого change.

### D3. Приём, сканирование и хранение

Принять байты в изолированную зашифрованную временную область, одновременно считать размер и SHA-256. Проверить антивирусом до постоянного сохранения и разбора. Затем проверить фактическую структуру PDF/DOCX/XML в ограниченном окружении и атомарно опубликовать неизменяемый оригинал в storage. DOCX распаковывается как внутренний контейнер с ограничением объёма/вложенности; внешние сущности XML, внешние загрузки, макросы и исполняемые вложения отключены.

Технические ключи хранения формирует сервер, пользовательское имя не используется как путь. Начальный адаптер — закрытый постоянный volume с шифрованием средствами среды; контракт storage допускает замену на объектное хранилище без изменения предметной модели. Хеш сам по себе не предоставляет доступ и не служит глобальной пользовательской ссылкой.

После публикации оригиналов транзакция БД создаёт принятый реестр, запуск и outbox. При сбое транзакции оригинал не включён во входы; безопасный сборщик удаляет только неподтверждённые временные/осиротевшие объекты после проверки ссылок. Транзакции PostgreSQL и storage не объявляются общей атомарной транзакцией. Неуспех сканера не допускает обхода проверки.

Представление Files для §9.1/§10 получается из File + FileDocumentPart + DocumentRevision и включает все требуемые метаданные. Для составного файла ответ содержит несколько частей, а не произвольно одну общую стадию. Метаданные не дублируются как несколько независимо изменяемых истин. Исторический запуск хранит их выбранный снимок.

Неизвестные поля nullable до распознавания/уточнения. `approval_status` хранит наблюдаемое значение и основание; новое перечисление вроде DRAFT/APPROVED не выдаётся за взятое из ТЗ. Проверенный версионированный словарь интерпретирует наблюдаемые признаки. Неизвестность утверждения запрещает использование в качестве авторитетного источника. Если собственного шифра нет, система сохраняет этот факт, собственный номер отдельно и запрос уточнения; не придумывает шифр из названия папки.

Инварианты БД: ссылки только в пределах разрешённого объекта; уникальность эффекта задания/повторной загрузки; неизменяемость снимков и использованных редакций; отсутствие циклов predecessor; optimistic concurrency для карточек и блокировка/версия процесса для дозагрузки и финализации. Поля контроля конкуренции технические, не новые бизнес-статусы.

### D5. Классификация и редакции

Последовательность: структурное чтение → обнаружение собственных реквизитов/частей → кандидаты полей → проверка по версионированному словарю → разрешение согласованных признаков → связи/редакции → решение о допуске. XML читается по полной схеме и пути, не по имени leaf-узла: `number` встречается у акта, приказа, сертификата и приложения.

Источники: собственные поля XML, титул и основная надпись, таблица изменений и штампы, контекст документа; имя файла/папки — слабый сигнал. Несколько сильных противоречащих источников требуют уточнения. Марка РД, вид ИД и раздел Матрицы — разные справочники со связями, не один enum. Например, ВК требует контекста для ИОС2/ИОС3; ГИ нельзя просто объявить новым разделом ПД.

Уверенность оценивается для каждого поля, калибруется на validation по объектам. Порог Exact Match 0,90 — приёмочная метрика, не заданный порог принятия. При отсутствии численной оценки сохраняется метод и основание, число не придумывается. Для уточнения показываются варианты и реальные фрагменты; смена значения не стирает машинную гипотезу.

Текстовые и визуальные признаки подписей/печатей/штампов хранятся отдельно от результата криптографической проверки электронной подписи. Скан бумажного акта допускается без ЭП. Для электронного представления отсутствие проверенного подтверждения подписания не превращается в утверждение. Отдельный `.sig` не добавляется в список разрешённых файлов без изменения контракта.

Редакции связываются по предметной идентичности и доказательствам замены; выбирается последняя применимая утверждённая редакция для конкретной области и времени проверяемых работ. Изменение части листов не отменяет все остальные листы. Не переносить решения инспектора на изменившиеся доказательства автоматически.

Альтернатива «один запрос к языковой модели возвращает готовую карточку» отвергнута: она не обеспечивает различение собственных ссылок, прослеживаемость и достоверное утверждение. Семантическая модель помогает извлечению, решения о допустимости определяются проверяемыми правилами.

### D6. Матрица, извлечения и координаты

Импортировать 132 реальные строки Приложения 1 в неизменяемый исходный слой с номером строки и хешем. Сформировать проверенную конфигурацию Params по §8: идентификаторы/коды, section, типы/единицы, источники, trigger_logic, regex, границы и нормативные ссылки. В XLSX нет полного набора этих полей: генерация 132 фиктивных правил недопустима. Соответствие кодов и исполняемых правил каждой строке утверждается администратором; неразрешённые строки не считаются покрытыми. Для готовности модуля к полной приёмке все 132 строки должны иметь проверенный план извлечения и проверки входных доказательств.

Источник с `;` не превращается автоматически в AND/OR. Правила хранят типизированное дерево источников/альтернатив, применимость, единицу покрытия и границы. Исходный текст сохраняется для ревью. Старые значения «критическое (приостановка работ)» импортируются только как raw; семантика решения берётся из итогового PDF: HIGH/MEDIUM/LOW — приоритет экспертного просмотра, не санкция.

Для текста использовать regex и семантические якоря с Sentence-BERT all-MiniLM-L6-v2 либо совместимым аналогом, как допускает §9.1. Конкретный OCR-провайдер выбирается воспроизводимым сравнением на validation, с возможностью обработки в изолированном контуре. Внедрить обработку текстовых, сканированных и смешанных PDF; DOCX-таблиц и XML-значений. Включить CV PDF: линии, размерная линейка, калибровка, расстояния. Нет масштаба — нет достоверного измерения.

Locator содержит страницу исходного PDF и номер листа отдельно. Geometry нормализуется после CropBox/MediaBox/Rotate. Для DOCX фиксируется версия детерминированного renderer и сопоставление абзац/таблица → производная страница; для XML — path → стабильное отчётное представление. Хеш исходного файла сохраняется отдельно от хеша производного; координаты чужого PDF нельзя приписывать XML. Это позволяет построить проверяемые `Evidence_Fragments` и viewer.

Redis хранит независимый от объекта результат чтения по file_hash + версия parser/renderer/нормализации. Решения о применимости, ссылки и итог Checks не переиспользуются только по hash. Потеря Redis не должна терять постоянные данные. В ответах Python валидируются типы/геометрия/версии; содержимое документов не может менять инструкции обработчика или исполнять код.

### D7. Ожидаемый состав и комплектность

Два разных реестра: **что фактически поступило** и **что требуется для объекта/работ**. Второй строится из проверенных правил Матрицы, состава проекта, ведомостей РД и общих данных (§3–6). Реестр ИД помогает сопоставлению, но сам по себе не доказывает полноту всех работ объекта. Извлечённые требования показываются инспектору с источниками; подтверждение создаёт версию перечня. Это отдельное действие от принятия однозначных метаданных.

Каждое требование содержит стадию, вид/раздел, ключ/область работ, обязательность/применимость, количество/листы, AND/OR-источники, основание, версию и автора подтверждения. Администратор утверждает базовые правила, инспектор — применимость и состав конкретной проверки. Редактирование не должно задним числом менять основания старого запуска.

Оценка требования: определить применимость → найти покрывающие его документы/части → проверить область и редакцию → проверить набор доказательств. Один акт не покрывает все работы того же вида. Повторные форматы не увеличивают счётчик. Ожидаемое количество не берётся из примера «5 из 15» и не равно числу загруженных файлов.

Результат хранит все причины. Для отображаемого исхода конкретного параметра: доказанная неприменимость → NOT_APPLICABLE; неизвестная применимость, противоречивые метаданные или редакция → CLARIFICATION_REQUIRED; отсутствующий обязательный документ/фрагмент → MISSING_EVIDENCE; имеющиеся, но несопоставимые источники → NOT_COMPARABLE; только затем допуск к сравнению. Такой порядок — техническая детализация §9.2; причины не теряются из-за выбора одного исхода. Найденная слабая кандидатная связь не превращается в отсутствующий документ без объяснения неопределённости.

По стадии рассчитываются ровно девять статусов ТЗ. Пока состав/классификация не определены достаточно, соответствующая оценка nullable с объяснением «полнота не определена»; это отсутствие оценки, а не новый enum. Фактические числа файлов и документов остаются доступны. Для сценария известная частичность имеет приоритет PARTIALLY_LOADED; иначе используется сочетание присутствующих стадий. FULL без полного закрытия требований не выводится только из трёх непустых папок.

### D8. Задания, снимки и инкрементальность

В транзакции с записью Run создаётся Outbox. Отправитель использует устойчивую очередь, persistent messages, publisher confirms и контроль маршрутизации. Сообщение содержит идентификаторы, версию схемы и trace context, без бинарных документов. Node worker подтверждает доставку после постоянного сохранения исхода. Идемпотентность закрепляется уникальными ключами run/job, lease с fencing защищает от позднего обработчика. Таймаут файла: первоначальная попытка + максимум два повтора с задержкой, затем долговечный исход и уведомление администратора; неисправимый вход повторно не крутится.

`process_id` стабилен для проверки до финализации, каждая принятая дозагрузка/уточнение создаёт новый Run. InputSnapshot канонически сериализует object/process, файловые хеши и части, выбранные редакции/решения, matrix/dataset/model/parser/requirements versions; SHA-256 даёт `input_manifest_hash`. Порядок представления массива файлов не должен случайно менять семантически тот же снимок; версии и содержательные изменения должны менять его.

После изменения построить зависимости «файл/часть/редакция/метаданные → требования/источники → параметры/evidence_group». Пересчитать транзитивно затронутые группы. Глобальное изменение применимости может затронуть много параметров, но это должно объясняться зависимостями, а не безусловным полным прогоном. Старые протоколы/решения не перезаписываются.

Сервер проверяет матрицу допустимых действий из LC-04; технический прогресс job хранится отдельно от process status. В ходе этапов подготовки данных процесс не переводится в READY. Дальнейший владелец процесса — модуль §9.2, который устанавливает READY только после сохранения настоящего протокола. Если этот потребитель ещё не реализован, система явно показывает отсутствие результата проверки; нельзя завершать интеграционную приёмку моковым READY.

Дозагрузка, публикация результата и финализация используют общий транзакционный контроль версии/блокировку процесса. При финализации фиксируется именно валидированный снимок. Поздний результат другого run не становится текущим. Автоматический источник после FINALIZED создаёт уведомление о новых документах, но не меняет протокол и не начинает новую проверку без действия инспектора.

### D9. Безопасность, эксплуатация и восстановление

Роли и доступ к объекту проверяются в каждом маршруте и команде, в том числе при получении evidence и оригиналов. Предлагаемый доступ: назначенный инспектор управляет документами/уточнениями своего объекта; администратор управляет правилами и назначениями; ML-инженер получает предусмотренные учебные/диагностические данные, но не доступ ко всем оригиналам по факту роли. `role = null` не даёт предметных прав.

TLS 1.3 для внешнего и межсервисного обмена в целевом контуре; шифрование PostgreSQL/файлов/временной области/резервных копий средствами среды, раздельные секреты и минимальные права сервисов. Логи не содержат тела запросов с base64, OCR-текстов и секретов. Аудит отдельно от debug: действительный пользователь, объект, действие, серверное время, IP с учётом настроенного trusted proxy и основание.

Prometheus/Grafana для метрик, ELK для JSON-логов; end-to-end request/job correlation, счётчики отказов, непрочитанных областей, неопределённых полей, очереди, retries и конфликтов. Администратору настраиваются email и Telegram; ошибки доставки видны и повторяются по ограниченной политике. В этом change описана реализация уведомлений, а не разрешение агенту отправлять реальные сообщения при подготовке плана.

Ежедневный контроль SHA-256 и резервные копии с удержанием 30 дней. Одних ежедневных копий недостаточно для RPO 15 минут: добавить журналируемое восстановление БД и непрерывное/частое копирование неизменяемых оригиналов с согласованной контрольной точкой. Проверять восстановление ссылок и хешей, outbox и незавершённых заданий. RTO ≤1 часа, RPO ≤15 минут. Для SLA 99,9% нужны эксплуатационные средства отказоустойчивости, IDS/DDoS и наблюдение в целевой среде; локальный compose не является доказательством SLA.

### D10. Проверки на реальных примерах и приёмка

Октябрьская используется как регрессионный корпус разработки, без объявления его скрытым тестом:

- XML АОСР №52: root `aosr`, собственные номер/дата и ссылка `workDocumentationSectionCode = 23.009-Р-ГИ`; одинаковые leaf-названия в других частях XML не смешиваются.
- `23.009-Р-П-КЖ_ГИ-изм3 (1).pdf`: внутренний шифр ГИ и штамп «В производство работ», несовпадение слабого сигнала имени.
- Редакции ГИ изм.1/3/4: основание актуальности и изменённые листы, не сортировка по времени загрузки.
- Несколько представлений акта, приложения и повторяющиеся сертификаты: физическая дедупликация отдельно от предметной принадлежности.
- Реестр ИД с десятью актами: известный перечень этого реестра не объявляется полным составом всего объекта.

Для негативных/геометрических сценариев разрешены явно обозначенные синтетические fixtures: 50/200 МБ и +1 байт, CropBox/Rotate, смешанные страницы, заражённый тестовый образец в изолированном стенде, обрыв соединения, конфликт snapshot/finalize. Они не заменяют реальные количественные испытания.

Стенд и критерии: QA-05–QA-07. Фиксировать исходные файлы/метки, объекты, версии, объём выборки и оборудование. Пороги не подбирать на hidden test. Изоляция по объекту включает все версии и представления. Отчёт публикует CER/WER, coverage/abstention, ключевые поля, linkage, IoU, интервалы и разбивку; общего среднего недостаточно. Испытание 132 параметров требует проверенного полного реестра и потребителя сравнения.

### Зависимости за пределами загрузчика

§2 — зафиксированная ТЗ нормативная база, её произвольное обновление не входит в change. §9.2 — предметное сравнение и полный протокол; change поставляет gate/извлечения/снимки, интеграционная приёмка требует реального потребителя. §9.3 — решения о нарушениях и финализация; change поддерживает уточнение метаданных и транзакционную защиту, но не заменяет все действия инспектора. §9.4 и §14 — GOLD/обучение: подготовлены источники и версии, публикация модели остаётся отдельным модулем. §9.5 — свободный поиск. §9.6 — действительный коннектор, УКЭП исходящих запросов, retry 1/5/15 минут и синхронизация; правила исходящих повторов не смешиваются с двумя повторами обработки файла. Прочие модули §7 — полные dashboard, администрирование норм и еженедельный ML-отчёт.

Для внешних возможностей зафиксировать владельца интеграции, версию контракта и ссылку на реализацию при выпуске. Если их нет, модуль может демонстрироваться отдельно, но совместные приёмочные пункты остаются невыполненными. Ни заглушка, ни наличие planning-artifacts не закрывают такие пункты.

## Risks / Trade-offs

- [JSON/base64 увеличивает трафик и риск расхода памяти] → потоковый декодер, ограниченные временные данные, нагрузочный тест настоящего пути через Nginx.
- [Шифры встречаются в ссылках и приложениях] → структурный контекст, собственные реквизиты, отдельные связи и регрессии на акте №52.
- [Состав проекта/перечень ИД неполон] → подтверждённая версия ожидаемого состава; неизвестность не выдаётся за полноту.
- [Автоматическая нормализация ломает обозначение] → raw + normalized, NFC и значимые знаки, проверяемый словарь.
- [Объединение представлений скрывает различия] → проверка реквизитов и содержания, конфликт остаётся спорным, оригиналы неизменяемы.
- [Позднее задание меняет старый результат] → fencing, идентификатор run, снимок и транзакционный контроль процесса.
- [132 текстовых правила не равны 132 готовым алгоритмам] → проверенный реестр планов, критерий полноты по каждой строке, запрет фиктивного NEGATIVE_VERIFIED.
- [Пилотные данные малы и использованы при разработке] → object split, отдельный validation/hidden test, организаторская фиксация и все пороги §14.
- [Локальный compose не доказывает безопасность и SLA] → отдельная эксплуатационная проверка целевого контура, журнал ограничений приёмки.

## Migration Plan

1. Добавить новые таблицы миграциями без удаления User/AuthSession и без переименования существующих auth-endpoints; проверить прямую миграцию и восстановление резервной копии.
2. Поднять закрытое хранилище, карантин/антивирус, Redis и worker/Python; настроить секреты, шифрование, очереди и мониторинг. Сохранить текущий auth-сценарий.
3. Внести проверенные словари и исходную Матрицу; привязать все 132 строки к версиям правил, не использовать фиктивные seed-данные.
4. Включить backend API и UI загрузки для тестового объекта, затем выполнить регрессионные, отказные, нагрузочные и качественные испытания.
5. Подключить реальные потребители сравнения/протокола/финализации и выполнить совместные критерии; не объявлять READY из загрузчика.
6. Выпуск разрешён после фиксации результатов по таблице соответствия и явного перечисления ещё не выполненных общесистемных требований. Полная приёмка ТЗ требует отсутствия таких невыполненных обязательных пунктов.

Откат: запретить новые загрузки, остановить публикацию/потребление новых заданий, сохранить принятые оригиналы и снимки, вернуть совместимые версии приложения. Не удалять принятые документы и историю при rollback. Для несовместимых данных использовать проверенную процедуру восстановления, а не обратную миграцию с потерей исходников.

## Open Questions

Следующие параметры заполняются до испытаний и не меняют выбранные specs или архитектуру: адреса и ключи целевой инфраструктуры; конкретный OCR-движок после validation-бенчмарка; ресурсный профиль стенда; пороги технических алертов; контакты каналов администратора; предоставление организатором независимого hidden test и утверждённых эталонных связей.

Конфликт формата DWG вынесен отдельно в D11 как ограничение заявления о выполнении конкретной строки ТЗ. Все предлагаемые здесь контракты подлежат ревью change перед реализацией; ответа пользователя о режиме классификации недостаточно, чтобы считать уже утверждёнными фактические перечни документов каждого объекта.
