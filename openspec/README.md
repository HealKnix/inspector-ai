# Рабочий OpenSpec

Рабочий корень OpenSpec с 17.09.2026 находится **в этом Git-репозитории**, рядом с frontend/backend. Все команды ниже выполняются из корня `inspector-ai`. Внешняя папка материалов больше не содержит активного `openspec/`.

Действующее ТЗ и приложения доступны после клонирования: [реестр источников](../docs/requirements/SOURCES.md). Основной документ — итоговый PDF; прежние модульные спецификации и карта 24 changes остаются производными материалами.

## Семь активных changes

Разделён один большой `add-document-ingestion-and-completeness`. Семь changes покрывают его функциональные части; это **не весь проект и не сокращение двухнедельного релиза**. Общие работы C01, C05/C18, C23, C24 сохранены отдельно; остальные модули сравнения, протокола, интеграций и обучения по-прежнему нужны проекту.

В каждом каталоге есть `.openspec.yaml`, `proposal.md`, `design.md`, `specs/<capability>/spec.md`, `tasks.md`. У каждого активного change свой capability, без конкурирующих дельт на одну спецификацию. Backend, frontend и ML — задачи внутри функционального change, с общей проверкой результата.

Первый change начинается с таблиц объектов и назначений доступа (исходная задача 2.1 перенесена из C01). Его приёмка проходит путь от пустого списка объектов через создание и выбор объекта до загрузки привязанного файла. Объект больше не предполагается заранее существующим или вручную вставленным в БД. Полный паспорт и бизнес-жизненный цикл объекта в этот минимум не входят.

## Контекст и зависимости

ING реализуется в ветке `feat/safe-document-ingestion` вместе с необходимой частью
C01; подтверждённая политика доступа описана в CONTRACTS.md. Код, проверенные
сценарии и ограничения перечислены в [отчёте ING](changes/add-safe-document-ingestion/evidence.md).
Остальные changes и общая приёмка C24 сохраняют собственные открытые задачи.

- [CONTRACTS.md](CONTRACTS.md) — владельцы сущностей, API/события, два уровня снимков, матрица прав и нерешённый переход после ошибки/уточнения.
- [SHARED_BACKLOG.md](SHARED_BACKLOG.md) — открытые общие обязательства. `C05-C18` в машинной карте означает совместное направление **C05 и C18**, а не диапазон всех номеров между ними.
- [SPLIT_MAP.md](SPLIT_MAP.md) и [delivery-map.json](delivery-map.json) — распределение всех **98 исходных задач и 40 требований**. Несколько владельцев означают разделённую обязанность, а не необходимость повторно реализовать её целиком.
- [Исходный change](superseded/2026-09-17-add-document-ingestion-and-completeness/proposal.md) сохранён без изменения содержимого в `superseded/`. Это заменённый план, **не завершённый архив**. Исторические относительные ссылки в нём могут вести к старой структуре; действующие источники указаны выше.

Готовность движка EXT не закрывает все 132 конфигурации Матрицы. Генерация события не закрывает доставку Telegram/email. Проверка порта финализации не закрывает испытание с настоящим протоколом. Соответствующие общие задачи остаются открытыми.

## Как отслеживать выполнение

```sh
openspec list
openspec status --change add-safe-document-ingestion
openspec instructions apply --change add-safe-document-ingestion
node openspec/verify-planning.mjs
openspec validate --all --strict
```

Если в Windows `openspec` не найден в PATH, используйте установленный shim, например `& "$env:APPDATA\npm\openspec.cmd" list`. Дополнительный проект или второй OpenSpec-корень создавать не нужно.

`openspec status` показывает готовность **артефактов планирования**. Реальное выполнение — чекбоксы `- [ ]` / `- [x]` в `tasks.md`; `openspec list` и `verify-planning.mjs` показывают их количество. Отмечать задачу можно после её реализации и указанной проверки. Результаты проверок, версии корпуса/модели и ограничения записывайте в `evidence.md` своего change при реализации.

Изменение спецификации и соответствующий код включайте в один проверяемый PR либо явно связывайте PR между собой. Git показывает историю планов и выполнения вместе с кодом. Сам перенос файлов и создание artifacts не являются коммитом или подтверждением готовности функций.

После проверки реализации выполните штатный sync/archive workflow. Только реализованные требования попадают в `openspec/specs/`; сейчас main specs намеренно пусты. При архивировании обновляйте ссылки указателя и карту, если меняются владельцы или имена. Старый объединённый change не возвращайте в active и не архивируйте как выполненный.

`verify-planning.mjs` — проверка структуры и сохранности разделения: хеши истории, полнота карты, владельцы/зависимости, ссылки и число отмеченных задач. Она не запускает приложение и не доказывает выполнение требований. Не удаляйте `[SRC-x.y]` и `[SRC-REQ ...]`: это связи с исходным планом, а не номера текущих задач.

## Работа четырёх участников в пределах двух недель

Назначения P1–P4 — предложенное распределение, а не новые роли приложения. P1 ведёт backend/общие контракты; P2 — frontend; P3 — OCR/извлечение/CV; P4 — Матрицу, правила и координацию проверок. P3 нельзя одновременно загрузить всеми ML-задачами на полную мощность: независимые измерения, подготовку корпуса и конфигураций помогают делать P4 и остальные участники.

| Окно    | Результат и параллельная работа                                                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Д1–Д2   | C01 и общие контракты; P2 готовит UI по схемам; P3 проверяет OCR/CV на разрешённом validation; P4 формализует Матрицу и подтверждения. Решения LC-08, права и целевая среда должны получить владельцев. |
| Д2–Д5   | ING и PAR соединены; ID развивается на реальных ParseArtifact; UI приёма/viewer проверены. Правила C05/C18 готовятся параллельно.                                                                       |
| Д4–Д8   | ID, EXT и GEO; COM готовит алгоритм и интерфейс по согласованным схемам. Другие модули проекта подключают реальные входы.                                                                               |
| Д7–Д11  | COM и INC, полный реестр 132/132, сравнение/протокол/интеграции, общие уведомления и эксплуатационные средства.                                                                                         |
| Д12–Д14 | Совместная приёмка C24, нагрузка, скрытая оценка, восстановление и исправления.                                                                                                                         |

Это целевые окна, а не доказанная оценка трудозатрат. На Д2 и Д5 график пересматривается по реальной скорости, качеству OCR и готовности контрактов. Семь changes помогают проверять и объединять работу по частям, но сами по себе не гарантируют полный выпуск за 14 дней. Обязательные требования не вычёркиваются ради календаря.
